# Исследование интеграций и выбор адаптеров Tibicen

Срез официальной документации на 22 октября 2026 года. Исследование ниже описывает механику и границы нескольких интеграций: что Tibicen сможет надёжно подключать и какой контракт для этого нужен. Оно не устанавливает, какие инструменты лучше подходят пользователям, и не задаёт очередь их рекомендации или разработки. Данных о пользовательских кейсах и сравнительной пользе для безусловного приоритета «следующий — Spec Kit» здесь нет.

Список кандидатов неполный. Основания технической оценки — сохранность приложения, точное согласие, отсутствие автоматических коммитов и постоянного runtime. Наличие инструкции установки у upstream не означает проверенную совместимость. Ссылки на main отражают исследованный срез; перед реализацией закрепляются конкретные release/SHA и состав.

## Основание пользовательской рекомендации

Сначала Tibicen выясняет по проекту и доступному диалогу задачу, ожидаемый результат и фактическое затруднение. Затем проверяет достаточность текущих правил и встроенных возможностей. При подтверждённом пробеле сравнивает подходящие варианты по значимым возможностям, ограничениям среды и команды, добавочной пользе, ручной работе, стоимости и сложности установки и сопровождения. Пользователь получает одну обоснованную рекомендацию; сохранение текущего решения допустимо.

Наличие адаптера позволяет выполнить подключение, но само по себе не делает инструмент подходящим. Если полезное решение пока нельзя надёжно подключить, нужно показать конкретный gap и допустимый ручной путь, сохранив полезную настройку. Поддержанный инструмент, не покрывающий существенную потребность, не становится заменой по умолчанию. Например, просьба отвечать короче может полностью решаться текущими правилами, а достаточный принятый процесс не требует миграции на OpenSpec.

## Какие виды адаптеров нужны

| Область | Что требует отдельного контракта | Решение |
|---|---|---|
| Рабочий процесс | Служебная структура, стадии, шаблоны, команды, обновление и сохранение существующего процесса | Первый ограниченный OpenSpec реализован; дополнительные процессы выбираются по непокрытым кейсам |
| Coding tool | Точки входа, формат/место скиллов и конфигов, startup и свидетельства загрузки | Подтвердить заявленные профили; расширять по агентам целевых проектов и выявленным пробелам |
| Обычный скилл | Источник, полный SHA, лицензия, ресурсы, целевой формат, загрузка и полезность | Общий механизм Agent Skills; отдельный адаптер для каждого названия не нужен |
| Пакет с hooks/plugins/runtime | Помимо материалов — исполняемые эффекты, глобальный scope, способы отключения и обновления | Только отдельный проверенный контракт; обычной установкой SKILL.md не считать |
| MCP | Формат целевого конфига и параметры транспорта/секретов | Использовать существующие адаптеры stdio/config; специальный адаптер сервиса нужен лишь при дополнительном неподдержанном поведении |

Общий формат Agent Skills предусматривает SKILL.md и необязательные scripts/references/assets. Поэтому единицей установки должен быть проверенный комплект нужных ресурсов, а не только один Markdown-файл. Это основание для общего обработчика, а не универсальное подтверждение любого скилла. [Спецификация Agent Skills](https://agentskills.io/specification).

## Процессные кандидаты

| Потребность для исследования | Кандидат | Что исследовать в конкретном кейсе | Основная цена поддержки |
|---|---|---|---|
| Связать требования, изменения и задачи | OpenSpec | Подходит ли его процесс ограничениям проекта; ограниченный адаптер уже есть, но это не основание рекомендации | Живая загрузка/рабочий цикл, обновления версий, дополнительные форматы агентов |
| Сохранить принятые constitution, спецификации, планы и задачи либо восполнить подтверждённый пробел | Spec Kit | Достаточен ли существующий процесс и чем этот вариант полезнее доступных альтернатив | Отдельный CLI, scripts/templates, выбранная integration и учёт её собственного install manifest |
| Поддержать более широкий продуктовый/архитектурный процесс | BMAD | Нужны ли команде конкретные роли/модули и оправдана ли сложность | Полнота модулей, setup-эффекты, несколько runtime-инструментов, различающиеся линии версий |
| Улучшить проверку завершения, отладку, ревью или планирование | Superpowers | Достаточны ли текущие правила, отдельная практика или требуется полный процесс | Полный процесс включает bootstrap/plugins и собственные решения о worktrees, делегировании и Git |
| Вести длительную работу по фазам и сохранять состояние | GSD | Есть ли совместимый с границами Tibicen способ сохранить нужный команде процесс | Execution workflow включает коммиты и управление исполнителями; это конфликтует с текущими границами Tibicen |

### OpenSpec

Официальная установка создаёт процесс и генерируемые файлы выбранных tools; отдельные настройки профиля/доставки бывают глобальными. Документация также предупреждает об очистке старых интеграций при init. Для Tibicen оправдан ограниченный путь с точными файлами и собственными инструкциями к нативным командам, с отдельной установкой CLI. [Установка](https://github.com/Fission-AI/OpenSpec/blob/main/docs/installation.md), [настройка](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/start/setup.md).

Текущий адаптер поддерживает 1.14.3, локальный spec-driven и форматы Codex 0.157.0 / Claude Code 2.1.283. Механически проверены ресурсные хэши, сохранность, повтор, восстановление и доступность нативного шаблона CLI. Внешние stores, смена зарегистрированного агента/версии и другие версии CLI пока требуют отдельной миграции/адаптера. Живая приёмка PROC остаётся открытой.

### Spec Kit

Текущая документация использует явный выбор integration и отдельные sh/ps/py варианты scripts. Init создаёт структуру, шаблоны и интеграционные файлы; Git-функции вынесены в отдельное extension и не установлены по умолчанию. Это делает ограниченный вариант без Git extension перспективным, но сам по себе флаг не доказывает отсутствие побочных эффектов всех стадий. [Core commands](https://github.com/github/spec-kit/blob/main/docs/reference/core.md).

У Spec Kit уже есть manifest-aware upgrade: локальные правки интеграционных файлов блокируют обычное обновление, shared scripts/templates учитывают прежнюю управляемую копию. Адаптер Tibicen должен согласовать это владение со своим паспортом; force не должен становиться обычным способом обновления. [Upgrade](https://github.com/github/spec-kit/blob/main/docs/upgrade.md).

Если пользовательские кейсы обоснуют этот адаптер, перед реализацией нужен небольшой изолированный spike: закрепить релиз CLI/исходные материалы, один target tool и один вариант scripts; получить точный install manifest и эффекты init/adopt/upgrade, проверить запрет коммитов и сохранность локальных шаблонов/constitution/specs. После этого — отдельный OpenSpec change и SKILL/PROC-подобная новая сессия. Исследование не назначает Spec Kit следующим адаптером или обязательной частью первого выпуска.

### BMAD

Upstream описывает отдельную стабильную линию v6.12 и main как v7 preview alpha с меняющимися skills/setup. Также перечисляются разные способы установки и дополнительные инструменты. Поэтому один адаптер «BMAD latest» не имеет достаточно определённого контракта. Если пилотная команда уже использует BMAD, сначала выбрать конкретную линию/модули и проверить adoption; универсальную автоматическую установку отложить. [Официальный README](https://github.com/bmad-code-org/BMAD-METHOD).

### Superpowers

Полный пакет — методология поверх composable skills с bootstrap и установкой, зависящей от coding tool. Описанный workflow включает worktrees, варианты делегирования, тестирование и Git-коммиты. Для Tibicen это отдельная интеграция с собственными эффектами; установка одной полезной практики через проверенный скилл должна оцениваться отдельно от включения полного процесса. [README и workflow](https://github.com/obra/superpowers/blob/main/README.md#the-basic-workflow).

### GSD

Настройки описывают planning.commit_docs, но отключение коммитов planning-файлов не доказывает отключения коммитов кода. Execution workflow прямо связывает закрытие плана с production/SUMMARY commits. До проверенного совместимого режима без коммитов полный адаптер не подходит текущему продуктовому контракту. Существующую .planning/ можно распознавать и сохранять при анализе; это ещё не поддержка исполнения GSD. [Конфигурация](https://github.com/gsd-build/get-shit-done/blob/main/docs/CONFIGURATION.md), [execute-plan](https://github.com/gsd-build/get-shit-done/blob/main/get-shit-done/workflows/execute-plan.md).

## Ponytail и Caveman

23.10.2026 канонический Ponytail подтверждён по README автора: [DietrichGebert/ponytail](https://github.com/DietrichGebert/ponytail/tree/09c434ab73ca43761c5d8b0c5d341926c2fba710). Для SKILL-серии закреплены полный SHA 09c434ab73ca43761c5d8b0c5d341926c2fba710, skills/ponytail/SKILL.md, MIT и точные Git blob/SHA256. Выбран самодостаточный skill-only состав без plugin/hooks/npm-установщика; домашняя копия не использована. Историческая редакция и полезный исчезнувший пример отдельно закреплены для обновления. [Состав и границы](../evals/MATRIX.md#pinned-sources) подтверждают источник фикстуры, пока не живое применение скилла и не его универсальную пригодность.

У Caveman найден upstream JuliusBrussee/caveman и отдельный skills/caveman/SKILL.md. README различает установку только скилла и полный продукт с CLI/proxy/прочими частями. Ограниченный skill-only состав можно исследовать при подтверждённом пробеле; предпочтение лаконичности само по себе не обосновывает даже такую установку. Полный установщик изменяет существенно больше. [README](https://github.com/JuliusBrussee/caveman#say-less-the-caveman-voice), [исходный скилл](https://github.com/JuliusBrussee/caveman/blob/main/skills/caveman/SKILL.md).

Лицензирование нужно закреплять вместе с редакцией: upstream указывает Apache-2.0 начиная с 3.0.0, а прежние выпуски сохраняют свои условия. Старое представление «Caveman всегда MIT» неприменимо ко всем версиям. Это ещё одна причина проверять фактический источник/NOTICE и выбранные материалы, а не название. [Licensing](https://github.com/JuliusBrussee/caveman/blob/main/LICENSING.md).

Скилл также ссылается на соседние варианты ultracave/megacave: перед установкой нужно проверить, какие ссылки действительно необходимы выбранному режиму, и не обещать отсутствующие режимы. Для SKILL-приёмки остаются фиксация SHA/состава, обычные гейты источника и живое наблюдение загрузки/применения. Маркетинговые оценки экономии токенов из README не становятся обещанием Tibicen.

## Как формировать очередь адаптеров

Ближайшая принятая инженерная работа — закончить стенд и наблюдаемую приёмку текущего OpenSpec и хотя бы одного дополнительного скилла. Эти проверки доказывают работу конкретных интеграций, а не преимущество их для любого пользователя. Отдельная [программа PREF](../evals/PREFERENCE_SELECTION.md) проверяет качество выбора, включая разные контексты одного запроса.

Для следующих адаптеров нужны реальные или явно обозначенные репрезентативные кейсы: задача, существующий процесс, ограничения и оставшийся пробел. Сначала сравниваются подходящие решения, включая сохранение текущего; затем оценивается, какое новое покрытие даст адаптер, сколько ручной работы снимет и сколько будет стоить его реализация/сопровождение. Гипотетический кейс не выдаётся за подтверждённый спрос. Без этих оснований универсальная очередь названий не назначается. Существующие проекты выбранного процесса должны входить в его приёмку вместе с первоначальной настройкой.

Новый адаптер оправдан, когда общий механизм файлов/источников не выражает его стадию, эффекты или обновление. Для допуска нужны версия и происхождение, точные пути/действия, сохранение локальных решений, проверенные ограничения запуска и отдельная новая сессия. Популярность и число скиллов не заменяют эти критерии.
