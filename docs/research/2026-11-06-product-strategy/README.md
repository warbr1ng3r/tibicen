# Tibicen: choose the next product bet

**Research date: 6 November 2026, Europe/Moscow. Completed research: six source lanes, two independent reviews and root synthesis.** English is canonical; the adjacent Russian edition is README_ru.md. This study recommends decisions and experiments; it does not approve implementation or replace the [roadmap](../../DEVELOPMENT_PLAN.md).

## Decision under investigation

Choose between two low-cost delivery hypotheses for an existing-project repair: Tibicen's current integrated workflow, and a native-first diagnosis/repair reference or small utility. A maintainer with accepted local decisions and an immediate next task is a practical first case because the current product fits it; this is not a validated beachhead or proof of stronger demand than other segments. Keep first-time setup available; do not expand merely to match more tools.

This is a hypothesis, not a demonstrated market position. Native audits, ordinary agent prompts and existing package managers may already solve the job well enough. A legitimate result of the next comparison is to keep Tibicen as a maintained small utility rather than grow it into a platform.

## Why another feature inventory is insufficient

The previous [post-1.3 study](../2026-11-05-post-1.3-priorities/README.md) identified task-aware diagnosis and narrow local MCP repair. Those directions have since shipped. Repeating them as new strategic findings would confuse history with opportunity.

Current [Claude documentation](https://code.claude.com/docs/en/memory#audit-your-instruction-files) describes an instruction audit with proposed edits and a version requirement. That is declared native capability, not a comparison run performed here. The [competition lane](competition.md) also checks agent package/deployment and evaluation alternatives. A multi-agent wrapper, a manifest or a verification report alone is not an established advantage. The [independent challenge](challenge.md) additionally checked native migration: Claude documents reading other tools' instructions during initialization and an import path for supported configuration. Migration is therefore a comparison case, not an unoccupied category; this documents capability, not successful preservation here.

The central product question is whether a particular user reaches a correct, preserved and useful setup with less active work than with a competent native method. Our own tests are necessary technical evidence and cannot answer that question alone.

## Ranked strategic choices

The ranking is a product judgment from the lanes, not a market-size score or forecast. Existing init/adopt functionality remains available under every option.

| Choice | Proposed decision now | Evidence that could change it |
| --- | --- | --- |
| Existing-project repair through the current integrated workflow | **Peer first candidate.** One named change event, existing decisions and a next task; reuse 1.4.1. Selected for current-product fit and low test cost, not validated segment demand. | A competent native method is equal or easier; no qualifying user wants the extra workflow. |
| Native-first repair reference or small utility | **Peer first candidate.** Let the user keep native execution if concise diagnosis and repair guidance help more than another application workflow. Reference usefulness is also unmeasured. | Native documentation already provides the answer with no additional effort; no useful diagnostic contribution remains. |
| Broad first-time agent setup | Keep as an entry and useful capability; do not make generic generation the growth thesis. | Repeated unaided starts show a specific gap native initialization leaves. |
| Team baseline distribution and drift maintenance | Conditional later expansion. Compare Git/shared files and APM/AgentRC first; legitimate local deviations must survive. | Independent teams repeatedly need the same unresolved operation, with a named owner and maintainable scope. |
| Hosted organization control, orchestration or a marketplace | Defer. This changes the product's operating model and competes with established infrastructure. | Evidence of a buyer, an unmet operational need and capacity to support the new trust/runtime contract. |
| A maintained free utility with bounded support | A valid durable outcome, including if the native comparison wins most cases. | Incremental repeated value and a sustainable operating budget justify more investment. |

Do not turn every upstream feature into a Tibicen adapter, every user complaint into a new subsystem, or every website impression into an installation project. A narrower reliable promise can be more useful than a large support matrix. Choosing the strategy does not authorize dropping existing supported contracts.

The [repeat-value study](retention.md) keeps three concrete future branches open: a local maintenance assistant that proposes PRs for repeatedly observed objective drift; an interoperability advisor where host differences defeat an otherwise useful team baseline; and a curated repair/evidence reference when users value diagnosis but prefer native execution. Each needs its own residual-gap test. The last is a credible alternative delivery model if Tibicen's application workflow adds more effort than it removes.

## Economics and the upkeep boundary

The [economics lane](economics.md) distinguishes a maintained free utility, optional sponsorship, a fixed-scope manual engagement, recurring team support and hosted software. The smallest proposed commercial step is one bounded service after usefulness, an available operator and a real budget holder are established. Competitor asking prices and funding mechanisms establish neither Tibicen demand nor owner payout eligibility. No price, revenue target or customer is assumed.

The [trust lane](trust.md) recommends measuring the cost of current promises before adding more native adapters. Record actual review, reproduction, translation, release and support effort during existing maintenance work. A concise user-facing proof can reuse current records: starting setup, exact approved change, preserved decisions, observed next task and recovery route. This is a presentation of evidence, not another telemetry or security subsystem. Format support, native loading, useful task completion and human benefit retain separate claims.

For the owner, the unresolved choices are how much maintenance time is available and whether commercial operation is desired at all. They are decisions for a later selected packet, not questions that block this research. A sponsorship mechanism does not staff support, and a recurring invoice does not establish a recurring user problem.

## One sequence of experiments, not six backlogs

Each lane offers candidate experiments. **They are a menu, not a cumulative research program.** The sequence below consolidates them; sample sizes and thresholds are proposed attention/budget limits, not validated benchmarks, statistical estimates or new release requirements. No live execution, recruitment or spending is authorized by this report.

1. **Finish interpreting the current native observation in its own effort.** Preserve the failed attempt and remaining unknowns. A future comparison needs a finite, observable route; repairing the evaluator is not itself customer value. Source research, maintenance and preparation of truthful examples can proceed in parallel. Do not repeat a live run just because this study recommends comparison.
2. **Compare one decision-bearing repair through the whole workflow, with a sufficient-setup guard.** Select one concrete existing-project problem, accepted local decisions and a next task. Use equivalent saved starting states, permissions, host/model versions and task criteria; choose the owner's competent current/native method, including native import where applicable. Count Tibicen installation, proposal review, applying changes, assistance and recovery through the fresh accepted task. Neither arm gets hidden defect locations. For both arms, the sufficient-setup guard must avoid unnecessary edits and still complete the ordinary useful task. Before either arm starts, declare finite attempt, elapsed-time and spend caps, with no automatic retries; record total active operator work, elapsed time and model cost separately, retaining unknown costs. Predeclare the benefit that matters for this case without a universal percentage. Continue only when Tibicen preserves protected material, completes the useful task and reduces total active operator work, or delivers a specific tradeoff accepted before the run, without worse task quality. Removing one intervention alone cannot pass if added installation or review work outweighs it. Any unauthorized change or lost accepted decision stops the study. If native is equal/easier, do not expand the integrated workflow for this job; a useful diagnostic contribution can instead justify an artifact-only reference test. If neither approach adds value, keep only the bounded utility/maintenance option. Unavailable execution is inconclusive. The [competition lane's larger three-pair design](competition.md#smallest-comparative-experiment) and other lane experiments are optional later variants, not prerequisites.
3. **If willing people become available, test one promise on six qualified real starts.** Use the existing page, not another redesign. Qualify a real change trigger and next task before showing the proposal. Follow the [pilot policy](../../PILOT.md), agree the protocol and success/time rules, use comparable native/current-method controls and retain all starts, assistance, failures and unknowns. A proposed next-round rule is four completed useful tasks without maintainer rescue and three cases with a comparative advantage under the predeclared whole-work criteria above. Report diagnostic/no-change success separately from fresh useful-task completion, including whether it saved work. Show both all-start outcomes and the eligible-repair subset; never remove failures, assistance or unknowns to improve the repair rate. This tiny convenience sample screens a direction; it cannot estimate the market or general benefit. No cohort or coordinator is assumed.
4. **Only then probe reach and event-driven return.** Choose one job-specific example and one actually verified catalog surface from [distribution](distribution.md); distinguish controlled exposure from organic discovery. At a later real agent/update/repository event, record whether an eligible person chooses Tibicen again, uses a native alternative or declines. Show opportunity counts, unsolicited versus prompted returns, mature follow-up windows and unknowns. Frequent visits are not a goal for temporary scaffolding. Stop multiplying channels or features when useful completion is absent; no exposed cohort means unobserved demand, not rejection.
5. **Consider team or commercial work only on a repeated concrete pull.** A request, interview preference, competitor price or sponsorship link is not paid demand. Start with a bounded manual offer only if the owner chooses a commercial direction and a willing buyer appears. Agree deliverable, exclusions, cost and support before work. A hosted platform, billing system and enterprise guarantee are separate bets, not prerequisites for learning.

These are decision gates rather than a calendar commitment. A useful first planning horizon is the next bounded comparison, then one observed-user round, then a return/commercial decision. Lack of available participants should keep growth claims modest and expansion bounded; it must not reopen the project's voluntary human-research release gate or assign an owner questionnaire.

## Measurement cautions

The following are freshly reopened primary research already present in the [earlier evidence study](../PUBLIC_AGENT_SETUP_EVIDENCE.md), not newly discovered demand signals or Tibicen trials. Abstracts and relevant method/result/limitation sections were inspected on 6 November; no datasets or experiments were rerun:

| Source | Narrow implication and limit |
| --- | --- |
| [Evaluating AGENTS.md, v3](https://arxiv.org/html/2602.11988v3) | In its evaluated settings, context files increased cost without a statistically significant task-success improvement. It supports questioning extra instructions, not declaring Tibicen ineffective. |
| [AGENTS.md efficiency study, v2, 30 March 2026](https://arxiv.org/html/2601.20404v2) | Operational efficiency findings do not include a comprehensive correctness evaluation. Shorter time must be checked against useful output. |
| [Two-agent ablation, v1, 28 July 2026](https://arxiv.org/html/2607.27250v1) | Its two-agent/three-repository evaluation finds limited correctness effects from context delivery. It does not test configuration repair or Tibicen. |
| [METR design update, 24 February 2026](https://metr.org/blog/2026-02-24-uplift-update/) | The authors identify participant/task selection and concurrent-work timing problems in productivity measurement. We should retain refusals, task differences and active-time versus elapsed-time distinctions. It provides no Tibicen effect estimate. |

The studies have different interventions, settings and metrics; they are not combined into a pooled estimate. A pilot must compare Tibicen with the user's competent existing agent method, using comparable starting states, agreed success and preservation criteria, and separately reported assistance. The existing [voluntary pilot policy](../../PILOT.md) remains unchanged. The owner is not assumed available to recruit or answer a questionnaire.

## Scope and access

This is purposive public-source research and repository reading. Original reports establish reported experience; vendor documentation establishes a declared contract; code and release records establish their own bounded behavior. Closed/corrected reports and sufficient native methods are counterevidence. No counts of sources, issues, stars or installs estimate user prevalence, total market, revenue or product efficacy.

A web extraction of the unversioned Tibicen GitHub page returned an obsolete alpha README despite the current release evidence. It is excluded from conclusions about current onboarding or traction; exact local/version-bound records take precedence for that baseline. Search dates do not make every returned page current.

No code/landing/roadmap edits, installs, live model evaluations, paid APIs, telemetry, credentials, outreach, commits or publication are performed by this study. Future behavior changes need their own scoped OpenSpec work. Future experiments below will be proposals until separately selected and specified.
