# Is Tibicen doing its job, and what should come next?

**Research date: 6 November 2026. Published skills: 1.4.1.** Three parallel
source lanes and a separate challenge inform this assessment. English is canonical;
the adjacent Russian edition is `README_ru.md`. This is decision research, with
no implementation or release selected.

## The direct answer

**Engineering evidence supports Tibicen's declared setup/repair workflow. Its
reduction in human setup effort remains unmeasured.** It can inspect a project,
prepare exact approved infrastructure changes, preserve accepted content, apply
supported changes and report checks or gaps. Assisted useful tasks and a narrow
native memory cycle were observed. These facts support a working small utility;
they do not establish that it consistently improves an ordinary agent's result.

The [current capability inventory](../../CURRENT_CAPABILITIES.md) defines what
ships. The [release report](../../evals/results/2026-11-06-release-1.4.1/README.md)
binds the delivery checks. The [repair comparison](../../evals/results/2026-11-06-repair-comparison/README.md)
is important counterevidence: direct Codex and Tibicen made the same repair,
completed the same task and both preserved sufficient setup. It did not test task
success without the repair, normal installation or total active human work.

Version 1.4.1 remains appropriate: the subsequent source work repaired development
evaluators and updated documentation, without changing the published skill bytes.
The latest [documentation commit](https://github.com/warbr1ng3r/tibicen/commit/7be84864783a386f56245bf8f396c802edf8dd63)
passed CI. A version number should describe an actual product change.

| Work through varied hosts | The common file/Node route does not require a catalog entry or particular model provider. | Native discovery, writes and execution probes keep narrower version/adapter limits. |
| Save user time | Unknown. | Neither test counts nor public-source anecdotes measure Tibicen's human benefit. |

The [first working-session report](../../evals/results/2026-11-06-first-working-session/README.md)

## What fresh public reports changed

The [first-use lane](first-use.md), [memory lane](memory.md) and
[integration lane](integrations.md) compare original complaints with current
Tibicen behavior and native remedies. They retain source dates, versions, closure,
source reuse and contrary cases. Agent agreement is not independent user demand.

- **Host identity and mode matter.** The official Copilot matrix distinguishes
  Visual Studio, VS Code and CLI; one brand name does not establish the same
  instruction loading. Tibicen already accepts task/host context and unknowns.
  [Owning support matrix](https://docs.github.com/en/copilot/reference/custom-instructions-support).
- **Memory goals conflict.** Original reports request both shared worktree memory
  and branch isolation. A new storage service would not choose correctly for the
  user. [Shared-memory request](https://github.com/anthropics/claude-code/issues/34975),
  [isolation request](https://github.com/anthropics/claude-code/issues/39920).
- **Correct files can coexist with a host defect.** The closed OpenCode desktop
  report concerned a service environment regression; another file parser would
  not fix that runtime. Fixed historical reports are counterevidence to expanding
  Tibicen from every complaint. [Original report](https://github.com/anomalyco/opencode/issues/50882).

These are reported experiences and declared native contracts, not new Tibicen
trials, prevalence estimates or customer validation.

## What could be added

**No immediate code addition is selected.** The strongest remaining hypotheses
are small and conditional; the current/native answer may already suffice.

| Candidate | Ordinary request and visible result | Actual gap and rejection condition |
| --- | --- | --- |
| Explicit instruction source and compact task context | “I moved to another agent. What should it read?” Carry a deliberately supplied instruction path/hash into the report, then show its relevant rules, selected memory and next action. | An uncatalogued filename can already be scanned/read without becoming a structured instruction candidate. Existing handoff and native inspectors may suffice. Reject if added metadata changes no useful action or requires guessed native precedence/loading. |
| Source-change visibility for remembered facts | “Our setup changed. Which saved facts need checking?” Flag a deliberately bound source change for review. | No general mechanical fact/source comparison ships. Consider only explicit local bindings; reject if ordinary adopt/Git gives the same action, harmless edits become false alarms, or metadata upkeep outweighs checking. Never expire owner decisions by age. |
| Version-impact explanation | “After this update, what actually needs changing here?” Connect a verified upstream change to an affected local decision or justified no-change. | Existing practices and update reasoning may already supply it. Reject another command/schema if one existing answer can explain the case; an old issue alone cannot prove local impact. |

A connected context map is already a future extension in the
[addendum](../../PRODUCT_VISION_ADDENDUM.md), not an absent first-release duty.
The first-use lane's narrower path/hash observation would not add an adapter,
writer or proof that a session read the file. It would keep caller-supplied facts
distinct from observed native loading; current permitted file inspection remains
available without it.
The source-change candidate is a more substantive feature hypothesis, with higher
metadata and false-alarm costs. The version-impact candidate may need only an
editorial example. The lane reports give concrete rejection cases; this synthesis
does not queue another benchmark, prototype, recruitment or model run.

## Recommendation and version policy

Maintain the current utility and its supported contracts. Preserve accurate
native guidance, useful no-change outcomes and the existing approval/update
mechanisms. The next implementation should answer one retained request that
current Tibicen and competent native operation cannot already answer adequately.
The optional candidates above are a shortlist for that decision, not three
parallel implementation packages.

No inspected evidence selects a memory backend, host orchestrator, HTTP/OAuth
manager, automatic updater or extra provider adapter. Model/provider choice
belongs to the host. More installation targets, files or report fields are not
an established benefit. Additional application profiles remain an optional
post-release direction without a newly established comparative need here.

If a compatible feature is selected and delivered, normal SemVer points to a
minor release; a compatible bug fix uses patch. Documentation and desk research
do not require a new skill version. No 1.5 candidate or publication is selected
by this study. Follow the [release procedure](../../RELEASING.md) for actual scope.

The [independent challenge](review.md) records the final assessment. Research did
not launch native agent evaluations or MCP servers, access credentials or personal
memory, install tools, recruit participants, rerun runtime tests, alter old evidence, commit,
push or release anything. Human benefit remains unknown.
