## Native child-process observation

The nested Node launch recorded status `0` **and** an `EPERM` spawn error, with empty stdout/stderr. That is evidence of a failed or blocked launch, not a successfully executed child losing stdout. Direct execution of the same proposal returned a valid canonical 7,964-byte envelope.

No caller retry, application, network command or paid API was used. This was a diagnostic command, not another completed project workflow.

The immediate operational lesson is to run the CLI directly when possible and check `result.error` before parsing a child result. The observation establishes neither the underlying kernel/policy cause nor the cause of the older overwritten capture. No product runtime fix is justified by this evidence alone.
