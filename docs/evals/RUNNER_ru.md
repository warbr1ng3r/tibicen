# Offline evaluation runner

Задачи 1.2 и 2.1 change [build-agent-evaluation-harness](../../openspec/changes/build-agent-evaluation-harness/tasks.md). Реализация — [fixtures.ts](../../scripts/evals/fixtures.ts) и [runner.ts](../../scripts/evals/runner.ts); форматы остаются из [CONTRACTS](CONTRACTS.md). Этот этап проверяет работу стенда на подставных локальных процессах, без моделей и реальной авторизации.

## Diagnostic fixtures

`loadDiagnostic(id)` загружает строгий сценарий и отдельный закрытый oracle, сверяет id и digest. В `scripts/evals/fixtures/` находятся два неизменяемых исходных набора:

| id | Вход | Что должна проверить будущая приёмка |
|---|---|---|
| diagnostic-bare | Небольшое ESM-приложение, тест double, CI и заметка команды; агентской инфраструктуры нет | Достаточная настройка по фактическим задачам/командам с сохранением приложения |
| diagnostic-conflicts | То же приложение, дубли в AGENTS.md и старое правило с неверной командой yarn check | Устранение противоречия с сохранением полезных правил и отдельного ревью владельца |

В обоих случаях task просит добавить triple и тест в новой сессии. Во время setup исходники приложения, package.json, тесты, CI и заметка защищены. Task разрешает только src/math.js и tests/math.test.js. Команда проверок задаётся digest объекта `{executable: "node", argv: ["--test"], cwd: "."}`; фактическая версия Node фиксируется профилем до живой серии. Скрытый oracle дополнительно содержит независимые случаи double/triple, критерии сохранности и качества; решения или обязательного названия инструмента в запросе нет.

`materializeScenario(scenario, parent)` каждый раз создаёт отдельную папку и пишет только `scenario.files`. Возвращает проекцию без oracle и будущих реплик; ошибочное дерево удаляется. Оба варианта получают одинаковые исходные байты, а Tibicen добавляется выбранным будущим профилем только в свой вариант. Перед каждой попыткой вызывающий код обязан материализовать отдельную копию: runner не переиспользует и не очищает переданный cwd. Тесты проверяют состав дерева, независимость копий, различие setup/task и непередачу закрытых данных. Физическая недоступность соседних каталогов требует отдельного preflight; временная папка её не обеспечивает.

## Process execution

`runProcessAttempt({experiment, scenario, attemptId, profile, signal?, reviewReply?})` связывает попытку с замороженными id/hash сценария и полным описанием профиля. Возвращает связанные `result/events` через validateRun, без изменения EvalAttempt schema 1. Oracle не передаётся дочернему процессу и на этом этапе не исполняется.

`ProcessProfile` использует существующие EvalProfileSpec и preflight; `command(stage)` задаёт абсолютные executable/cwd, literal argv и явный env. Окружение родителя не наследуется автоматически, shell не используется. В этом runner профили с auth отличной от none, платные профили и hostile-сценарии блокируются; проверены только trusted auth:none/paid:false драйверы. Настоящий [Codex-профиль](CODEX_DIAGNOSTIC.md) и [внешний командный вход](EXTERNAL_RUNS.md) реализованы отдельно. Метаданные профиля сами по себе не ограничивают возможности переданного executable.

После успешного preflight запускается процесс setup. Получение сообщения ready подтверждает старт подставного сценария; один spawn, exit 0 или наличие файлов не дают launch pass. После setup pass запускается новый процесс task в его согласованном рабочем дереве, без текста setup и его будущих ответов. Лимит launch включает preflight и запуск setup; setup получает отдельный лимит после ready. Весь запуск task, включая ожидание ready, расходует taskMs. Время стадий измеряется host до выхода/остановки процесса; ожидание принудительной очистки группы не добавляется к durationMs.

Таймаут, отмена, неверный протокол, превышенный вывод и ненулевой exit дают error текущей стадии. Предыдущий setup pass сохраняется, а при setup не pass задача пропускается. Непрошедший preflight даёт незапущенную попытку с причиной; его исключение и таймаут — launch error. Код причины ограничен, сырые native ошибки и stdout/stderr в возвращаемые наблюдения не включаются. Расход сам не придумывается: usage допускает null, реальное ограничение стоимости внешних профилей ещё не реализовано.

Остановка посылает SIGTERM группе, затем SIGKILL после 100 мс; выход лидера не отменяет эскалацию. Это применяется также при успешном выходе, чтобы не оставлять фоновых потомков и не зависать на унаследованных pipes. Проверки используют потомков и внуков, игнорирующих SIGTERM. Механизм опирается на [POSIX-группу процесса Node](https://nodejs.org/docs/latest-v22.x/api/child_process.html#optionsdetached); Windows получает process-tree-unavailable до запуска. Повторно отделившийся процесс может уйти из группы: такой запуск требует другого проверенного контроля среды и здесь не поддерживается.

## Driver protocol and human replies

Trusted-драйвер получает одну JSON-строку stdin: schema, идентификатор попытки, текущую стадию, id сценария, доступный диалог, текущий prompt и allowedPaths/allowedCommands. Другую стадию, oracle и staged-реплики он не получает. Вывод — JSONL:

- `{kind: "ready"}` — один раз до действий;
- `{kind: "observation", observation: "artifact" | "command" | "instructions-loaded" | "usage", data: ...}` — только поля соответствующего EvalEvent;
- `{kind: "reply", when: "clarification" | "proposal" | "review", proposalDigest?: ...}` — запрос следующего человеческого ответа;
- `{kind: "finished", status: "pass" | "fail" | "error" | "skip", reason?: ...}` — результат подставной стадии, затем нормальный выход;
- `{kind: "error", reason: ...}` — ограниченный код отказа, допустим и до ready.

В этой фазе ready и finished — контролируемые сигналы подставного процесса. Настоящему профилю потребуется независимое наблюдение старта и собственный парсер; самоотчёт агента не становится доказательством. Статусы подставных процессов подтверждают переходы стенда; [механическая обёртка](OBSERVATIONS_AND_GRADERS.md) отдельно проверяет дерево/согласие, ресурсы и результат task и понижает ложный pass. Качество рекомендации и живая загрузка требуют следующих этапов.

Неизвестные поля, повторный ready, действия до ready/после finished, неполная строка, более 64 KiB на строку или 1 MiB stdout отвергаются. Пока запрошен ответ, драйвер ожидает ответную строку. Без reviewReply возвращается null: текст фикстуры не является автоматическим согласием. Host получает только запрошенную staged-реплику и сам проверяет показанное предложение; runner допускает approvedDigest только для proposal/review и только при совпадении с запрошенным digest. Clarification не может одобрить исполнение. Соответствие digest реальному предложению/путям требует проверки host и оценщика; тестовый callback этой проверки не доказывает. Зависший callback ограничен таймером стадии, поздний ответ не отправляется завершённому процессу.

## Checks and remaining work

Локальный прогон: `node --test tests/evals/*.test.ts`. Подставной драйвер находится в tests/evals/helpers/process-driver.mjs и сам не является интеграцией с агентом. Результаты тестов не добавляются в матрицу живых испытаний.

Безопасное хранение, синтетическая граница авторизации и механические оценщики реализованы для offline/auth:none: [описание и ограничения](OBSERVATIONS_AND_GRADERS.md). [Рубрика с recorded-калибровкой и парный отчёт](QUALITY_AND_REPORTS.md) реализованы отдельно; семантические результаты настоящего судьи не заявляются. [Явный внешний вход](EXTERNAL_RUNS.md) реализован в 2.6; [Codex preflight и диагностика](CODEX_DIAGNOSTIC.md) — в 3.1–3.2. Остальные native-профили остаются открытыми. Все файлы scripts/evals, тесты, fixtures/oracle и документация разработки исключены из распространяемых скиллов. Этот офлайн-runner сам не вызывает модели и не устанавливает ничего в личную среду.
