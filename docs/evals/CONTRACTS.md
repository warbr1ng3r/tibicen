# Evaluation contracts · schema 1

Реализация — scripts/evals/contracts.ts; офлайн-проверки — tests/evals/contracts.test.ts. Это контракты стенда; отдельные первые фикстуры и runner подставных процессов описаны в [RUNNER](RUNNER.md). Настоящие профили и результаты живых испытаний ещё не готовы. Все объекты отвергают неизвестные поля и версии; старый EvalAttempt schema 1 из results.ts остаётся неизменным.

| Контракт | Зафиксированные данные |
|---|---|
| Experiment | id, полный source SHA, conditionsHash, id/hash сценариев, профили, повторы, порядок всех пар Tibicen/baseline и лимиты launch/setup/task/cost |
| EvalProfileSpec | id, агент/версия/модель, маршрут auth без credentials, платность, startupHash и permissionsHash |
| EvalScenario | id, изоляция, входные текстовые файлы/доступный диалог, setup/task с запросом и точными путями/хэшами команд, staged-реплики человека и ссылка id/hash на закрытый oracle |
| EvalEvent | experimentId/attemptId, seq/elapsedMs, стадия, вид и строго разрешённые структурные данные |
| Grade | независимый id/attemptId, стадия, область оценки, pass/fail/unverified, код основания и ссылки на события |

conditionsHash фиксирует канонический документ с настройками среды/сети/источников, версией рубрики/применимыми критериями и прочими сравниваемыми условиями; само содержимое и его соответствие наблюдаемой среде обязан проверить будущий runner. Hash сценария считается digest всего EvalScenario. Изменённые условия, материалы или источник требуют нового эксперимента/когорты. Каждый scenario/profile/repeat заранее имеет оба варианта с уникальными id; перезапуски не подменяют прежние попытки.

executorScenario создаёт отдельную копию входа без oracle и будущих человеческих реплик. Профиль получает только эту проекцию; реплики/согласие поступают через отдельный callback runner после наблюдаемого запроса и проверки точного предложения. Наличие реплики в фикстуре не создаёт согласия. Закрытый oracle получает только оценщик; runner сверяет его hash до оценки.

Интерфейс EvalProfile определяет preflight и run с наблюдениями, AbortSignal и запросом ответа. Preflight ready требует подтверждённых startupControlled/authProtected/processTreeControlled. Hostile-сценарий требует фактически подтверждённой hostile-изоляции; тип поля не создаёт sandbox. Платный профиль требует явного положительного лимита стоимости; неизвестный/неприменимый лимит для остальных записывается null. Настоящие профили, исполнение лимитов и защита credentials остаются отдельными задачами.

EvalGrader получает сценарий, события, schema 1 результат и закрытый oracle. Grade проверяется отдельно; non-unverified вердикт обязан ссылаться на события своей стадии. Эти проверки подтверждают корректность ссылок, не качество судьи.

События:

- scenario-started — наблюдаемый старт сценария на стадии launch, не факт spawn;
- artifact — относительный путь и beforeHash/afterHash, null для отсутствующего файла;
- command — id, точный commandHash и exitCode/null, без raw argv/env/stdout;
- instructions-loaded — путь, contentHash и toolUseId наблюдаемого чтения;
- stage-finished — ровно статус/длительность/код причины соответствующей стадии результата;
- usage — накопленные costUsd/inputTokens/outputTokens внутри стадии, null для неизвестного расхода; последнее наблюдение заменяет предыдущее, snapshots не суммируются.
- checkpoint / approval / assertion / host-command — независимые снимки дерева, точное согласие, хэши проверенных полей и исполненная host-проверка; только host, не сообщения драйвера;
- driver-finished — заявленный исход драйвера перед независимой оценкой; stage-finished содержит итог стадии.

validateRun связывает результат с замороженной попыткой и hash сценария. События имеют последовательные seq и монотонное время, идут launch → setup → task; исполненная стадия требует финального наблюдения. Setup/task ждут наблюдаемого старта, task — setup pass. Ошибка task сохраняет setup pass; отказ до старта сохраняет незапущенную попытку. Итоги передаются validateAttempt/summarizeAttempts без метаданных эксперимента.

Запрещённые дополнительные поля не проходят сериализацию через эти валидаторы. Строгая форма сама не очищает секреты: [хранение наблюдений](OBSERVATIONS_AND_GRADERS.md) отдельно выбирает поля, проверяет известные чувствительные значения и не сохраняет сырой вывод/контекст. Синтетическая offline-проверка не подтверждает реальную авторизацию будущих native-профилей. Стенд, сценарии, oracle и эта документация исключены из распространяемых скиллов.

[Рубрика и парные отчёты](QUALITY_AND_REPORTS.md) описывают независимый обезличенный запрос, человеческую сверку, recorded-калибровку и отдельные observed/evaluated сводки поверх той же schema 1 результата. Режим калибровки не смешивается с живыми свидетельствами.
