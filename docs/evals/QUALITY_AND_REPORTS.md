# Quality and paired reports

This is an offline harness contract. Recorded grades check data flow and disputed cases; they are neither independent-model trials nor human expert review. Native loading of a selected component and process compliance by a real agent are checked through the [SKILL/PROC program](COMPONENT_INTEGRATION.md). The explicit entry was implemented in task 2.6; see the [command contract](EXTERNAL_RUNS.md). The [first Codex diagnostics](CODEX_DIAGNOSTIC.md), 3.1–3.2, contain observations of separate setup/task sessions, but no independent quality grades yet. Other profiles and series remain in change group 3.

## Rubric

Version `tibicen-quality-1` and the exact request text are defined in [quality.ts](../../scripts/evals/quality.ts). Applicable criteria are frozen with conditions before an experiment; the basic four are mandatory for setup, and application is mandatory for task. Loading and process are added to task when a scenario requires a new-session observation. For each criterion, the judge returns `pass/fail/unverified`, a reason code and evidence ids.

| Criterion | Pass | Fail / unverified |
|---|---|---|
| grounding | The conclusion uses available instructions/dialogue; assumptions are named and an explicit clarification is incorporated | Invented history or an ignored override is fail; unavailable context is unverified |
| fit | The solution fits the task and constraints, considering benefit, manual effort and maintenance | An unsuitable tool chosen because an adapter is available is fail; insufficient selection data is unverified |
| sufficiency | Sufficient rules are retained; a confirmed gap gets a suitable improvement or an explicit manual step/gap | Installation for its own sake or forced migration of sufficient Spec Kit is fail |
| consistency | Material conflicts are resolved while preserving owner decisions; commands and links agree | Incompatible mandatory commands retained together are fail; an unreadable result is unverified |
| loading | Independent observation shows reading specific content/version in a new session | Metadata, file presence and self-report are unverified; observed reading of the wrong version is fail |
| application | An observed action follows a specific rule | General task success without a link to the rule is unverified; an observed rule violation is fail |
| process | Approved specification → plan → implementation → verification are observed | Init/CLI alone is unverified; a confirmed sequence/consent violation is fail |

An independent judge makes semantic assessments. Code only validates structure and adequacy of evidence kind: positive loading requires host evidence with `instructions-loaded`, application requires an observed host action, and process requires all four stages in order. Selection needs context and an observed recommendation outcome. These checks do not prove host evidence is true or replace the judge reading the content. Mechanical invariants take precedence in the final report.

## Independent request and human cross-check

`prepareJudgePacket` builds a separate `request`: rubric, applicable criteria and excerpts from one result selected by the lead observer. The hidden oracle, expected grades, profile/variant, alternative response and complete execution history are excluded. Attempt id and binding hashes remain in the host envelope, which should not be sent to the judge. Excerpts are data; instructions inside them are not executed. The operator selects sufficient excerpts, removes variant names/self-description, checks secrets and does not cherry-pick quotations for the desired grade. Known sensitive values are blocked before sending.

The host envelope bindingHash binds the complete validateRun: experiment, scenario, outcomes, events and mechanical grades. Judge response and human cross-check have separate bindingHash/packetHash; the operator links the response to the exact run and sent request. These fields are not added to the anonymized model request. Changed observations or excerpts require a new packet/grade; matching ids and event numbers are insufficient. A grade from another packet is rejected before acceptance.

The native runner uses [native-evidence.ts](../../scripts/evals/native-evidence.ts) to select evidence. The module receives only explicitly selected commands, messages and known files from the materialized project; it does not receive the full private trace or oracle. The packet includes the actual command with exit/output, linked source/rule reads, intermediate messages, summary/question from the structured response and user replies actually supplied. `kernelPlan` and other full-JSON-response fields are not copied to the judge. Available initial context is marked `scenario`, not presented as observed reading.

New excerpts contain `criteria` — references to applicable frozen-plan criteria — and `provenance`: source kind, original-content hash, a sanitization flag, and, for the relevant observation, a relative path, tool-use id and saved-session hash. A judge or human reference to an excerpt for another criterion is rejected. For loading, path, hash and tool-use id must match an `instructions-loaded` event in the same stage. These fields link observations; they are not independent proof that the content is correct. Old packets without metadata retain their previous validation and grades.

A read is recognized only after a successful observed command, matching path and exact known content in output; an OpenSpec template may use its exact JSON template from the standard read-only instructions command. Reading `available-sources` or an ordinary document remains context and does not prove loading of an installed skill. Partial output and a compound shell command that the current parser cannot bind unambiguously to a file remain command evidence without invented loading. A missing selected observation therefore means `unverified`, not established absence of an action.

Personal paths, process path, attempt id and local scopes are replaced before selection; known sensitive values and secret-like data are blocked before truncation, including in provenance. Limits are unchanged: at most 4000 characters per excerpt and 200 items per packet. Truncated text includes `truncation` with its post-sanitization length, saved-prefix length and an explicit omission marker. Each stage gets up to 99 excerpts; on overflow, the earliest item in the largest kind/origin/criteria/step group is replaced, retaining representation of other groups. A separate record with the omitted-item count reports incomplete selection. This is a deterministic volume limit, not selection of convenient grades. The judge must not infer missing actions from truncated text.

Current independent math-export and OpenSpec checks are separate named [checkMathExports/checkOpenSpecArtifacts](../../scripts/evals/native-checks.ts) functions. They work on a separate copy through a supplied bounded executor; exact consent, auth/env and permissions remain with the runner. The checks do not expand the rubric or turn earlier series into acceptance of a new harness. Offline selected-evidence regressions: `node --test tests/evals/native-evidence.test.ts tests/evals/quality.test.ts tests/evals/native-workflow.test.ts`.

Before live trials, a human separately reads input and result using the same rubric, without seeing the model grade, and saves a complete vector with a separate id/version. Mandatory cross-checks cover the first repeat of each pair, every nonpositive grade, stage errors and mechanical-check errors; an additional deterministic sample takes approximately 20% of the rest based on the binding+packet hash. An empty additional sample in a small series is allowed after mandatory cases. The sample is reproducible without rerolling.

A missing mandatory cross-check gives `unverified`. Disagreement retains both grades and evidence, and the final criterion becomes `unverified`; there is no averaging or automatic selection of a convenient response. Both graders must independently reference a sufficient evidence kind. Resolving disagreement requires a new explicitly versioned assessment while retaining the original; the current implementation does not invent it automatically. Fields `model/human` are the operator's attestation, not proof of an independent session; confirming that belongs to a future preflight.

## Calibration before model calls

1. Check a sufficient result, conflict, invented history, unnecessary installation, forced Spec Kit migration and selection because an adapter exists.
2. Separately check a positive synthetic SKILL observation, self-report without loading, task success without application, init without stages and a complete PROC cycle.
3. Compare a prerecorded `recorded` vector with the control `reference`; retain disagreements and missing evidence. These labels define the control set, not measured model accuracy.
4. Before a real series, repeat the set with an independent judge and human; resolve disputed cases, and if the rubric changes, change its version and repeat calibration.

The [control set and grades](calibration-quality.json) are reproduced from [offline examples](../../tests/evals/helpers/recorded-quality.ts) and checked by [tests](../../tests/evals/quality.test.ts). One intentional disagreement is preserved. Synthetic loading/process events check the contract, but do not confirm Ponytail/OpenSpec operation.

## Paired report

`buildPairedReport` in [report.ts](../../scripts/evals/report.ts) accepts frozen experiments, per-scenario criterion plans, evidence mode and linked attempts. The report module neither calls models nor writes files; explicit invocation and publication are implemented separately in the [external-trial command](EXTERNAL_RUNS.md). Offline check: `node --test tests/evals/quality.test.ts tests/evals/report.test.ts`.

A cohort is intentionally limited to one frozen experiment, scenario, specific profile, rubric/plan and `calibration/observed` mode. The full experiment hash includes SHA, conditions, versions, model, startup/permissions, limits, order and repeats. Even apparently identical distinct experiments are not combined automatically. Every planned repeat contains both ids; a missing record remains `record: null`, rather than becoming a rejection before start. Duplicates and foreign/relabeled records are rejected.

Each row retains original `observed` stages and a separate `evaluated` projection. An original pass is accepted only with positive invariants, an independent task result for task, and a complete positive quality vector with mandatory cross-checking. Failure of any independent check takes precedence; absent/incomplete evidence gives error. An original fail/error/skip is not upgraded by assessing text. If evaluated setup is not accepted, evaluated task gets skip; the task that actually ran and its time remain in observed. Failed invariants remain a separate list even after a successful repeat. This is not yet the release gate of task 4.1.

Both summaries use unchanged `summarizeAttempts` and show three fractions with numerator/denominator: setup among started attempts; task among accepted setups; end-to-end success among started attempts. The observed summary describes recorded outcomes; evaluated describes acceptance based on available independent grades. Planned/recorded/missing coverage is separate. Missing records have no known start; an error after observed start remains in the denominator. Experimental rates do not replace product metrics in §14 or prove Tibicen's benefit.

Executed-stage time comes from the result; measured zero stays 0, and skip is shown as `null`/notExecutedCount. Missing-record time is unknown. A usage event contains the **cumulative total within its stage**: the latest event replaces the previous one, including a transition to null; consecutive snapshots are not summed. Attempt cost is known only when every executed stage has an explicit cost. Unknown values do not become zero; explicit zero is valid. The summary has knownSubtotal/knownCount/unknownCount/notExecutedCount, while full total remains null if coverage is incomplete or no measurements exist. Tokens are retained per stage without conversion to money. Differences `tibicen - baseline` are computed only for two known measurements of one pair; negative time means less measured time, without claiming statistical superiority.

The [saved paired example](calibration-paired.json) contains six planned slots, five records, an invariant violation, rejection before start, error after start, successful repeat, explicit zero/unknown cost and an incomplete pair. All data is synthetic. [Report tests](../../tests/evals/report.test.ts) also cover multiple scenarios/profiles, changed conditions and absence of hidden context in the projection. Output is checked for known sensitive values; a packet with text excerpts is not copied into the report.
