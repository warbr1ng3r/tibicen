# Качество и парные отчёты

Это офлайн-контракт стенда. Записанные оценки проверяют передачу данных и спорные случаи; они не являются испытаниями независимой модели или человеческой экспертизой. Нативная загрузка выбранного компонента и соблюдение процесса настоящим агентом проверяются по [программе SKILL/PROC](COMPONENT_INTEGRATION.md). Явный вход реализован в задаче 2.6; [контракт команды](EXTERNAL_RUNS.md). [Первые Codex diagnostics](CODEX_DIAGNOSTIC.md) 3.1–3.2 содержат наблюдения отдельных setup/task-сессий, но пока не независимые quality-оценки. Остальные профили и серии остаются в группе 3 change.

## Рубрика

Версия `tibicen-quality-1` и точный текст запроса определены в [quality.ts](../../scripts/evals/quality.ts). Набор применимых критериев фиксируется до эксперимента вместе с условиями; базовые четыре обязательны для setup, применение — для task. Loading и process добавляются в task там, где сценарий требует наблюдения новой сессии. Для каждого критерия судья возвращает `pass/fail/unverified`, код причины и id оснований.

| Критерий | Pass | Fail / unverified |
|---|---|---|
| grounding | Вывод опирается на доступные инструкции/диалог; допущения названы, явное уточнение учтено | Придумана история или проигнорирован override — fail; недоступный контекст — unverified |
| fit | Решение соответствует задаче и ограничениям, учитывает пользу, ручной труд и сопровождение | Неподходящий инструмент выбран ради готового адаптера — fail; недостаточно данных для выбора — unverified |
| sufficiency | Достаточные правила сохранены; подтверждённый пробел получает подходящее улучшение либо честный ручной шаг/gap | Установка ради установки, навязанная миграция достаточного Spec Kit — fail |
| consistency | Существенные конфликты устранены с сохранением решений владельца; команды и ссылки согласованы | Одновременно оставлены несовместимые обязательные команды — fail; результат нельзя прочесть — unverified |
| loading | Есть независимое наблюдение чтения конкретного содержимого/редакции в новой сессии | Метаданные, наличие файла и самоотчёт — unverified; наблюдаемое чтение неверной редакции — fail |
| application | Наблюдаемое действие выполняет конкретное правило | Общий успех задачи без связи с правилом — unverified; наблюдаемое нарушение правила — fail |
| process | Наблюдаемы согласованные specification → plan → implementation → verification | Только init/CLI — unverified; подтверждённое нарушение порядка/согласования — fail |

Семантические оценки делает независимый судья. Код лишь валидирует структуру и достаточность вида свидетельств: положительный loading требует host-свидетельства с `instructions-loaded`, application — наблюдаемого host-действия, process — всех четырёх стадий по порядку. Для подбора нужны контекст и наблюдаемый результат рекомендации. Эти проверки не доказывают истинность host-свидетельств и не заменяют чтение содержания судьёй. Механические инварианты имеют приоритет в итоговом отчёте.

## Независимый запрос и человеческая сверка

`prepareJudgePacket` формирует отдельный `request`: рубрика, применимые критерии и выбранные ведущим наблюдателем отрывки одного результата. Скрытый oracle, ожидаемые оценки, профиль/вариант, альтернативный ответ и полная история запуска туда не копируются. Идентификатор попытки и хеши связи остаются в host-обёртке, которую не следует отправлять судье. Отрывки считаются данными; инструкции внутри них не исполняются. Ведущий отбирает достаточные отрывки, убирает названия варианта/самоописание, проверяет секреты и не подбирает цитаты под желаемую оценку. Known sensitive values блокируются до отправки.

Host-обёртка bindingHash фиксирует весь validateRun: эксперимент, сценарий, исходы, события и механические оценки. Ответ судьи и человеческая сверка имеют отдельные bindingHash/packetHash; ведущий связывает ответ с точным запуском и отправленным request. Эти поля не добавляются в обезличенный запрос модели. Изменение наблюдений либо отрывков требует нового пакета/оценки; совпадения id и номеров событий недостаточно. Оценка другого пакета отвергается до приёмки.

Нативный runner использует [native-evidence.ts](../../scripts/evals/native-evidence.ts) для выбора оснований. Модуль принимает только явно выделенные команды, сообщения и известные файлы материализованного проекта; полный private trace и oracle ему не передаются. В пакет входят фактическая команда с exit/output, связанные чтения источников и правил, промежуточные сообщения, summary/question структурированного ответа и реально выданные реплики пользователя. `kernelPlan` и прочие поля полного JSON-ответа судье не копируются. Доступный исходный контекст отмечается как `scenario`; он не выдаётся за наблюдаемое чтение.

Новые отрывки содержат `criteria` — ссылки на применимые критерии замороженного плана — и `provenance`: тип источника, hash исходного содержимого, признак очистки, а для соответствующего наблюдения также относительный путь, tool-use id и hash сохранённой сессии. Ссылка оценщика или человека на отрывок другого критерия отклоняется. Для loading путь, hash и tool-use id должны совпадать с событием `instructions-loaded` той же стадии. Эти поля связывают наблюдения; они не являются самостоятельным доказательством правильности содержания. Старые пакеты без metadata сохраняют прежнюю проверку и прежние оценки.

Чтение признаётся только при успешной наблюдаемой команде, совпавшем пути и наличии точного известного содержимого в выводе; для шаблона OpenSpec допускается его точный JSON template из штатной read-only команды instructions. Чтение `available-sources` или обычного документа остаётся контекстом, без доказательства loading установленного скилла. Частичный вывод и составная shell-команда, которую текущий разбор не связывает однозначно с файлом, сохраняются как команда без выдуманного loading. Поэтому нехватка выбранного основания означает `unverified`, а не установленное отсутствие действия.

Личные пути, путь процесса, id попытки и локальные scope заменяются до отбора; известные чувствительные значения и похожие на секреты данные блокируются до усечения, в том числе в provenance. Лимиты не увеличены: не более 4000 символов на отрывок и 200 элементов на пакет. Усечённый текст содержит `truncation` с длиной после очистки и длиной сохранённого префикса и явную отметку пропуска. На каждую стадию отводится до 99 отрывков; при переполнении замещается самый ранний элемент самой многочисленной группы kind/origin/criteria/step, сохраняя представление других групп. Отдельная запись с числом пропущенных элементов сообщает неполноту отбора. Это детерминированное ограничение объёма, а не выбор удобных оценок. Судья не должен дополнять усечённые действия догадкой.

Текущие независимые проверки math-экспортов и OpenSpec выделены в именованные [checkMathExports/checkOpenSpecArtifacts](../../scripts/evals/native-checks.ts). Они работают на отдельной копии через переданный ограниченный исполнитель; точное согласие, auth/env и разрешения остаются у runner. Проверки не расширяют рубрику и не превращают прежние серии в приёмку нового стенда. Офлайн-регрессии выбранных оснований: `node --test tests/evals/native-evidence.test.ts tests/evals/quality.test.ts tests/evals/native-workflow.test.ts`.

Перед живыми испытаниями человек отдельно читает входы и результат по этой же рубрике, не видя оценки модели, и сохраняет свой полный вектор с отдельным id/версией. Обязательная сверка: первый повтор каждой пары, все неположительные оценки, ошибки стадий и механических проверок; дополнительно детерминированная выборка примерно 20% остальных по хешу binding+packet. Пустая выборка на малой серии допустима после обязательных случаев. Выборка воспроизводится без повторного броска.

Отсутствующая обязательная сверка даёт `unverified`. Расхождение сохраняет обе оценки и основания, а итог критерия становится `unverified`; усреднения и автоматического выбора удобного ответа нет. Оба оценщика должны независимо сослаться на достаточный вид свидетельств. Разбор расхождения требует новой явно версионированной оценки с сохранением исходной; текущая реализация её автоматически не сочиняет. Поля `model/human` — аттестация ведущего, а не доказательство независимой сессии; её подтверждение входит в будущий preflight.

## Калибровка до вызовов моделей

1. Проверить достаточный результат, конфликт, придуманную историю, лишнюю установку, навязанную миграцию Spec Kit и выбор ради адаптера.
2. Проверить отдельно положительное синтетическое наблюдение SKILL, самоотчёт без loading, успех задачи без application, init без стадий и полный PROC-цикл.
3. Сопоставить заранее записанный вектор `recorded` с контрольным `reference`, сохранить расхождения и нехватку свидетельств. Такие labels задают контрольный набор, а не измеренную точность модели.
4. До реальной серии повторить набор независимым судьёй и человеком; спорные случаи разобрать, при изменении рубрики сменить её версию и повторить калибровку.

[Контрольный набор и оценки](calibration-quality.json) воспроизводятся из [офлайн-примеров](../../tests/evals/helpers/recorded-quality.ts) и проверяются [тестами](../../tests/evals/quality.test.ts). Один намеренный спор сохранён. Синтетические loading/process-события проверяют контракт, но не подтверждают работу Ponytail/OpenSpec.

## Парный отчёт

`buildPairedReport` в [report.ts](../../scripts/evals/report.ts) принимает замороженные эксперименты, планы критериев по сценариям, режим свидетельств и связанные попытки. Модуль отчёта не вызывает модели и не пишет файлы; явный вход и публикация реализованы отдельно в [команде внешних испытаний](EXTERNAL_RUNS.md). Офлайн-проверка: `node --test tests/evals/quality.test.ts tests/evals/report.test.ts`.

Когорта намеренно ограничена одним frozen experiment, сценарием, конкретным профилем, рубрикой/планом и режимом `calibration/observed`. Полный hash эксперимента включает SHA, условия, версии, модель, startup/permissions, лимиты, порядок и повторы. Даже внешне одинаковые разные эксперименты автоматически не объединяются. Каждый запланированный повтор содержит оба id; отсутствующая запись остаётся `record: null`, а не превращается в отказ до старта. Дубли и чужие/перемаркированные записи отклоняются.

В строке сохраняются исходные `observed` стадии и отдельная проекция `evaluated`. Исходный pass принимается только при наличии положительных инвариантов, независимого task-результата для task и полного положительного вектора качества с обязательной сверкой. Fail любой независимой проверки имеет приоритет; отсутствие/неполнота свидетельств даёт error. Исходный fail/error/skip не повышается оценкой текста. Если evaluated setup не принят, evaluated task получает skip; фактически исполненная task и её время сохраняются в observed. Неудачные инварианты видны отдельным списком даже после успешного повтора. Это ещё не релизный гейт задачи 4.1.

Обе сводки используют неизменённый `summarizeAttempts` и показывают три дроби с числителем/знаменателем: setup среди начатых; task среди принятых setup; сквозной успех среди начатых. Сводка observed описывает записанные исходы, evaluated — приёмку по имеющимся независимым оценкам. Покрытие planned/recorded/missing показывается отдельно. Пропущенные записи не имеют известного старта; ошибка после наблюдаемого старта остаётся в знаменателе. Экспериментальные доли не заменяют продуктовые метрики §14 и не доказывают пользу Tibicen.

Время исполненной стадии берётся из результата; measured zero остаётся 0, skip показывается `null`/notExecutedCount. Для пропущенной записи время неизвестно. Событие usage содержит **накопленный итог внутри своей стадии**: последнее событие заменяет предыдущее, включая переход к null; суммы последовательных snapshot не складываются. Стоимость попытки известна лишь при явной стоимости каждой исполненной стадии. Неизвестные значения не становятся нулём; явный ноль допустим. В сводке есть knownSubtotal/knownCount/unknownCount/notExecutedCount, а полный total остаётся null при неполном покрытии либо отсутствии измерений. Токены сохранены по стадиям без пересчёта в деньги. Разности `tibicen - baseline` вычисляются только для двух известных измерений одной пары; отрицательное время означает меньшее измеренное время, без вывода о статистическом преимуществе.

[Сохранённый парный пример](calibration-paired.json): шесть запланированных слотов, пять записей, инвариантное нарушение, отказ до старта, ошибка после старта, успешный повтор, явная нулевая/неизвестная стоимость и неполная пара. Все данные синтетические. [Тесты отчёта](../../tests/evals/report.test.ts) также проверяют несколько сценариев/профилей, изменённые условия и отсутствие скрытого контекста в проекции. Вывод проходит проверку известных чувствительных значений; packet с текстовыми отрывками в отчёт не копируется.
