## Result and admission rules

- Keep each scenario's real user request, agent questions, proposed structure,
  exact diff, external approval record, commands and final result together.
- Record discovery/loading, explicit reads, rule use, functional output and file
  preservation as separate observations. Correct output alone proves none of
  the loading or memory-use dimensions.
- Declare assistance and unavailable capabilities. Synthetic controller consent
  is not human approval; self-reported reads are not exported tool traces.
- Keep original failures, unknowns and protocol deviations. A new observation
  cannot regrade an old packet or imply human/causal benefit or all-host support.
- Respect the frozen call/deadline/resource stops and cleanup ownership. Failed
  admission does not permit another worker, retry or broader matrix automatically.
- No paid-API authorization or old allowance is renewed by this tracker. Resolve
  the applicable authorization and unsettled accounting before paid work.
- Confirmed product fixes need their own scoped OpenSpec requirements and tests;
  a new commit, version or publication is a separate authorized action.

## Wayfinding operations

- Effort map: `.scratch/<effort>/map.md`; label `wayfinder:map`.
- Child ticket: `.scratch/<effort>/issues/NN-<slug>.md`; its path is its identifier.
  Link text uses the ticket title.
- Ticket fields: `Type: grilling|prototype|research|task`,
  `Labels: wayfinder:<type>`, `Status: open|claimed|resolved`,
  `Assignee: none|<session>`, `Blocked by: none|NN, NN`.
- Before starting, claim the ticket and set the assignee. Its contract defines
  allowed paths, checks and any linked OpenSpec task group.
- Only resolved dependencies unlock a ticket. Within a batch, select open,
  unassigned, unblocked tickets in number order with ready independent inputs.
- On completion, record the answer/evidence, resolve the ticket, clear its
  assignee and add a short linked result to the map's `Decisions so far`.
  A human decision requires the owner's response.
- A map uses only `wayfinder:map`; tickets use only `wayfinder:<type>`.
  `dashboard.md` reflects ticket changes; a chat visual is a snapshot, not a
  second tracker. Detailed implementation checkboxes stay in OpenSpec.
