## Политика версий и changelog

После 1.0 используйте [SemVer 2.0.0](https://semver.org/spec/v2.0.0.html): совместимые исправления увеличивают patch, совместимая функциональность — minor, несовместимые поддерживаемые интерфейсы — major. Описывайте совместимость и шаги миграции, включая подключаемые по выбору форматы записей, которые старый runtime не читает. Примеры после опубликованной 1.0.0:

| Изменение | Следующая версия | Пример заголовка |
|---|---|---|
| Совместимое исправление ошибки | 1.0.1 | `fix(report): retain the incomplete reason` |
| Совместимая новая возможность | 1.1.0 | `feat(memory): configure project memory` |
| Несовместимый поддерживаемый контракт | 2.0.0 | `feat(core)!: replace a supported proposal format` |
| Первый опубликованный prerelease 1.1.0 | 1.1.0-rc.1 | `chore(release): prepare 1.1.0-rc.1` |
| Исправление опубликованного prerelease | 1.1.0-rc.2 | `fix(core): preserve a local block` |

Используйте Conventional Commits (`feat`, `fix`, `docs`, `refactor`, `test`, `build`, `ci`, `chore`); scope необязателен. Отмечайте несовместимость символом `!` либо footer `BREAKING CHANGE:`. Сам тип коммита не публикует и не повышает версию.

Завершённые пользовательские изменения ведите под `Unreleased` в [CHANGELOG.md](../CHANGELOG.md), используя подходящие категории Added, Changed, Deprecated, Removed, Fixed или Security из [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Планы и невыполненные задачи не являются готовыми возможностями. Меняйте версию корневого package.json при подготовке кандидата, затем генерируйте из неё оба скилла. При выпуске переносите завершённые записи под версию и фактическую дату; до этого подготовленный черновик остаётся явно неопубликованным.

Используйте `-rc.N` только для реального prerelease. Внутренний кандидат может связывать намеченную стабильную версию с неизменяемым snapshot, хешем сборки и идентификатором попытки. Каждое исправление после публикации получает новую версию. Опубликованные tags, файлы выпуска и суммы сохраняют исходные байты.

## Процедура кандидата

1. Следуйте текущему change и задачам выпуска из [плана разработки](DEVELOPMENT_PLAN.md). Подтвердите завершённый охват, совместимость, намеченную версию и идентификатор исходников. Обновите package.json для кандидата; изменения внутренних схем обосновываются отдельно. Рабочее дерево можно ревьюить, но перед наблюдениями кандидата нужно заморозить его точный состав и хеш.
2. На закреплённых Node/pnpm выполните `pnpm install --frozen-lockfile`, `pnpm test` и `pnpm build`. При правках сайта отдельно проверьте браузеры. Сохраните логи и идентификатор замороженных исходников; тесты не заменяют приёмку кандидата.
3. Скопируйте собранное дерево и `dist/SHA256SUMS` в новый каталог кандидата. Проверьте версии/ресурсы обоих сгенерированных скиллов, состав архива и каждую сумму. Выполните оба CLI `self-test` вне checkout, без Git в PATH. Сохраните точные байты: повторная генерация создаёт нового кандидата, если неизменность не доказана.
4. Получите независимое инженерное ревью и предусмотренные change наблюдения поведения на кандидате. Сохраняйте неудачи и сведения о помощи. Для памяти проекта отделяйте проверки файлов/ссылок от фактического чтения, использования и обновления в свежих сессиях; см. [память проекта](PROJECT_MEMORY.md). Изменение распространяемых байтов требует обновления затронутых проверок и наблюдений.
5. Проверьте локальную установку точного кандидата, обновление между замороженными поставками, восстановление, удаление и сохранность пользовательских данных. При наличии памяти включите заметки, добавленные после настройки. Локальный путь или архив не доказывает публичную доставку.
6. Свяжите кандидата с применимыми L1/PREF/SKILL/PROC-свидетельствами, версиями источников, [независимой инженерной оценкой](evals/ENGINEERING_ACCEPTANCE.md) и границами сопровождения. По политике от 03.11.2026 человеческая калибровка и начальный пилот пользы имеют отдельное добровольное расписание после публикации; их отсутствие раскрывается. OpenSpec-сценарии применяются к запросам с этим компонентом. Отсутствующие обязательные загрузка, применение и другие технические свидетельства остаются открытым пробелом; ревью не заменяет отсутствующее наблюдение.
7. Подготовьте локальный release draft: версия, замороженные идентификаторы исходников/поставки, намеченный tag `v<version>`, маршрут установки, суммы, changelog, release notes, совместимость/миграция, инструкции обновления/восстановления/удаления и поддержанные/непроверенные исходы. Укажите оставшиеся публичные проверки. Получите явное разрешение владельца на коммит, push и публикацию конкретного пакета. Используйте уже данное явное разрешение плана выпуска в его охвате; одно утверждение плана функции не разрешает релизные действия.
8. После разрешения свяжите публичный source commit и distribution SHA с кандидатом. Пройдите обычный публичный CI и существующие шесть сочетаний macOS/Ubuntu/Windows × Node 22.20/24.15. Проверьте установку реального публичного репозитория поставки по полному SHA закреплённым установщиком, включая применимые обновление/удаление и сохранность. Запишите точные результаты и ограничения.
9. После успешных проверок опубликуйте новый неизменяемый SemVer tag, файлы выпуска и соответствующие release notes. Проверьте возвращённые байты файлов и суммы. Обновляйте metadata/checksum-записи Pages только для описания выпущенных байтов и отдельно проверяйте deployment. Сообщите фактические публичные URL и оставшиеся ограничения.

Исправления записывайте новым кандидатом. Сохраняйте неуспешные попытки и старые суммы. Опубликованные tags и байты неизменны; исправление опубликованного дефекта требует новой версии. Фонового обновления установленного Tibicen или настройки проекта нет.
