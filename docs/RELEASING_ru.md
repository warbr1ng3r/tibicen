# Подготовка выпуска

Эта процедура описывает публикацию скиллов Tibicen. Статический лендинг можно выкладывать отдельно, отражая в тексте фактическую доступность скиллов. Контакты безопасности, результаты пилота и полная приёмка скиллов не являются техническими условиями GitHub Pages.

Выпуски выполняются вручную. Обычный коммит, merge или успешный CI не создаёт tag или release. Версия продукта берётся из package.json; версия продукта и версии сохраняемых схем независимы. Сборщик копирует версию продукта в оба скилла. Меняйте схему только при реальном изменении схемы.

## Политика версий и changelog

До 1.0 совместимые исправления увеличивают patch; новые возможности и несовместимые изменения — minor. Даже для 0.x описывайте несовместимости и шаги обновления. Примеры после опубликованной 0.1.0:

| Изменение | Следующая версия | Пример заголовка |
|---|---|---|
| Совместимое исправление ошибки | 0.1.1 | `fix(report): retain the incomplete reason` |
| Новая возможность | 0.2.0 | `feat(adopt): add a supported adapter` |
| Несовместимое изменение | 0.2.0 | `feat(core)!: change the proposal format` |
| Первый кандидат 0.2.0 | 0.2.0-rc.1 | `chore(release): prepare 0.2.0-rc.1` |
| Исправление кандидата | 0.2.0-rc.2 | `fix(core): preserve a local block` |

Используйте Conventional Commits (`feat`, `fix`, `docs`, `refactor`, `test`, `build`, `ci`, `chore`); scope необязателен. Отмечайте несовместимость символом `!` либо footer `BREAKING CHANGE:`. Сам тип коммита не публикует и не повышает версию. Пользовательские изменения ведите в [CHANGELOG.md](../CHANGELOG.md), отделяя неопубликованную работу от выпущенных версий. Переносите записи под версию и фактическую дату только после публикации.

## Процедура кандидата

1. Изучите задачи и свидетельства в [prepare-first-public-release](../openspec/changes/prepare-first-public-release/tasks.md). Подтвердите source SHA, намеченную версию и согласованный охват. Dirty tree — работа для review, а не неизменяемый источник выпуска.
2. На закреплённых Node/pnpm выполните `pnpm install --frozen-lockfile`, `pnpm test` и `pnpm build`. При правках сайта отдельно проверьте браузеры. Сохраните логи и source SHA; тесты не заменяют приёмку конкретного кандидата.
3. Скопируйте собранное дерево и dist/SHA256SUMS в новый каталог кандидата. Проверьте все суммы, версии/ресурсы обоих установленных скиллов и оба CLI `self-test` вне checkout, без Git в PATH.
4. Проверьте реальный Git-репозиторий поставки по полному SHA закреплённым установщиком. Проверьте переход между замороженными поставками, удаление, пользовательские данные и платформенные ограничения. Предыдущая версия не обязана уже быть публичной. Локальный путь или архив не доказывает публичный Git-маршрут.
5. Свяжите кандидата с текущими L1/PREF/SKILL/PROC-свидетельствами, версиями источников, [независимой инженерной оценкой](evals/ENGINEERING_ACCEPTANCE.md) и границами сопровождения. По политике от 03.11.2026 человеческая калибровка и начальный пилот пользы имеют отдельное добровольное расписание после публикации; их отсутствие раскрывается. OpenSpec-сценарии применяются к запросам с этим компонентом. Отсутствующие обязательные загрузка, применение и другие технические свидетельства остаются открытым пробелом; ревью не заменяет отсутствующее наблюдение.
6. Подготовьте локальный release draft: версия, source SHA, маршрут установки, суммы, примечания, обновление/удаление и ограничения. Получайте явное согласие на публикацию после подготовки конкретного проверяемого черновика.

Исправления записывайте новым кандидатом. Сохраняйте неуспешные попытки и старые суммы. Опубликованные tags и байты неизменны; исправление опубликованного дефекта требует новой версии. Фонового обновления установленного Tibicen или настройки проекта нет.

## Подготовленный кандидат 1.0.0 — 4 ноября 2026

Версия исходного пакета — `1.0.0`. Подготовленный коммит поставки — `e8532bba0582564c93e50de1f55174daaa9bbd34`; inventory SHA-256 его 86 payload-файлов — `0bdcf606c644859120dbae065b04095a8f7bacedb39ec98508f72290cfc0bbb3`. Поставка отделена от коммита исходников; это не доказательство публичной установки или опубликованного version tag.

Точный локальный gate исходников прошёл 736 тестов, ноль ошибок и один намеренный пропуск, затем сборку, с кэшированными locked-зависимостями. Реальный локальный пакет прошёл восемь version/resource-вызовов на Node 22.20.0/24.15.0. Эти записи предшествуют финальным правкам installer/site metadata. Свежий CI с обычной frozen-установкой, финальные заявленные платформы, публичная Git/asset-установка и возвращённые байты Pages ещё ожидают проверки. Сохранить alpha refs и исторические свидетельства; переносить Unreleased-записи changelog только после реального выпуска.

## Что ещё требуется для полного MVP

31 октября 2026 года владелец подтвердил [@warbr1ng3r](https://github.com/warbr1ng3r) ответственным за ядро/адаптеры и получателем частных security-сообщений. Частный маршрут раскрытия уязвимостей включён; см. [SECURITY](../SECURITY.md).

- Проверить ограниченные public project/private GitHub Support-маршруты [CoC](../CODE_OF_CONDUCT.md), сохраняя подтверждённого private vulnerability-получателя. Прежнее обещание общего приватного conduct-inbox заменено; inbox или другой получатель не назначены. Доставка форм/уведомлений заново не проверена.
- Опубликовать и проверить отдельно версионируемый Pages-индекс advisory/сумм из [MAINTENANCE](MAINTENANCE.md). Локальная alpha-запись не доказывает рабочий канал; управление GitHub общее.
- Технический охват и приёмка заявленных компонентов, агентов и платформ с привязкой к кандидату; явно разрешённые неподдержанные исходы сохраняются с причинами.

Эти условия остаются открытыми после ограниченной alpha. Сопровождение выполняется ежемесячно и после существенных изменений инструментов; изменённые рекомендации требуют новых init/adopt-проверок.

[Процедура сопровождения](MAINTENANCE.md) и [последняя проверка источников](evals/results/2026-11-03-maintenance-review/README.md) фиксируют назначенного ответственного, частоту ревью и документацию/CLI metadata. Они не подтверждают доставку уведомлений или реальную публикацию Pages-индекса и не заменяют оставшиеся поведенческие свидетельства. Принятый [контракт maintenance-канала](../openspec/changes/define-maintenance-reporting-and-checksum-channel/specs/maintenance-channels/spec.md) определяет независимость артефакта/публикации/origin; публикация и сверка байтов ожидают задачу 3.2.

## Добровольное исследование после публикации

Начальный пилот пользы на реальной работе и человеческая калибровка рубрики отложены, а не выполнены, согласно принятой [политике свидетельств](../openspec/changes/separate-release-evidence-from-usefulness-pilot/specs/product-scope/spec.md). Анкета владельца и поиск участников не являются дорелизными зависимостями. При появлении добровольцев используйте [протокол пилота](PILOT.md). До наблюдений человеческая польза указывается как неизмеренная; открытые обсуждения и мнения моделей не заполняют записи участников. Для человечески откалиброванных исследований сохраняются протокол калибровки/сверки и прежние оценённые исходы.

Сохраняются контрольная точка 50 измеренных сессий / 8 недель после публикации и определения 30-дневного повторного использования. Нехватка данных требует явного решения искать участников, продлить или закрыть исследование; она не доказывает пользу и не сбрасывает отсчёт.
