# Участие в разработке Tibicen

Tibicen опубликовал первый ограниченный [предварительный alpha-выпуск](https://github.com/warbr1ng3r/tibicen/releases/tag/v0.1.0-alpha.1). Репозиторий — [warbr1ng3r/tibicen](https://github.com/warbr1ng3r/tibicen). Полная MVP-приёмка, ответственный сопровождающий и приватные контакты безопасности/поведения остаются открытыми. Перед подготовкой нового выпуска или приглашением участников пилота прочитайте [сведения о выпуске](docs/RELEASING.md).

## Язык документации

Основная документация проекта пишется на английском. Рядом с каждым руководством храните русский перевод `NAME_ru.md` и обновляйте обе версии вместе. В обеих версиях ссылки и указатели инструкций ведут на основные английские файлы. Правило охватывает руководства проекта; устанавливаемые инструкции скиллов и версионируемые runtime references имеют отдельный релизный охват.

## Подготовка и проверка изменения

Используйте Node 24.15.0 и pnpm 11.21.0, закреплённый в package.json:

```sh
pnpm install --frozen-lockfile
pnpm test:core
pnpm test
pnpm build
```

Во время правок выполняйте проверки затронутой области, затем полный gate перед интеграцией. `pnpm test` включает lint, форматирование, типы, сборку сайта, строгую проверку OpenSpec и офлайн-тесты Node. Браузерные проверки запускаются отдельно через `pnpm test:site`; используйте их при изменении поведения сайта. Тестам не нужны учётные данные моделей. Для живых агентских испытаний требуются собственные согласованные протокол и бюджет; офлайн-успех не является живой приёмкой.

## Небольшие изменения

Сначала прочитайте [границы продукта](docs/PRODUCT_VISION.md) и затронутый код. Для ошибки или рискованного поведения добавьте регрессионную проверку. Сохраняйте файлы приложения, решения пользователя и границы согласия. Честно отмечайте неподдержанные проверки.

Для существенных изменений поведения храните требования, сценарии и задачи в OpenSpec change под `openspec/changes/`. Небольшие текстовые и CSS-правки можно выполнять напрямую. Порядок этапов ведите в [плане](docs/DEVELOPMENT_PLAN.md), подробные задачи — в change. OpenSpec для разработки и сгенерированные им скиллы не включаются в распространяемые скиллы Tibicen.

Предложение правила или адаптера должно указывать проблему пользователя, датированный первичный источник, точную версию, затронутые агенты и пути, ожидаемые эффекты и проверки init/adopt и сохранности. Одно название компонента не доказывает поддержку. Сохраняйте upstream-лицензии и записывайте происхождение скопированных материалов.

## Подача и review

Используйте шаблоны issue и pull request. Опишите пользовательский результат, реально выполненные проверки и ограничения. Приводите минимальные обезличенные примеры; не публикуйте токены, приватные исходники, пользовательские пути и полные агентские стенограммы. Для уязвимостей следуйте [SECURITY.md](SECURITY.md).

Используйте Conventional Commit заголовок, например `fix(core): preserve local rules` или `feat(adopt): explain a manual step`. Во внешних PR допустимы любые промежуточные сообщения коммитов, если итоговый squash-заголовок соответствует соглашению. Агенты создают коммиты только по явному поручению пользователя.

Соблюдайте [кодекс поведения](CODE_OF_CONDUCT.md). Публичные маршруты участия и сообщений о поведении будут добавлены после подтверждения владельца и ответственного сопровождающего. Наличие этих документов не означает, что маршруты уже работают.
