# Prospective acceptance protocol

Recorded before fresh-agent dispatch on 6 November 2026. The owner approved this
implementation packet, including fresh-session checks. Root acts as operator for
generated fixtures only and may approve exact fixture proposals after reviewing
their diffs. This does not record human usefulness or approve real-user edits.

## Candidate and execution

Build two standalone skills into a frozen external output, record SHA256SUMS and
source hashes. Use fresh subagents without parent conversation, explicitly read
the selected complete SKILL.md, and limit work to the assigned generated fixture.
Capture dispatch, reports, proposal, approval, apply/verify/status/report outputs,
protected hashes and project tests. Evaluation artifacts may be written outside
the fixture as explicitly authorized capture; no target preapproval writes.

No network, installs, third-party execution, paid API, credential access or native
CLI launches. These are source-assisted agent observations through this app's
subagent mechanism. Selected target-host identity is fixture input, not the
actually executed native harness. Retain that distinction in every result.

## Cases and criteria

| Case | Starting state and ordinary request | Required observable result |
| --- | --- | --- |
| I1 | Small existing Node application, no infrastructure; set up a custom team-agent with minimal rules and remember accepted date/dependency preferences | Correct init route; current project command; taskScope with unknown host; one sufficient common entry and at most one approved store; exact proposal; protected application intact |
| A1 | Existing root instructions with a stale check command, useful memory, intentional Russian-only subtree instructions; review setup for a documentation task using ZCode as selected target | Actual root-command defect explained and repaired; root/cwd/target explicit; subtree differences preserved; no ancestry-based native loading claim; same store and useful notes preserved |
| M1/M2 | Fresh working agents after applied I1/A1; explicit first reading step from handoff; prepare a date-sensitive export example, then receive a lasting owner correction | Read relevant memory through instructions, use UTC date convention in the result, update accepted changed meaning without another store or losing the unrelated dependency note |

Each setup has one initial attempt. A failed attempt remains failed; an applicable
correction and any rerun receive their own ID and changed-byte explanation.
Exact-plan fixture approval is a separate operator message, never a field in the
proposal. Report setup quality, structural checks, assisted task behavior and
native loading independently. A native observation is unavailable in this bounded
protocol, not a pass. Independent review assesses claims and preservation.
