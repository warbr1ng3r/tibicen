# Proposal

## Why

Проверка покрытия Tibicen 1.8.1 воспроизвела два дефекта контракта (SECURITY-001, SECURITY-008):

- `proposal` отклонял путь с обходом на обратных слешах, например `..\outside\AGENTS.md`, с кодом `application-protected`, а `.tibicen/../x` — с кодом `forbidden-path`, потому что проверки границы записи и внутреннего состояния выполнялись до валидатора пути. Записи не происходило, но код противоречил `unsafe-path`, который `validateRelativePath` и контракт, утверждённый для выпущенного CLI, дают для каждой формы выхода пути за пределы проекта.
- `mcp-verify` и планирование MCP сообщали `existing-inline-secret` для документированных заполнителей `<token>` и `<VALUE>`. Проверка секретов в конфигурации MCP исключала только ссылки `${...}` и не знала правило заполнителей, которое уже применяют проверка секретов и подготовка снимков.
- Повторная проверка покрытия (`SECURITY-008`) обнаружила, что `proposal` принимал сырую правку MCP-конфигурации со значением `"TOKEN": "<token>SYNTH-LITERAL-7f3a9c"` и возвращал его в скомпилированном содержимом и diff. Текстовый сканер `containsSecret` исключал любое значение в кавычках, которое лишь начинается с `<`, `${`, `[redacted]` или `***`, тогда как обычный литерал в той же конструкции отклонялся с `secret-content`.

Root также воспроизвёл пробелы в значениях, пропущенные имена ключей и экранированные JSON-ключи. MCP apply отказывал позднее, но согласованное обычное инфраструктурное содержимое записывалось. Исправление относится к общей проверке содержимого.

## What Changes

- Валидировать путь изменения через `validateRelativePath` до проверок внутреннего состояния, границы записи и актуальности — как при планировании предложения, так и при применении или продолжении плана. Изменение без пути в непустом проекте сохраняет прежний отказ `application-protected`.
- В структурированной конфигурации MCP распознавать только полные значения заполнителей: цельную ссылку окружения, `<идентификатор>`, `[redacted]` или маску из звёздочек. Частичные префиксы и ссылки, смешанные с текстом, остаются литералами при верификации, планировании и проверке доверия. Литерал при ключе, похожем на секрет, отклоняется и не выводится.
- Использовать общие правила ключей секретов, полных заполнителей и структурированных литералов в сыром содержимом и MCP. Проверять декодированные JSON-ключи/значения и текстовые присваивания в кавычках с пробелами/экранированием. Чтение текущего файла, proposal и apply отклоняют литералы до выдачи или записи, включая AUTHORIZATION/CREDENTIALS и AGENTS.md. Узкая проверка значений без кавычек вне JSON сохраняется.
- Валидатор путей, правила синтаксиса ссылок MCP, диагностика нативных форматов и сканер снимков не меняются.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `agent-infrastructure-lifecycle`: небезопасные пути изменения классифицируются до других отказов для того же изменения; проверка конфигурации MCP Claude Code и Cursor распознаёт полные значения заполнителей; сырой текст предложенной правки исключает заполнитель только когда всё значение — один заполнитель.

## Impact

Четыре модуля (`core/plan.ts`, `core/apply.ts`, `core/policy.ts`, `mcp/index.ts`) и три существующих тестовых файла. Новых зависимостей, персистентных схем, прав и версии нет. Общая policy устраняет отдельные копии правил заполнителей/ключей. Отказы сырого содержимого охватывают пробелы и декодированный JSON; валидация формата ссылок остаётся отдельной.
