# Design

## Context

Tibicen 1.5.6 executes approved project checks only for the web profile (`runProjectChecks`: `profile !== 'web'` → `unsupported-profile`). Scan discovers commands only from package.json scripts. `validateCommand` rejects every shell executable outright, so an existing project smoke script has no legal execution route. The comparison machinery (id/commandHash matching, baseline retention, `pre-existing-red`, regressions, interruption) is language-agnostic and already proven for literal-argv runners on independent snapshot copies. Reproduced gaps on f5816c7: python profile → `unsupported-profile`; bash script → `forbidden-command`; scan returns `commands: []` for a Python project.

## Goals / Non-Goals

**Goals:** comparable baseline/final application checks for Python, documentation and Bash projects with existing entrypoints; exact consent (digest-bound commands with pinned interpreter paths); honest unverified reasons for missing interpreters, missing entrypoints and drift; unchanged web behavior.

**Non-Goals:** package installation or venv reproduction, Makefile/task-runner semantics, interpreter version detection (needs pre-consent execution), containers/sandboxes, a general profile framework, Windows execution, network access, task/quiz/compat changes, new scan command inference from language names alone.

## Decisions

1. **Profile vocabulary, not a profile system.** `runProjectChecks` accepts `web | python | bash | docs`; an unsupported runtime profile stays `unsupported-profile`. New proposals reject unknown profile names earlier with `invalid-check-command`. The three new names share one runtime rule set (approved literal-argv commands on execution copies, no dependency environment) and exist so reports name the stack honestly and later stack-specific rules have a place. Profiles gate execution, not discovery: the agent still reads project files and proposes only commands whose entrypoint it actually observed; a language name or popular template proves nothing.
2. **Interpreter pinning at proposal time.** For the new profiles the CLI rewrites bare `node`/`python3`/`python`/`bash` in build/test/lint commands to an absolute executable found by scanning `PATH` directories with `fs` (no child process, read-only, pre-consent safe). Only absolute `PATH` entries whose candidate is a file with an execute bit can produce a pin; relative entries and plain data files are skipped. Missing interpreter → `interpreter-unavailable` refusal. Other executables must be absolute or `./`-relative. Pinning removes baseline/final PATH drift; no version is recorded because detecting one requires executing the interpreter.
3. **Explicit script-binding contract.** A check command may carry `script: { path }`; `createProposal` reads the file (bounded, forbidden-path aware), hashes its bytes into the compiled plan, and the execution snapshot re-verifies the hash before spawning (`command-source-changed` on drift or absence). The compiler normalizes a matching first argument to `./` plus the canonical script path before review. Runtime validation requires that explicit file argument, so filenames such as `--version` or `inspect` cannot become interpreter options/subcommands. For `node`/`python3`/`python` file checks the binding is required; a Python installed-module runner may instead use `-m NAME`. These rules cover bare and absolute interpreter spellings. Bindings are unavailable in the web profile, and a file argument may bind only to a pinned interpreter, not an arbitrary wrapper. Package.json `source` keeps its own existing meaning.
4. **Narrow bash acceptance.** `validateCommand` admits `bash` only when kind ∈ build/test/lint, the executable is an absolute pinned path, `script` is bound with a 64-hex hash and a canonical relative path, and argv is exactly `['./' + script.path]`. Script-bound interpreter commands run from the project root with that explicit path as `argv[0]`. Direct `./` entrypoints are instead bound by their executable path and retain their approved argv, including an empty list; they run via their shebang. Both paths execute the same bytes that were verified. Absolute executables inside the original project, including external aliases resolving into it, are refused at compilation and execution by the same shared check; otherwise `$0`-relative writes could affect the original instead of the copy. The web profile and every non-controlled profile keep the previous flat shell ban, enforced at proposal time and defensively at run time. Extra Bash interpreter arguments, `sh`/`zsh`/`fish`/`cmd`/`powershell`/`pwsh`, `npx`/`env`/`xargs` and inline code stay forbidden. Trust still comes from the user, and a copy is still not a sandbox.
5. **Environment separation.** `local-node-modules` environments are web-only: proposal refuses the combination, and `runProjectChecks` defensively returns `unsupported-profile` if a non-web snapshot carries an environment. The node runtime/link checks and `node-environment-*` reasons stay web-scoped.

## Risks / Trade-offs

- [Bound script bytes do not sandbox bash] → the contract binds reviewed bytes and exact argv, requires trust plus approved digest, runs on a detached process tree with timeout/abort, and the report keeps calling copies non-sandboxes; arbitrary trusted code remains outside the promise.
- [PATH scan may pick an unusual interpreter] → the pinned absolute path is shown in the plan digest before consent; the user can reject it. No version claim is made.
- [Interpreter changes between proposal and apply] → the absolute path is re-spawned as-is; a replaced binary is a machine change outside the plan, same as the existing web runtime identity limits.
- [Three names for one rule set] → accepted for honest per-stack reporting; a shared helper keeps the implementation single-path.

## Migration Plan

Additive: `Command.script` is optional, old plans validate unchanged, web path untouched. New profiles require new proposals and fresh consent (digests change). Tests cover each new profile through the public CLI on real fixtures plus negative contracts; published 1.5.6 artifacts are not modified.
