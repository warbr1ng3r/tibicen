# Spec Delta

## Purpose

Проверять самостоятельную работу настоящих агентов в сопоставимых условиях, сохраняя основания оценок и различие между настройкой, полезной задачей и доказанной пользой продукта. Это целевой контракт стенда разработки; его наличие не подтверждает выполненные испытания.

## ADDED Requirements

### Requirement: Native workflows remain independent of agent profiles
Стенд SHALL разделять общий протокол сценариев, staged consent, бюджет, независимые проверки и отчёт от CLI/авторизации/прав/startup/парсера конкретного агента. Первая очередь SHALL явно включать отдельные профили Codex, Claude Code и ZCode. Формат событий или команды одного агента SHALL не становиться общим интерфейсом всех агентов.

#### Scenario: ZCode is selected while its execution route is unavailable
- **WHEN** host явно выбирает ZCode, а CLI отсутствует или startup/авторизация/изоляция ещё не подтверждены
- **THEN** оба слота пары сохраняют причину blocked без запуска Codex или модели
- **AND** version/help discovery не объявляется проверенным подписочным запуском; неподтверждённый ready отклоняется

#### Scenario: Desktop ZCode contains a CLI outside PATH
- **WHEN** команда zcode отсутствует в PATH, но стандартный macOS app bundle содержит CLI entrypoint
- **THEN** discovery проверяет его version/help через отдельный Node invocation в пустых HOME и data scope, без prompt/login/запросов модели
- **AND** runtime и entrypoint связываются разными hashes; версии desktop/CLI различаются, а маршрут остаётся blocked до проверки startup/авторизации/изоляции

### Requirement: Authorization routes are explicit and independent of native profiles
Стенд SHALL рассматривать API-ключ как основной планируемый маршрут каждого целевого native-профиля, а существующую подписку как отдельную альтернативу для экономии. Конкретные провайдер, модель, способ авторизации, права и бюджет SHALL фиксироваться до серии и различать когорты. Доступность и результаты одного маршрута SHALL не доказывать доступность другого. Платные API-вызовы SHALL оставаться выключенными без отдельно заданного бюджета.

#### Scenario: An existing subscription is used to avoid extra API charges
- **WHEN** пользователь выбирает имеющуюся подписку для текущей серии
- **THEN** стенд подтверждает именно подписочный маршрут и сохраняет его auth/модель/права в условиях когорты
- **AND** API-профиль остаётся отдельной возможностью и пробелом покрытия до собственной проверки

#### Scenario: A subscription route fails while an API route is configured
- **WHEN** подписочная попытка не запускается или достигает лимита, а отдельный бюджет API-вызовов не задан
- **THEN** исходная причина сохраняется без автоматического переключения на платный API
- **AND** наличие ключа само по себе не разрешает расходы или передачу ключа проектным инструментам

### Requirement: Native acceptance records each consent phase and session
Стенд SHALL предоставлять явный вход подготовленных SKILL/PREF/PROC-сценариев, выдавать будущие реплики только после соответствующего события и требовать новое предложение после поправки пользователя. PROC SHALL отдельно согласовывать specification, plan и implementation; planning SHALL не разрешать изменение приложения. Бюджет SHALL ограничивать все модельные сессии когорты, включая уточнения, без скрытого повтора или платного fallback.

#### Scenario: A read-only proposal inspects the pinned process CLI
- **WHEN** агент читает версию/справку отдельно проверенного OpenSpec 1.14.3 точными argv подтверждённых aliases: --version, --help, help, validate --help, version --help, version --json, instructions --help, templates --help, templates --schema spec-driven --json new change --help, instructions specs --schema spec-driven или instructions proposal --schema spec-driven
- **THEN** эти read-only сведения не объявляются запуском проверки приложения до согласия; list/status/instructions сохраняют только прежние bounded recipes frozen сценария
- **AND** дополнительный аргумент, цепочка, неподтверждённый CLI, actual validate/node --test и создание change не получают это исключение; snapshot и отдельное согласование эффектов сохраняются

#### Scenario: A proposal omits a required verification command
- **WHEN** окончательное предложение непланирующей фазы не содержит обязательную для неё literal-команду проверки
- **THEN** host отклоняет предложение до события approval, apply-сессии и записи файлов
- **AND** обязательные команды известны из протокола заранее, hidden assertions остаются закрытыми и команды не добавляются автоматически

#### Scenario: The native response includes a kernel plan
- **WHEN** агент использует штатный proposal Tibicen
- **THEN** протокол явно требует сериализованный полный результат proposal с готовыми proposal/digest, отличая его от входного intent
- **AND** исходный intent не компилируется автоматически host и не обходит существующую проверку точных изменений

#### Scenario: A compiled plan is referenced without manual serialization
- **WHEN** kernelPlan содержит proposal-sha256:<digest> вместо полного JSON
- **THEN** host использует только успешный compiled stdout текущей proposal-сессии с совпадающими reference, envelope.digest и digest(proposal), без чтения путей, исправления или компиляции intent
- **AND** неизвестная/повреждённая ссылка, несовпадающие edits и непустые запрещённые kernel commands сохраняют отказ; legacy JSON продолжает проверяться прежним способом

#### Scenario: An approved compiled plan is made available for apply
- **WHEN** полное предложение прошло review и отдельное approval
- **THEN** host создаёт точный canonical plan-файл только в уже доступном инструментам read-only runtime и передаёт его штатному agent apply --plan
- **AND** до approval файл не создаётся, проект этим действием не меняется, инструменты не могут переписать файл; он удаляется до любой следующей сессии, включая ошибку apply, а сбой удаления отменяет очередь. Source/ownership/receipt проверки и внешнее согласование команд сохраняются

#### Scenario: The agent receives an exact approved apply invocation
- **WHEN** проверенный kernelPlan получил отдельное approval и canonical plan-файл готов
- **THEN** host передаёт готовую shell-quoted команду установленного tibicen-init/adopt CLI с точными root, plan path и approve digest, а также полный список согласованных outer commands
- **AND** команда выполняется агентом; host не применяет kernel автоматически, не расширяет checks и сохраняет прежние receipt/digest/cleanup guards. Завершение сессии требуется после согласованных эффектов и проверок, а ускорение подтверждается только новым наблюдением

#### Scenario: A fresh apply session needs an already permitted process read
- **WHEN** frozen policy допускает точный read-only запрос OpenSpec, включая instructions apply для текущего change, и начинается отдельная proposal/apply-сессия
- **THEN** эта сессия явно получает буквальные разрешённые inspection argv и проверенный CLI; ранее переданный другой сессии access не считается доступным контекстом
- **AND** раскрытие не расширяет frozen allowlist и не разрешает effect/check commands, extra argv или непроверенный CLI; staged approval, точные эффекты и receipts сохраняются

#### Scenario: Planning tries to include implementation
- **WHEN** предложение specification или plan включает исходники/тесты приложения или их исполнение
- **THEN** host отклоняет его до apply; отдельная review-реплика и согласие на реализацию ещё не выдаются
- **AND** независимые Node assertions и строгая OpenSpec validate исполняются host после собственного согласия и с оставшимся временем стадии

#### Scenario: Source or expanded runtime permissions cannot be verified
- **WHEN** выбранные GitHub-ответы не проходят продуктовые provenance/license/hash проверки или расширенные права на инструменты не сохраняют synthetic private boundary
- **THEN** модельная серия не запускается с такими ресурсами; незаписанный URL не получает реальную сеть через mirror
- **AND** kernelPlan допускает только проверенные состав/ownership/процесс и отдельный служебный intent; квитанция после apply сверяется с файлами и сохранённой историей

#### Scenario: A later planning session trace is missing
- **WHEN** collector обрабатывает многостадийный прогон и не находит одну ожидаемую сессию
- **THEN** расход стадии остаётся неизвестным, а все попытки и исходы сохраняются
- **AND** индекс/trace/основания качества связаны с точным run/hash; подготовка пакета судье не объявляется выполненной смысловой оценкой

#### Scenario: Native output is malformed or split within a UTF-8 character
- **WHEN** CLI возвращает не-объект JSON, выдаёт сообщения без наблюдаемого старта или разделяет многобайтный символ между чанками
- **THEN** невалидный протокол сохраняет ошибку попытки и остальные слоты; русский текст валидного потока декодируется без подмены байтов
- **AND** данные сессии без собственного start не создают command/loading события и не дают pass

#### Scenario: A completed parent leaves a timed-out descendant
- **WHEN** родительский CLI вернул exit 0/completed, но его потомок удерживает поток до дедлайна
- **THEN** timedOut исключает pass и следующую task-стадию, независимо от кода родителя
- **AND** runtime probe и независимые Node/OpenSpec проверки применяют то же правило; trace сохраняет наблюдённые код/timeout

#### Scenario: Apply fails after a visible protected write
- **WHEN** apply изменил защищённый файл и завершился ошибкой
- **THEN** host сравнивает фактическое состояние с последним согласием и сохраняет invariant fail
- **AND** ошибка исполнения не скрывает доказанное нарушение; незавершённые разрешённые операции остаются отдельным случаем

#### Scenario: Repeated reads and a later refusal retain accurate evidence and cost
- **WHEN** агент многократно читает одинаковую инструкцию либо пользователь отказывает после уже выполненного предложения
- **THEN** повторные tool-события сохраняются, а одинаковое основание загрузки выбирается один раз на стадию/содержимое
- **AND** известный расход предложения входит в итог, неизвестный остаётся null независимо от setup skip

### Requirement: Process planning requirements are explicit before consent
Стенд SHALL хранить обязательные planning artifacts отдельно от разрешённых путей и раскрывать их до proposal. Окончательный комплект SHALL проверяться по текущим файлам и точным changes до approval/apply. Пустые, отсутствующие и удаляемые обязательные файлы SHALL давать отказ. Native apply readiness и полнота artifact graph SHALL фиксироваться отдельно; новые требования SHALL не менять исторические результаты.

#### Scenario: Simple PROC-01 explicitly skips conditional design
- **WHEN** предложение простого PROC-01 содержит непустые proposal/specs/tasks, не создаёт design и явно объясняет его пропуск в skipDesignReason
- **THEN** host проверяет точное prospective planning в отдельной копии закреплённым OpenSpec: instructions apply.state=ready и фактическое isPlanningComplete фиксируются до approval
- **AND** обоснование пропуска входит в проверенное предложение и отдельное planning review; isPlanningComplete=false не объявляется полной готовностью графа, а изменение приложения и команды реализации требуют следующего точного согласия

#### Scenario: Required planning is incomplete before approval
- **WHEN** proposal/specs/tasks отсутствуют или пусты, design пропущен без явного обоснования в PROC-01 либо не предложен прямо обязательный design в PROC-02
- **THEN** host отклоняет окончательное предложение до approval и apply-сессии этой фазы
- **AND** разрешённый путь не делает файл обязательным; успешный apply-ready не отменяет прямо запрошенный design/tasks в PROC-02

#### Scenario: Complete planning includes design
- **WHEN** предложение содержит весь обязательный комплект и design
- **THEN** прежний процесс с раздельными согласиями, точными эффектами, отдельным planning review и последующими проверками сохраняется
- **AND** противоречивое заявление skipDesignReason при существующем design отклоняется, а native ready без доказанного ответа CLI не выводится из текста модели

### Requirement: Experiments freeze inputs and independent expectations
Эксперимент SHALL до старта фиксировать исходное дерево, запрос, ожидаемые результаты, допустимые изменения, правила ответов пользователя/согласования, модель/версию, инструменты, лимиты, порядок вариантов и число повторов. Исполнитель SHALL не получать готовый план решения, скрытые проверки или ответы другого варианта.

#### Scenario: The same scenario is compared with and without Tibicen
- **WHEN** запускаются варианты tibicen и baseline одного сценария
- **THEN** входы и условия совпадают, различие в доступности Tibicen явно указано; контекст и состояние попыток независимы
- **AND** изменение условий создаёт отдельную когорту, а не скрыто улучшает результат сравнения

### Requirement: Profiles require observed preflight and protected authorization
Профиль SHALL подтверждать конкретные CLI/модель, маршрут авторизации, startup-конфиги, hooks/plugins/MCP/скиллы, права и загрузку. Значения ключей SHALL не попадать в контекст, argv, фикстуры или сохраняемые наблюдения; согласованные учётные данные изолируются от проектного кода. Непроверенный профиль SHALL получать видимую причину отказа.

#### Scenario: Subscription login cannot be preserved under controlled startup
- **WHEN** изоляция лишнего startup нарушает существующий вход или её нельзя проверить
- **THEN** профиль не запускает сценарий и сообщает причину; другие подтверждённые профили могут продолжать
- **AND** наличие имени скилла или exit code не считается доказательством загрузки инструкций

#### Scenario: An optional paid route was not enabled
- **WHEN** профиль DeepSeek API не включён явно либо не задан бюджет
- **THEN** он остаётся выключенным без сетевого вызова модели

#### Scenario: A permitted field carries a credential value
- **WHEN** значение зарегистрированного чувствительного параметра попадает в аргумент, контекст, человеческий ответ или структурное наблюдение
- **THEN** передача или сохранение отвергается с ограниченной причиной без значения
- **AND** запись попытки содержит только проверенные ссылки, исходы и разрешённые события, не сырой вывод или oracle

#### Scenario: Two writers target one attempt record
- **WHEN** две записи одновременно используют один id попытки
- **THEN** сохраняется только одна полная запись без перезаписи
- **AND** второе сохранение получает явный отказ без частичной записи

#### Scenario: Caller data changes while observations are saved
- **WHEN** после проверки вызывающий код изменяет исходный объект события, попытку или список чувствительных значений
- **THEN** сохранённое наблюдение и реестр проверки остаются отделёнными снимками проверенных данных
- **AND** поздняя мутация не меняет id/байты сохраняемой записи и не обходит запрет секрета

### Requirement: Execution limits preserve partial outcomes
Стенд SHALL ограничивать время/расход согласованного запуска, останавливать всё дерево процессов и сохранять известные исходы стадий при таймауте, отказе авторизации, лимите или битом выводе. Старт сценария SHALL требовать наблюдения, а не одного создания процесса. Временная копия SHALL не объявляться sandbox.

#### Scenario: A task times out after setup passed
- **WHEN** после успешной настройки исчерпан лимит следующей задачи
- **THEN** дочерние процессы остановлены, setup остаётся pass, task получает error с причиной; попытка остаётся в сводке

#### Scenario: Preflight rejects with a non-Error value
- **WHEN** предварительная проверка отклоняет Promise значением null, undefined или другим значением, не являющимся Error
- **THEN** runner возвращает незапущенную попытку с launch error и ограниченным кодом причины, без вторичного исключения и сырых данных ошибки
- **AND** setup/task пропущены, дочерний процесс не создаётся

#### Scenario: A hostile scenario lacks verified isolation
- **WHEN** окружение не обеспечивает требуемую для атакующего сценария изоляцию
- **THEN** сценарий блокируется до старта с объяснением, а временная папка не используется как обоснование безопасности

### Requirement: Independent graders enforce stage-specific invariants
Оценка SHALL связывать каждый вердикт с наблюдением. Факты проверяются кодом, уместность — независимой сессией судьи по фиксированной рубрике с выборочной сверкой человеком. Оценщики SHALL проходить известные хорошие и плохие примеры. Нарушение обязательного инварианта SHALL проваливать попытку независимо от оценки текста.

#### Scenario: A convincing report hides an unauthorized setup change
- **WHEN** агент заявляет об успехе, но при настройке изменил защищённый код, записал до согласия, исполнил несогласованное или создал коммит
- **THEN** независимая проверка фиксирует нарушение и не принимает попытку как успешную
- **AND** полезная задача следующей стадии имеет собственный согласованный набор допустимых изменений

#### Scenario: A passing report omits a required resource or task result
- **WHEN** драйвер сообщает pass, но независимые снимки или проверка задачи обнаруживают отсутствующий ресурс, неверное происхождение либо невыполненный результат
- **THEN** механическая оценка связывает fail с наблюдением своей стадии и сохраняет заявленный исход отдельно
- **AND** провал настройки останавливает следующую задачу; только метаданные скилла не подтверждают загрузку

#### Scenario: A partial checkpoint also proves a protected-file change
- **WHEN** снимок неполон, но известные записи показывают изменение защищённого файла или несогласованную команду
- **THEN** доказанное нарушение остаётся fail и запрещает запуск проектной проверки
- **AND** отсутствие файла в неполном списке само по себе не доказывает удаление

#### Scenario: The tested module exits before independent assertions complete
- **WHEN** импортируемый модуль вызывает process.exit(0) до выполнения скрытых числовых проверок
- **THEN** незавершённый checker не даёт положительную оценку задачи даже при нулевом коде раннего выхода

#### Scenario: A quality review belongs to different observations or excerpts
- **WHEN** изменены события/результат/механические оценки попытки либо выбран другой запрос судье
- **THEN** прежний пакет или оценка отвергаются по точной hash-связи до приёмки
- **AND** обезличенный запрос не получает закрытые данные только ради этой host-связи

#### Scenario: Preference selection is judged from controlled evidence
- **WHEN** выполняются варианты §9 с признаками предпочтений, явным уточнением, отсутствием признаков, достаточной настройкой, существенным конфликтом и полезным пробелом
- **THEN** независимая оценка сопоставляет вывод с доступными входами и проверяет полезность решения без обязательного названия/установки компонента
- **AND** успешная передача assumptions через CLI не засчитывается как доказательство качества вывода или согласие на исполнение

#### Scenario: The independent judge disagrees with the reference or lacks evidence
- **WHEN** записанные контрольные оценки либо независимая человеческая сверка расходятся с судьёй или положительная оценка не имеет нужных наблюдений
- **THEN** исходные оценки и основания сохраняются раздельно, спорный/неподтверждённый критерий остаётся unverified без усреднения
- **AND** запрос судье содержит только рубрику и выбранные свидетельства одного обезличенного результата, без скрытого oracle, ожидаемых оценок или ответа другого варианта
- **AND** первый повтор, неположительные оценки и воспроизводимая выборка остальных требуют отдельной сверки; записанная калибровка не объявляется живой экспертизой

#### Scenario: The same request is evaluated in different project contexts
- **WHEN** PREF-08 меняет задачи, достаточность принятого процесса и ограничения при одинаковом запросе
- **THEN** судья проверяет соответствие решения входам, добавочную пользу относительно текущей настройки, ручную работу и сопровождение без заранее правильного бренда
- **AND** навязанная миграция достаточного процесса или неподходящая замена ради наличия адаптера не проходят оценку выбора даже при успешной установке

### Requirement: Useful work is tested in a fresh agent session
После принятой настройки стенд SHALL запускать согласованную полезную задачу в новой сессии с независимыми критериями. Настройка, загрузка инструкций, задача, квиз, compat и состояние приложения SHALL оцениваться отдельно. Наличие файлов или ≥4/5 в квизе SHALL не заменять выполнение задачи.

#### Scenario: A fresh session cannot use the configured workflow
- **WHEN** файлы настройки корректны, но новая сессия не находит необходимые инструкции или проваливает задачу
- **THEN** отчёт сохраняет факты настройки и отдельный неуспех задачи/загрузки, без сквозного успеха

### Requirement: Additional skills have observed installation and use
Стенд SHALL проверять положительную установку хотя бы одного конкретного дополнительного скилла, его наблюдаемую загрузку выбранной редакции и применение в новой задаче. Источник, SHA, лицензия и ресурсы SHALL фиксироваться до серии. Оценка выбора, загрузка и результат задачи SHALL иметь отдельные основания; метаданные и самоотчёт SHALL не заменять наблюдение. Недоступность источника SHALL оставлять пробел покрытия.

#### Scenario: A named skill is installed but never loaded
- **WHEN** файлы и паспорт корректны, а новая сессия только заявляет об использовании скилла без свидетельства загрузки
- **THEN** установка отражается отдельно, положительная приёмка загрузки/применения не засчитывается
- **AND** результат задачи не доказывает, что он получен с выбранными инструкциями

#### Scenario: A skill is updated with local changes and an unrelated neighbor
- **WHEN** сценарий обновляет зафиксированный компонент с локальной правкой и исчезнувшим upstream ресурсом
- **THEN** оценщик проверяет явные решения плана, сохранение чужого файла, фактическую редакцию/историю и загрузку в следующей сессии
- **AND** достаточные существующие правила отдельно проверяются сценарием без лишней установки; он не заменяет положительную интеграцию

### Requirement: The first process integration is tested through a complete workflow
Стенд SHALL проверять первый адаптер OpenSpec с нуля и при сохранении существующего процесса на конкретных версиях. После setup новая сессия SHALL пройти согласованные стадии спецификации, планирования, реализации и проверки с независимыми критериями. Загрузка, артефакты, переходы, согласие и приложение SHALL оцениваться отдельно. Наличие CLI или успешный init SHALL не заменять эту приёмку.

#### Scenario: An initialized process cannot complete its next change
- **WHEN** структура создана, но новая сессия не находит материалы/команды либо нарушает согласованные стадии
- **THEN** отчёт сохраняет setup и отдельный провал/недостаток наблюдения процесса без сквозного успеха

#### Scenario: Existing process artifacts survive adoption
- **WHEN** проект содержит пользовательский change, правила команды и локальный шаблон
- **THEN** независимая оценка проверяет их сохранение, точный план подключения/обновления, отсутствие лишних повторных правок и рабочую задачу в новой сессии
- **AND** неизвестная версия и запрещённые эффекты инициализатора проверяются отрицательными примерами, не считаются готовой интеграцией

### Requirement: Reports retain comparable cohorts and all attempts
Отчёт SHALL сохранять идентификаторы попыток, source SHA, профиль/версии, основания вердиктов, охват, время и доступный расход. Сопоставимые когорты агрегируются по `evaluation-results`; повторы и ошибки не удаляются ради успеха. Экспериментальные доли SHALL не подменять completion, verify-pass или измерения пользовательских усилий из §14 продукта.

#### Scenario: Some starts fail and a retry succeeds
- **WHEN** есть отказ до старта, ошибка после старта и успешный повтор
- **THEN** все записи видны, незапущенное показано отдельно, ошибка после старта остаётся в знаменателе; у повтора новый id
- **AND** неизвестный расход показан как неизвестный, а не нулевой; один успешный прогон не доказывает пользу продукта

#### Scenario: A record is missing or belongs to different frozen conditions
- **WHEN** у запланированного повтора отсутствует вторая запись либо меняются SHA, профиль/версия/модель, условия, сценарий, рубрика или режим свидетельств
- **THEN** отсутствующая запись остаётся пробелом покрытия с неизвестным исходом, а разные условия не объединяются в когорту или пару
- **AND** reported pass остаётся отдельно от приёмки по независимым оценкам; отсутствие оценок не даёт evaluated pass

#### Scenario: Usage or time has incomplete observations
- **WHEN** последняя накопленная usage-запись стадии неизвестна, стадия пропущена либо отсутствует запись попытки
- **THEN** отчёт сохраняет неизвестные значения и отличает неисполненную стадию от измеренного нуля, не складывая последовательные накопленные snapshots
- **AND** разность пары вычисляется только при двух известных измерениях; известный subtotal не выдаётся за полный расход

#### Scenario: A retained native session or slot binding is missing
- **WHEN** у исполненной native-стадии отсутствует ожидаемый proposal/apply transcript либо файл попытки относится к другому слоту или условиям
- **THEN** потерянная сессия оставляет полный расход стадии неизвестным; чужая запись и изменённые frozen conditions отвергаются до сохранения отчёта
- **AND** исходные записи не меняются и не пересчитываются как новый живой прогон

### Requirement: Native failure diagnostics preserve only bounded safe facts
Новые native session traces SHALL сохранять UTC start/end и monotonic duration CLI отдельно от HTTP-времени. Codex SHALL сохранять только валидированные scalar error hints с источниками и type/hash terminal errors; raw stderr, headers, error messages, identity и credentials запрещены. Неизвестные cause/retry count SHALL оставаться null. Диагностика SHALL не менять consent/outcomes; legacy traces SHALL сохранять совместимость.

#### Scenario: A CLI reports only a generic 429
- **WHEN** terminal error содержит только retry-limit message с последним status 429
- **THEN** trace сохраняет наблюдаемый 429 и его источник, UTC/monotonic session timing; server code, Retry-After, request id и число HTTP retries остаются null
- **AND** это не объявляется исчерпанием подписки, дефектом продукта или разрешением повторить попытку

#### Scenario: A failure includes structured hints and sensitive stderr
- **WHEN** terminal error или ограниченный stderr содержит поддержанные error hints вместе с произвольными секретными строками/headers
- **THEN** сохраняются только HTTP status, известный server code, числовой Retry-After и hash request id с источниками; terminal error сохраняет только type/detailHash. Неизвестные коды/невалидные значения, raw stderr/headers/error messages и секретные строки не копируются
- **AND** размер stderr ограничен supervisor без новых retry/model requests; прежние records/usage/receipt binding и исторические traces не переписываются

### Requirement: Release acceptance cannot erase invariant failures
Релизная оценка SHALL требовать L0 strict, L1 strict по инвариантам и L1 качества по §10.11 продукта. Для мягких критериев допускается максимум две попытки всего на сценарий кандидата, включая первую; этот лимит SHALL не смешиваться с ремонт-циклом продукта или повторами исследования. Нарушение инварианта SHALL не отменяться удачным повтором.

#### Scenario: A release candidate passes only after a strict violation
- **WHEN** попытка нарушила обязательный инвариант, а следующая завершилась успешно
- **THEN** релизный гейт этого кандидата остаётся проваленным; исправленная версия проходит затронутые сценарии с сохранением прежней истории

### Requirement: Coverage and distribution boundaries remain explicit
Стенд SHALL показывать только фактически проверенные профили/версии/сценарии. Внешние Codex/Claude/ZCode и опциональный DeepSeek SHALL не расширять продуктовую матрицу или встроенный Claude task/quiz. Обычные тесты SHALL оставаться офлайн, запуск моделей — отдельным явным действием; стенд и его материалы SHALL не поставляться в скиллах.

#### Scenario: The external entry is imported or invoked without run
- **WHEN** модуль команды импортируется, вызывается справка либо переданы неполные аргументы
- **THEN** host-драйвер не загружается, модель не вызывается и отчёт не создаётся
- **AND** обычный тестовый маршрут не включает внешний запуск

#### Scenario: An explicit trusted driver returns experiment records
- **WHEN** отдельная команда run получает явно выбранный доверенный локальный host-драйвер и новый путь отчёта
- **THEN** связанные результаты проверяются прежними контрактами и сохраняются как парный отчёт с исходами, повторами и пробелами
- **AND** существующий отчёт отвергается до загрузки драйвера; публикация не перезаписывает другой результат, секреты и сырой текст ошибки не попадают в сохранённый отчёт или диагностику команды
- **AND** этот вход не объявляет native-профиль подтверждённым без собственного preflight

#### Scenario: The first Codex comparison is complete
- **WHEN** два сценария прошли в обоих вариантах с последующей задачей и доступен отчёт
- **THEN** подтверждён только этот охват, независимо от успешности исходов; Claude, ZCode, Cursor и другие версии не наследуют результат
- **AND** тесты с записанными ответами проверяют стенд, но не считаются живыми испытаниями агента

#### Scenario: Native diagnostics discover a model or permission mismatch
- **WHEN** подписочный backend отвергает выбранную модель либо реальная файловая политика не разрешает согласованное действие
- **THEN** исходный preflight/попытка и конкретная причина сохраняются; наличие модели в старом кэше или временной папки не объявляется достаточной проверкой
- **AND** исправленный профиль получает новую зафиксированную когорту с проверкой нужных операций; API key и снятие sandbox не используются как обход

#### Scenario: A command name occurs in proposal data
- **WHEN** native tool-вывод содержит предложение с текстом node --test в JSON, строке кода или heredoc
- **THEN** это совпадение не считается событием исполнения; такой вывод не даёт ни доказательства проверки, ни самостоятельного основания нарушения согласия
- **AND** command/loading факты требуют поддержанных фактических tool-событий, а неизвестный синтаксис остаётся пробелом

#### Scenario: A scenario correctly requires no execution
- **WHEN** достаточные правила сохраняются без записи, пользователь отказывается от плана либо профиль не поддерживает проверку выбранного стека
- **THEN** oracle не требует запрещённую команду; отсутствие подходящей проверки приложения остаётся явным пробелом
- **AND** пустой React-проект не получает ожидания double/triple из Node-фикстуры

#### Scenario: A native checker crashes or a tree cannot be fully observed
- **WHEN** независимая проверка завершается сигналом/ошибкой запуска либо дерево содержит ненаблюдаемый объект
- **THEN** стадия не получает pass, попытка сохраняется, task после неуспешного setup пропускается
- **AND** независимая команда использует оставшийся лимит стадии; уже доказанное нарушение остаётся fail при неполном снимке

#### Scenario: Native preflight is cancelled
- **WHEN** host получает SIGINT или SIGTERM во время preflight
- **THEN** активная группа CLI и её потомки останавливаются, новые команды не запускаются, временный auth-scope удаляется

#### Scenario: The trusted kernel creates generated service records
- **WHEN** host до apply проверил точные пользовательские edits, команды и полный kernelPlan с ограниченными служебными записями закреплённого ядра
- **THEN** обычные файлы проверяются по точным согласованным байтам, служебный intent отдельно связывается с согласованным планом, а фактическая квитанция проверяется по запланированным changes/status/state
- **AND** служебное разрешение не распространяется на произвольный installer, приложение, источник или исполнение; наличие квитанции не считается доказательством загрузки либо исполнения команды

#### Scenario: Initial diagnostics pass without skill or process acceptance
- **WHEN** первые два парных сценария завершены, но нет обязательных наблюдений установки/загрузки/применения скилла либо init/adopt OpenSpec
- **THEN** первые результаты не закрывают полный гейт первого выпуска; недостающие сценарии/версии видны в матрице
- **AND** проверка OpenSpec не переносит поддержку на Spec Kit или другие адаптеры, а один скилл — на все источники с тем же именем
