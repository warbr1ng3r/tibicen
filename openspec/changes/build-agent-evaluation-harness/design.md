# Design

## Context

См. `proposal.md`. В `scripts/evals/results.ts` есть schema 1, строгая валидация стадий и три агрегата. Контракты, 67 расширенных фикстур, runner подставных процессов, хранение/механические оценщики, recorded-калибровка рубрики, парный отчёт и явный вход 2.6 реализованы офлайн. Codex preflight и две первые диагностические пары 3.1–3.2 наблюдались; смысловая приёмка, SKILL/PREF/PROC и остальные native-профили остаются открытыми. Основной продукт ограничивает встроенные task/quiz Claude-адаптером; внешний стенд это решение не меняет.

## Goals / Non-Goals

**Goals:** отделить подготовку эксперимента, наблюдение, оценку и агрегацию; получить проверяемые основания сравнения без изменения установленного runtime.

**Non-Goals:** платформа оркестрации, собственный sandbox, новые продуктовые агенты, фоновая телеметрия или вызовы моделей в обычном CI. Стенд проверяет явно включённый первый адаптер OpenSpec, но не реализует его и не добавляет поддержку Spec Kit/остальных будущих адаптеров.

## Decisions

### Native acceptance profiles and shared workflow

Способ авторизации — отдельное измерение native-профиля. API-ключ является основным планируемым маршрутом для Codex/Claude Code/ZCode; фактически доступные подписки используются как альтернативы для экономии. Провайдер, модель, auth и права подтверждаются для каждого маршрута и входят в frozen conditions; результаты разных маршрутов не смешиваются. Пользователь не разрешал дополнительных расходов: платные API-вызовы выключены до отдельного бюджета, подписочный отказ не включает API fallback. Сейчас common runner ещё требует `maxCostUsd: null` и запрещает API; задача 3.7 должна заменить это ограничение проверяемым выбором маршрута и бюджетом. Эта архитектурная цель не объявляет API-профили уже готовыми.

В продолжении 3.6 общий native runner, consent/schema, лимиты, process supervisor, независимые проверки и evidence отделены от профилей `profiles/codex`, `profiles/claude`, `profiles/zcode`. Общий интерфейс нормализует сообщения/tool events/start/completion/usage; специфичные CLI/config/auth остаются внутри профиля. Codex перенесён с сохранением старых import/CLI-входов. Claude/ZCode сейчас реализуют только version/help discovery и отказ неподтверждённого запуска; выбранный blocked-профиль сохраняет все парные слоты без подстановки Codex. Это готовность структуры, не приёмка трёх native-маршрутов.

ZCode discovery учитывает desktop-установку: при отсутствии PATH-команды проверяет стандартные macOS app bundles и запускает их `.cjs` entrypoint через Node. Профиль задаёт отдельный data-home env; общий probe отвечает только за argv, чистую среду, лимиты/группы и hashes runtime/entrypoint. Локальные desktop 3.14.4 / CLI 0.16.9 подтверждены только version/help, не авторизацией или живой загрузкой скилла. Проверен отдельный stream-json parser, но loader остаётся hard blocked с четырьмя явными startup/auth-read/fs-write/process-tree gaps; задача 3.4 закрыта конкретным отказом, не готовностью native execution.

Явный выбор SKILL/PREF/PROC требует frozen budget/порядок/repeats. PROC task имеет отдельные specification/plan/implementation согласия с разными путями; поправка требует нового предложения, отказ прекращает setup, будущая review-реплика выдаётся перед реализацией. Новый runtime probe проверяет сохранность synthetic private boundary после открытия отдельно проверенных инструментов. Для источников используется явно захваченный публичный GitHub mirror, перепроверенный продуктовыми provenance/license/hash правилами и общими pins; Node preload не имеет реального сетевого fallback. OpenSpec dev-пакет сверяется с полным frozen inventory, без автоматического init/update/установки в приложение.

Все proposal/apply/уточняющие сессии индексируются hash и digest run. Collector использует нормализованный usage, оставляет null при потере ожидаемой сессии и перепривязывает выбранные основания/пакеты судье к обогащённому run. Независимые Node assertions/OpenSpec validate используют оставшееся время стадии. Kernel approval сверяет точный показанный diff, component ownership, закреплённый состав и последующую квитанцию/историю. Обязательные literal-команды проверки объявляются заранее и проверяются до approval/apply, без автоматического добавления и раскрытия hidden assertions; planning и отказ сохраняют отдельные ветки. kernelPlan допускает явную proposal-sha256 ссылку только на успешный compiled stdout текущей proposal-сессии с проверенным digest; legacy envelope JSON сохранён. Intent host не компилирует. После approval точный canonical plan-файл передаётся штатному apply в read-only runtime и удаляется до следующей сессии, включая ошибку; сбой cleanup отменяет очередь. Runtime read/write boundary проверяется до модели. Kernel commands остаются пустыми, тесты согласуются отдельно во внешнем commands. Judge/человеческая выборка выполняются отдельно. [Контракт запуска и ограничения](../../../docs/evals/NATIVE_RUNS.md); fake CLI в тестах не является свидетельством ОС-изоляции или поведения живой модели.

- **Существующий формат остаётся строгим.** Метаданные эксперимента и очищенные события имеют отдельные версионированные контракты со ссылкой на id попытки; итог передаётся в `validateAttempt`/`summarizeAttempts` без лишних полей. Ослабление schema 1 ради произвольных логов сделало бы имеющиеся проверки бесполезными.
- **Один локальный стенд на Node.** Runner, интерфейсы профиля/оценщика и сценарные материалы остаются в области разработки; сначала используются подставные процессы и записанные наблюдения. Новая eval-платформа или SDK не требуются. Конкретные имена новых файлов определяются при реализации внутри этой области.
- **Фикстура содержит задание, не ответ исполнителю.** Определены исходное дерево, допустимые изменения, правила согласования, типичная задача и независимый oracle. Ответы пользователя проверяют предъявленное предложение, не передают агенту готовый план. Скрытые проверки и результаты другой попытки недоступны исполняющей сессии.
- **Наблюдение не равно вердикту.** До сохранения выбираются разрешённые структурные поля, а не полный сырой вывод с последующим обещанием очистки. События подтверждают старт и действия, оценщики выдают основания; агрегатор не становится судьёй. Неизвестные время/расход или результаты показываются явно. Для сравнения выбираются одинаковые условия и конкретный source SHA.
- **Профиль подтверждается до сценария.** Preflight использует сначала синтетический секрет для проверки изоляции, затем согласованный существующий вход без чтения значения в контекст. Подтверждаются startup, инструменты, права и остановка потомков; неконтролируемый профиль блокируется. Временная копия — средство сохранения входа, не изоляция стороннего кода.
- **Две независимые стадии.** Настройка начинается с чистого состояния, задача — с её результата в новой сессии. У setup и task разные разрешённые изменения и оценки. При setup не pass задача пропускается с причиной; последующий task error не отменяет setup pass. Baseline получает тот же запрос и ограничения без Tibicen.
- **Оценщики проверяются до моделей.** Код проверяет инварианты и ожидаемый результат задачи, отдельный судья — рубрику достаточности/противоречий с выборочной сверкой человеком. Набор известных положительных/отрицательных примеров включает ложный отчёт об успехе. Инвариант имеет приоритет над качеством текста.
- **Работа и приёмка имеют разные зависимости.** Форматы/фикстуры готовятся параллельно группе 2 `extend-infrastructure-contracts`; итоговая серия следует после её приёмки и проверки стенда. Диагностические ранние прогоны помечаются. Исправление SHA требует повторить затронутые сценарии, сохранив старые попытки.
- **Выбор, загрузка и применение разделены.** PREF проверяет обоснованность рекомендации, SKILL — конкретные байты/ресурсы, наблюдаемую загрузку и выполнение правил в новой задаче, PROC — доступность процесса и прохождение его стадий. Самоотчёт агента, метаданные или один init не закрывают эти основания. Нужен хотя бы один зафиксированный дополнительный скилл; Ponytail и Caveman — кандидаты конкретной технической проверки, до фиксации источника/SHA/лицензии их интеграция не заявляется. Явно запрошенные SKILL-01/PROC-01 не определяют рекомендацию другим проектам.
- **Пригодность проверяется изменением контекста.** PREF-08 даёт один запрос в четырёх контекстах: достаточные простые правила, достаточный принятый Spec Kit, подтверждённый пробел и подходящий кандидат без адаптера при неподходящем поддержанном. Судья проверяет основания, добавочную пользу и цену изменений; автоматическое предложение OpenSpec или другого фиксированного набора не получает pass за успешную установку. Конкретные входы замораживаются до серии, ожидания не видит исполнитель.
- **Процессные сценарии ждут механической готовности адаптера.** Для PROC нужны задача 3.3 и офлайн-часть 3.4 change ядра, затем стенд получает живые свидетельства и закрывает агентскую часть 3.4. Взаимного ожидания уже завершённой живой приёмки нет. Остальные будущие задачи группы 3 не блокируют первый выпуск.

## Risks / Trade-offs

- Подписочный вход может конфликтовать с изоляцией startup → проверять конкретный маршрут; отказ одного профиля не блокирует разработку остальных.
- Возможности остановки/изоляции зависят от ОС → подтверждать профиль на заявляемой ОС; атакующие сценарии не запускать без нужных гарантий.
- Самооценка агента завышает качество → независимые oracle/судья, калибровка и основания каждого вердикта.
- Малые серии не доказывают пользу → публиковать охват и исходы без обещания статистического преимущества; пользовательские усилия измеряются отдельным пилотом.

Ревью незакоммиченного блока выявило четыре дефекта, покрытые задачей 5.2: мутация проверенных объектов до записи, перенос оценки на изменённые наблюдения/запрос, потеря доказанного fail при неполном снимке и нулевой выход до скрытых assertions. События/проекция/реестр секретов отделяются копией; quality binding включает весь linked run, ответы связываются с bindingHash/packetHash. Неполнота не отменяет наблюдаемого нарушения и не доказывает отсутствие файла. Скрытый checker подтверждает завершение всех проверок через заранее зарегистрированный exit-handler; атакующий код по-прежнему требует отдельной изоляции, не обещанной офлайн-драйвером.

## Execution Order

Задачи 1.3–1.4 реализованы в [матрице](../../../docs/evals/MATRIX.md): 67 конкретных controlled/hostile случаев, независимые MechanicalOracle/QualityPlan/контрольные примеры, отдельный matrix-lock. В исполнителя не попадают oracle/будущие реплики/готовые ответы. Исторические state-шаблоны получены реальным hard exit; их synthetic root/HOME и digest привязываются host до заморозки пары. Привязка пользовательского state или изменение после старта этим механизмом не разрешены. Реальные источники Ponytail/старого полезного ресурса/Spec Kit имеют полный commit, Git blob, SHA256, MIT и состав; OpenSpec 1.14.3 — pnpm integrity, полный инвентарь и отдельные наблюдённые эффекты native init/update.

Задачи 3.1–3.2 используют отдельные [native Codex probe/driver](../../../docs/evals/CODEX_DIAGNOSTIC.md), сохраняя запрет настоящей авторизации в offline ProcessProfile. JS не читает значения credentials: родительский CLI использует временную auth-ссылку отдельного CODEX_HOME; команды не читают ни её, ни личный источник. Синтетический probe проверяет обе границы процесса, skill-записи и остановку потомка. Startup игнорирует user config/rules, не наследует credential env/сторонние hooks/plugins, loading требует конкретного tool-чтения. После read-only предложения host связывает exact edits/commands и, только для ограниченного доверенного ядра, весь kernelPlan со служебным intent; квитанция не подменяет наблюдение исполнения. Setup/task имеют разные HOME и native ephemeral сессии. В task скрытые числовые assertions исполняются отдельно от модели в защищённой копии. Исходы native-механики и независимое смысловое качество остаются раздельными.

Ошибки первого диагностического профиля сохраняются вместе с исходной когортой: payload с текстом команды не является исполнением, а штатная защита `.agents` требует явного проектного разрешения после согласия. Исправление создаёт новый conditions/experiment/harness hash. Неподдержанная модель подписки также остаётся отдельным preflight-отказом, без перехода на API key. Ни исправленная диагностика, ни observed pass без judge/человеческой сверки не закрывают релизный гейт или SKILL/PREF/PROC.

Задача 2.6 реализована в scripts/evals/external.ts и `pnpm eval:external`: только явный run загружает выбранный доверенный локальный host-модуль с run(), его результаты проходят buildPairedReport и сохраняются через общий атомарный writer наблюдений. Import/help не запускают драйвер; существующий отчёт отклоняется до его загрузки, ошибка не отражает сырые данные. Новый native-профиль этим входом не добавляется: preflight/авторизация/парсер и первые живые серии остаются задачами 3.1–3.2. [Контракт и офлайн-пример](../../../docs/evals/EXTERNAL_RUNS.md) описывают ответственность host-драйвера и отсутствие моделей в обычных тестах.

Задача 1.1 реализована в scripts/evals/contracts.ts: строгие schema 1 эксперимента/сценария/события/оценки, интерфейсы profile/preflight/grader, проекция исполнителя без oracle и staged-ответов, связь с неизменённым EvalAttempt. Документация — [CONTRACTS](../../../docs/evals/CONTRACTS.md). Сама валидация проверяет форму/ссылки/последовательность, не доказывает запуск, защиту секретов, наблюдение среды или качество оценщика.

Задачи 1.2/2.1 реализованы в scripts/evals/fixtures.ts и runner.ts: два зафиксированных сценария с отдельными oracle, независимая материализация входов, точная связь metadata, preflight/launch/setup/task с лимитами и отдельными процессами, staged-ответы только через host review и принудительная остановка POSIX-группы. [RUNNER](../../../docs/evals/RUNNER.md) описывает протокол подставных процессов и ограничения: нет готовых native-профилей, защиты реальной авторизации, физической изоляции скрытых данных, самостоятельной проверки среды или независимой оценки pass. Следующие задачи сохраняют эти обязательства.

Обработчик preflight принимает неизвестное исключение: только Error даёт проверяемое сообщение, остальные значения приводят к ограниченному preflight-unavailable. Null/undefined не вызывают вторичный сбой, попытка возвращается с launch error и пропущенными setup/task; поведение таймаута и отмены сохраняется.

Задачи 2.4–2.5 реализованы в quality.ts/report.ts. Судья получает отдельный обезличенный request без oracle/варианта/контрольных оценок. Зафиксированы семь критериев, обязательная сверка первого повтора/неположительных случаев и воспроизводимая выборка остальных; спор даёт unverified с сохранением обоих векторов. Записанные контрольные оценки проверяют контракт до моделей, не точность живого судьи. Отчёт держит отдельные observed/evaluated проекции schema 1 и консервативные когорты по полному experimentHash, сценарию, профилю, рубрике/плану и режиму. Все слоты/повторы остаются видимыми, пропущенная запись не считается отказом до старта; механический fail нельзя компенсировать текстом. Время skip и неизвестный расход не превращаются в ноль, usage — последний накопленный итог стадии. [Методика и сохранённые примеры](../../../docs/evals/QUALITY_AND_REPORTS.md) отделяют офлайн-готовность от будущего внешнего входа/preflight.

Задачи 2.2–2.3 реализованы в observations.ts/mechanical.ts. Записываются только связанные разрешённые поля, без контекста/oracle/сырых логов; файл 0600 публикуется атомарно с отказом на повтор id, включая параллельную запись. Зарегистрированный синтетический секрет проверяется перед передачей/сохранением, offline-команды не получают auth env. Реальная авторизация остаётся заблокированной до native preflight. Host отдельно фиксирует снимки дерева/точное согласие/поля паспорта и выполняет одобренные Node-проверки в копии со скрытыми случаями. Заявленный pass сохраняется отдельно; независимый fail не допускает task после неуспеха setup. Калибровка включает ресурсы/обновление/артефакты процесса на синтетических данных, без заявления живой SKILL/PROC-приёмки. Ограничения снимков, env и скрытых данных — в [OBSERVATIONS_AND_GRADERS](../../../docs/evals/OBSERVATIONS_AND_GRADERS.md); фактические команды — в [verification.md](verification.md).

Сценарная программа §9 — [PREF-01–08](../../../docs/evals/PREFERENCE_SELECTION.md). В формат стенда переносятся конкретные входы и отдельные закрытые ожидания; исполнителю не передаются критерии/ответы. Офлайн-forward summary/report проверяет передачу данных, а семантический судья отдельно оценивает основания, явный override, достаточность/пользу компонентов, соответствие кейсу и неопределённость. До наблюдаемых прогонов §9 не имеет статуса подтверждённого поведения.

Программа [SKILL/PROC](../../../docs/evals/COMPONENT_INTEGRATION.md) дополняет PREF и входит в обязательную приёмку первого выпуска. Источники/версии и все ресурсы замораживаются до серии; baseline имеет тот же доступ к ним. Изменение кандидата/версии создаёт новую когорту. В наблюдениях отдельно сохраняются основание загрузки, применение правил и результат задачи; доступные безопасные поля проверяет офлайн-калибровка оценщика.

Сначала контракты и офлайн-проверки runner/оценщиков. Затем два первых парных сценария Codex: приложение без инфраструктуры и конфликтующие инструкции. После этой диагностической точки — SKILL/PREF и PROC по механической готовности адаптера OpenSpec, каждый с последующей задачей и независимой оценкой. Далее внешние Claude Code через API-ключ и ZCode. Подписки Claude Pro у пользователя сейчас нет; её отсутствие не блокирует API-маршрут. Провайдер, модель и денежный бюджет фиксируются до платных запросов; изоляция ключа и ограничение расхода требуют реализации/подтверждения отдельным native-профилем. Затем — расширение до остальных сценариев А–Е, ML-инфраструктуры, двух tools и отказных случаев. DeepSeek API включается только явно с бюджетом. Первые четыре прогона не закрывают обязательную программу SKILL/PROC; этот порядок не является фактом запуска.

### Process inspection after the first PROC control

Первая PROC-пара сохранена как failed: физически read-only help/templates aliases не совпали с узкой metadata-проверкой host. Восемь отдельных clean HOME/XDG probes подтвердили отсутствие записей. Исправление5.5 использует один exact argv classifier для verified CLI: подтверждённые справочные формы плюс прежние frozen list/status/instructions. Физическая readOnly-метка actual validate не означает разрешения проверки до согласия; такой запуск остаётся отдельным command event. Unknown/extras/chains и неподтверждённый CLI не получают исключения. Oracle, approval, snapshot и phase guards сохраняются.

### Explicit planning before approval

Контракт 5.6 хранит required specification/plan paths в process fixture отдельно от allowed paths; они входят в frozen fixture hash и публичный протокол. PROC-01 требует proposal/specs/tasks, а условный design можно пропустить с непустым skipDesignReason в proposal. PROC-02 прямо требует design/tasks. Состав проверяется по текущим файлам с точным overlay предложенных изменений до approval; уточняющий вопрос сам по себе эффектов не разрешает.

Перед plan approval host создаёт отдельную prospective копию вне проекта, накладывает проверенные planning edits и вызывает только pinned OpenSpec status/instructions apply с остатком бюджета. Проверенный state=ready, isPlanningComplete и skip reason входят в основания planning review. Это read-only диагностика синтетической копии, раскрытая протоколом заранее, без команд приложения или разрешения code apply. Ready не заменяет required files и не означает graph complete. После точного применения сохраняются file/hash guards и проверка обязательного комплекта. Исторические run/report и неявный контракт прежней failed baseline не исправляются задним числом.

### Exact approved apply invocation

В новой паре timeout наступил после длинной setup proposal и поиска apply-синтаксиса в свежей сессии; отдельный baseline получил capacity error. Исправление 5.7 использует уже известные host installed tools, mode, root, canonical plan path и digest для готовой shell-quoted apply-команды. Список outer checks остаётся ровно reviewed.input.commands. Исполнение по-прежнему выполняет агент, receipt/exact effects/cleanup проверяет прежний host. Это устранение наблюдаемой необходимости искать параметры, а не доказанное устранение timeout или доступности модели; новый live-повтор этим исправлением не запускается.

### Safe failure diagnostics after the 429 audit

Отдельная задача 5.8 устраняет потерю наблюдений будущих сессий. Native runner добавляет UTC start/end и monotonic duration к trace, ограниченно читает stderr и передаёт его Codex parser только для извлечения безопасных scalar hints. Raw stderr и произвольные headers не записываются; известный код и числовой Retry-After валидируются, request id заменяется hash, каждое поле имеет источник. Новые terminal error/turn.failed records проецируются только в type/detailHash после извлечения hints из оригинала; raw messages/headers/identity не сохраняются. Прочие records и usage сохраняются прежним способом; дополнительные optional поля не требуют пересчёта старых receipts/collector outputs. Неизвестные server cause/retry count/endpoint не выводятся из defaults или generic429. Это не исправление server limit, не новый transport/auth framework и не live-повтор.

### Frozen inspection disclosure in every fresh session

Новая подписочная PROC-пара установила отдельный disclosure gap: instructions apply текущего change уже допускался frozen policy, но apply запускался с новым контекстом без точных read-разрешений. Агент отказался от всех согласованных эффектов. Исправление 5.9 передаёт разрешённые inspection recipes в каждую proposal/apply-сессию из общего источника точных argv с проверкой существующих hashes и verified CLI. Это раскрытие действующего разрешения, не расширение команд или отмена согласия на проверки/запись. Старый fail остаётся неизменным; эффект на настоящее выполнение требует отдельного будущего контроля.
