# Дизайн

## Контекст

См. [proposal](proposal.md). Раньше `runCommand` отказывал на win32 до запуска POSIX-группы процессов. Поиск контролируемых интерпретаторов предполагал Unix-биты исполнения и имена без расширений. Переносимая Windows-фикстура ожидала недоступную проектную проверку; теперь нужно проверить настоящее исполнение.

## Цели и ограничения

Один платформенный вход под существующими проверками и согласием. Сохранить форматы состояния, отдельные копии проектов и поведение POSIX. Без новых пакетов, готового бинарника, повышения привилегий, постоянного процесса, дискового кэша компиляции или общего интерфейса оболочки. Job Object управляет обычными потомками; он не ограничивает файловый/сетевой доступ и не защищает от намеренного выхода через WMI.

## Решения

1. **Закреплённый PowerShell-помощник входит в собственный Job Object до запуска проектного кода.** До разбора JSON и `Add-Type` помощник явно импортирует `Microsoft.PowerShell.Utility` по закреплённому абсолютному пути системного модуля; пути проекта и PATH не выбирают этот модуль. Windows PowerShell/.NET компилирует небольшой P/Invoke-класс в памяти. Он создаёт безымянный, не наследуемый дескриптор Job Object с `KILL_ON_JOB_CLOSE`, присоединяет к нему себя, затем запускает цель с `UseShellExecute=false`. Потомки наследуют членство. Помощник записывает результат и закрывает последний дескриптор, завершая себя и оставшихся обычных потомков. Это устраняет гонку поиска потомков у taskkill и окно между созданием suspended-процесса и его присоединением, если запускающий процесс погибает. Отсутствие PowerShell/модуля, запрет компиляции или невозможность присоединения дают явную недоступность.
2. **Структурированный запрос и отдельный результат.** Node создаёт один UTF-8 JSON-запрос с исключительным доступом в собственной временной папке, затем запускает закреплённый помощник с буквальными путями `-File` / `-RequestFile`, этой собственной папкой как cwd запуска и отключённым stdin помощника. Запрос сохраняет согласованную cwd целевого процесса. Поля запроса не подставляются в PowerShell-код и не передаются через переменные окружения; помощник получает согласованное минимальное окружение исполнения. Вход проекта перенаправляется отдельно через `RedirectStandardInput=true` и закрывается сразу после `Process.Start`: EOF задаётся явно, без зависимости от унаследованных дескрипторов. Случайный временный путь и nonce связывают ограниченный результат вне stdout/stderr. Отсутствующий или повреждённый результат означает недоступность; exit-код помощника не подменяет результат проекта. Временное состояние удаляется после завершения. Доверенный проектный код того же пользователя не считается изолированным противником.
3. **Два явных представления команд.** Для нативных `.exe` применяется стандартное CRT-экранирование аргументов Windows. Batch-файлы идут через закреплённый абсолютный системный `cmd.exe /d /s /v:off /c`, с кавычками и ограничениями: отказ для кавычек, NUL/переводов строки, символов подстановки/оболочки, скобок, аргументов с обратной косой чертой в конце и слишком длинной строки. Это покрывает обычную передачу npm-аргументов, не разрешая произвольные shell-строки. Системные пути берутся из системной папки хоста, не из cwd или проектного PATH.
4. **Один поиск интерпретаторов.** Proposal просматривает абсолютные папки PATH; Windows ищет нативные `.exe` без Unix-битов исполнения. Существующие границы внешнего абсолютного executable и согласованного скрипта сохраняются. Явный путь `./` не подменяется соседним файлом с расширением. Общая валидация отклоняет NUL в executable/cwd и Windows-написания запрещённых оболочек/коммитов.
5. **Нативные свидетельства обязательны.** Проверки представления аргументов и отказов работают на любом хосте. Настоящие Windows-тесты проверяют запуск, exit-коды, Unicode-пути/аргументы, batch-передачу, окружение/редакцию секретов, раннюю и живую отмену, timeout и завершение обычных потомков с унаследованными потоками и без них. Существующий ручной платформенный workflow запускает это на собранной поставке вместе с переносимой CLI-цепочкой apply/verify/status/report. [Нативная приёмка](verification.md#native-acceptance--windows-server-2022) прошла на Windows Server 2022 с Node 22.20.0 и 24.15.0; это не проверка всех Windows-сред или загрузки харнессом.

6. **Временные пути компилятора остаются относительными к собственной папке запуска.** Явные `CompilerParameters` ссылаются на загруженную framework-сборку `Process` по её системному пути и используют `TempFileCollection('.', false)`. Только на время компиляции `TMP`/`TEMP` процесса помощника равны `.`; `finally` восстанавливает прежние значения до запуска цели. Относительные временные аргументы не передают компилятору полные Unicode-пути. Новая глобальная папка, требование 8.3-путей или зависимость не добавляются. `.gitattributes` репозитория задаёт `* text=auto eol=lf`, делая текстовые байты checkout, включая поставляемые помощники, каноническими для межплатформенного сравнения поставки.

Прежние прототипы с pipe/файлом не установили причину в I/O. [Диагностический CI](https://github.com/warbr1ng3r/tibicen/actions/runs/44225584797) завершил `ReadAllText` и завис на шаге JSON/автозагрузки модуля. Последующий контроль с закреплённым импортом Utility прошёл разбор JSON, `Add-Type` и открытие job, но завис в `Run`. Явный EOF проекта — исправление контракта запуска, а не объяснение всех прежних зависаний. Последующие [контроли компилятора](https://github.com/warbr1ng3r/tibicen/actions/runs/44228143393) сузили оставшийся сбой до обработки временного вывода с Unicode: завершился только контроль с ASCII-окружением; одного явного Unicode `TempFiles` не хватило. Объединённое исправление относительных путей прошло [CI 44229803132](https://github.com/warbr1ng3r/tibicen/actions/runs/44229803132) на исходниках `7221397bae0679bffbe333d81b338fc55b33c741`; прежние неудачные попытки сохраняют свои исходы в [записи проверки](verification.md).

## Риски и компромиссы

- Холодный запуск PowerShell/C# добавляет время каждой команде → учитывать его внутри timeout, дать тестам реалистичный срок; заранее отменённая команда не запускается.
- Политика Windows может запретить компиляцию или вложенные jobs → вернуть недоступность и её причину, не ослаблять политику и не переходить на произвольную оболочку.
- Batch сложнее нативного argv → принимать только описанное подмножество и проверить настоящий `%*`-shim; более сложные строки доступны через нативный executable.
- Закрытие job завершает и помощника → читать отдельный результат после закрытия процесса/потоков, не использовать exit-код помощника как код проекта.
- На macOS разработчика нет нативного Windows-исполнения → подготовить точные исходники и локальные проверки, а Windows CI записать отдельно до заявления о проверенной поддержке.

## Миграция

Оставить работу Unreleased, а 1.6.0 — неизменной. Существующие планы и состояние читаются как прежде. После интеграции обновить проверки кандидата и манифесты ресурсов; следующий совместимый minor выбрать при подготовке релиза. Откат использует прежнюю опубликованную поставку; инфраструктура проекта автоматически не переписывается.
