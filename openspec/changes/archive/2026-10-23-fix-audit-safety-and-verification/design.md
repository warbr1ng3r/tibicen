# Design

## Context

Основание и объём — [proposal.md](proposal.md). Контракты — две дельты в `specs/`. Ниже описаны решения исправления; исходные результаты аудита относятся к `edfa451`, результаты реализации — в [verification.md](verification.md).

Существующие точки исправления: `runtimeHooks` теряет признак неполного прогона; MCP доверие берётся только из дополнительных записей плана; основной runner завершает только лидера процесса; сборка очищает лексически проверенный путь. Писатель создаёт файлы с `0600`, reader ограничивает данные 8 МиБ, а поиск секретов повторяет жадный поиск. В подборе выход из цикла не зависит от числа прошедших отбор кандидатов, и получение каждого файла создаёт новый кэш.

## Goals / Non-Goals

**Goals:** закрыть девять воспроизведений через существующие обработчики, тесты и публичный CLI; сохранить точное согласие, независимые статусы, историю и самостоятельность двух скиллов.

**Non-Goals:** новые процессные адаптеры, собственный sandbox, смена платформы тестирования, постоянный сетевой кэш, переустройство стенда, модельные вызовы и публичный выпуск. Старые активные changes не закрываются и не архивируются этим исправлением.

## Decisions

### 1. Preserve incomplete check outcomes — audit 1

В `scripts/core/runtime.ts` допускать `compareChecks` только после полного набора ожидаемых id и digest команд и нормального завершения обоих прогонов. Для нового проекта проверять полноту только итогового набора. Причины `command-source-changed`, `trust-required`, `command-outcome-unknown` и прочие отказы сохранять раньше сравнения; известные регрессии не обнулять.

В `scripts/core/apply.ts` отличать известный отказ до запуска от неизвестного исхода уже запущенной команды: первый не должен оставлять ложное `running`. Отдельное согласование повтора неизвестной команды сохраняется. Сравнение одинаковых успешных префиксов отвергается: оно не доказывает проверку остальных команд.

### 2. Derive MCP trust from the bytes being written — audit 2

В `scripts/mcp/index.ts` переиспользовать строгий разбор поддержанного JSON для сравнения исходных и итоговых серверных записей. В `applyPlan` до первого служебного сохранения вычислять добавленные/изменённые записи фактических MCP-файлов и требовать соответствующее явное `trusted: true` для агента и целевого пути. Поле `requiresExecutionTrust` не является источником разрешения.

Проверка действует для обычного `mcp`, сырых `changes`, установленного исходного файла и вручную изменённого resolved plan. Неизменённые серверы не требуют нового доверия; удаление само по себе не запускает код. Неоднозначные форматы и неподдержанный транспорт сохраняют ручной/отказной путь. Запретить только сырой вход недостаточно: resolved plan тоже является внешними данными.

### 3. Own termination of the process tree — audit 3

Для POSIX запускать процесс в собственной группе; на тайм-аут/отмену сначала завершать группу мягко, затем принудительно с фиксированным запасом 1 с. Выход лидера не отменяет принудительную остановку потомков; ожидание потоков также ограничено. Сохраняются `shell: false`, минимальный env, редактирование секретов и привязка к digest. Предварительная отмена не создаёт процесс.

Для Windows в этом исправлении возвращать `process-tree-unavailable` до запуска, пока отдельная штатная реализация не прошла проверку. Не выдавать POSIX-проверку за кросс-платформенную гарантию; отразить ограничение в документации. Подход остановки уже используется в офлайн-стенде, но его протокол не переносится целиком в продуктовый runner. Новая зависимость не требуется.

### 4. Validate build destinations before removal — audit 4

В `scripts/build.ts` нормализовать существующие реальные пути, проверить назначение, оба удаляемых дерева и `SHA256SUMS` до первого `rm`. Отклонять симлинк назначения, перенаправляющий родитель и пересечение с исходниками: внутри репозитория разрешён только `dist/` и его подкаталоги; безопасное внешнее назначение остаётся поддержанным. Одного сравнения строк недостаточно.

Тесты опасной сборки выполняются только в отдельной копии минимального исходного дерева. После отказа сравниваются хэши источников; удаление в рабочем checkout не является способом проверки.

### 5. Preserve ordinary file modes — audit 5

Писатель сохраняет обычные права существующего инфраструктурного файла. Для нового ресурса в точном плане вводится необязательный числовой `fileMode` из обычных битов `0000..0777`; специальные биты запрещены. При отсутствии поля применяется режим существующего файла либо `0600` для нового собственного текста. Для выбранного upstream файла режим выводится из проверенного Git `100644`/`100755`, показывается в предложении и перепроверяется при получении; произвольный режим не подменяет режим источника.

Права передаются в проверочные копии и учитываются при подтверждении результата/восстановлении. Правка одних прав не исчезает как no-op при совпавших байтах. Журнал фиксирует известные исходный и итоговый режимы вместе с хэшами; отсутствие этих сведений в прежних данных не мешает чтению и не создаёт ложного подтверждения. Изменения формы `Change`, `AppliedChange`, `FileRecovery` и записей исходных файлов должны быть согласованы в `types`, валидации, компонентах, сохранении и CLI. Миграция существующих схем ради необязательных полей не нужна; несовместимая смена смысла старого поля недопустима.

Служебные state/паспорт/счётчик остаются `0600`. Безусловный `0755` для всех файлов отвергается: он меняет права без основания.

### 6. Match writer limits to reader limits — audit 6

Сохранить действующий лимит 8 МиБ для собственных сериализованных документов; не увеличивать его без основания и не вводить отдельное хранилище оригиналов. Вынести общий лимит чтения/записи, проверять фактические UTF-8 байты полной сериализации до замены служебного файла. До начала применения проверить стартовый state с планом, историей и оригиналами.

При последующем росте журнала отказ записи оставляет предыдущий читаемый state, который уже содержит согласованный план и позволяет распознать фактические файловые операции. Для паспорта и счётчика действует тот же принцип. Не подрезать историю автоматически. Для прежнего уже слишком большого файла — явная ошибка и отдельный ручной разбор; обещание автоматического восстановления не добавляется.

### 7. Bound secret inspection without weakening it — audit 7

В `scripts/core/plan.ts` убрать повторный поиск жадного префикса имени с каждой позиции. Разбирать границу имени/присваивания однопроходно или эквивалентным линейным поиском; сохранить прежние поддержанные токены, приватные ключи, имена и разрешённые placeholders. Не объединять все детекторы секретов проекта в новую подсистему.

Регрессию длинной строки выполнять в отдельном процессе с лимитом 5 с на 1 МиБ и гарантированной остановкой при провале. Это широкий предел для обнаружения зависания, а не микро-бенчмарк и не сравнение миллисекунд под нагрузкой. Задача 7 зависит от готовой остановки дерева процессов либо использует уже проверенный изолированный тестовый механизм.

### 8. Retry based on usable candidates — audit 8

В `searchCandidates` переходить ко второму заранее заданному запросу, если после обработки первой выдачи нет допустимых кандидатов. Сохранить максимум две попытки, причины отклонения, дедупликацию и действующие сетевые/лицензионные ограничения. При сетевом отказе не добавлять цикл повторов. Успешная первая выдача завершает поиск сразу.

### 9. Reuse immutable reads within one apply — audit 9

В `sourceGate` создавать один `sourceCache` на применение и передавать его всем `fetchSourceFile`. Кэшировать только SHA-адресованные коммит, дерево и blob; актуальные metadata/license/blocklist проверки остаются отдельными. Память освобождается с запуском, другой apply и другой SHA не наследуют допуск.

Измерять число запросов по маршрутам: на двадцати файлах прежние 21 чтение коммита/дерева должны сократиться до числа проходов валидации, не зависящего от числа файлов. Число blob-запросов и проверки каждого хэша сохраняются объяснимыми. Объединять весь discovery pipeline ради устранения оставшегося фиксированного прохода не требуется.

## Risks / Trade-offs

- [Новые поля прав затрагивают восстановление] → проверить новые планы, прерывание до/после замены, старые schema 2/3 и подмену режима; старый формат не получает выдуманных свидетельств.
- [Остановка группы отличается между ОС] → POSIX-проверки реальными безопасными потомками; Windows отказывает до запуска и остаётся неподтверждённой платформой исполнения.
- [Граница размера может остановить длинную сессию] → диагностировать ограничение, сохранить последний читаемый файл и историю; не обещать поддержку произвольного суммарного размера.
- [Тест тайм-аута может оставить процесс] → ограниченный fixture, учёт PID, принудительная уборка в finally; проверки выполняются вне рабочего проекта.
- [Изменение шаблона секретов может ослабить отказ] → сохранить прежние положительные и отрицательные случаи; значения не выводить в ошибках.
- [Другие активные дельты затрагивают те же capabilities] → в этом change добавляются отдельные требования; при будущей синхронизации сохраняется объединённый контракт.

## Migration Plan

Реализовывать небольшими последовательными группами из [tasks.md](tasks.md): сначала регрессия, затем минимальная правка и соответствующие проверки. Обновить формат предложения и ограничения после изменения обработчиков. Полный офлайн-прогон, сборка и проверки обеих упакованных копий завершают механическую приёмку; живые SKILL/PROC/PREF остаются задачами существующего стенда на исправленном SHA.

Синхронизация дельт, архивирование и коммит выполняются только по соответствующему запросу. Если реализация требует несовместимой миграции вместо необязательных полей, до неё необходимо обновить этот план; автоматическое изменение старых пользовательских данных не предусмотрено.
