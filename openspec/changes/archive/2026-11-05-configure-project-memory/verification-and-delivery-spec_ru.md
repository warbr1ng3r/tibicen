# Spec Delta

## ADDED Requirements

### Requirement: Memory acceptance distinguishes structure and behavior

Свидетельства памяти SHALL разделять проверки пути и правил, наблюдаемое чтение, решения задачи и обновления в свежих сессиях. Наблюдения SHALL указывать кандидат, версии агента и инструментов, помощь, ограничения и сохранённые ошибки. Без контролируемого запуска результат SHALL оставаться unverified; инженерная приёмка SHALL NOT означать измеренную пользу людям.

#### Scenario: Setup passes but a later agent ignores memory

- **WHEN** файлы и ссылки прошли проверки, но новый агент не использовал нужное решение
- **THEN** структурный успех и поведенческая ошибка показываются отдельно
- **AND** наличие файла не даёт функции поведенческую приёмку

#### Scenario: Init and adopt are accepted on the candidate

- **WHEN** в свежих сессиях наблюдаются чтение решения после init и исправление принятого решения после adopt с сохранением остальных записей
- **THEN** наблюдения привязаны к проверенным байтам и версиям
- **AND** другие агенты, непроверенные версии и польза людям остаются вне этих наблюдений

### Requirement: Post-1.0 versions reflect compatibility

Стабильные релизы SHALL следовать SemVer: совместимые исправления повышают patch, совместимые функции — minor, несовместимые поддерживаемые интерфейсы — major. Выполненные изменения до выпуска SHALL иметь понятные записи changelog. Опубликованные версии, теги и файлы SHALL оставаться неизменными; исправление SHALL получать новую версию.

#### Scenario: Optional memory ships without breaking legacy workflows

- **WHEN** память принята с сохранением поддерживаемых прежних сценариев
- **THEN** следующий функциональный релиз готовится как `1.1.0`
- **AND** файлы и история опубликованной `1.0.0` сохраняются

#### Scenario: A repair is needed after publication

- **WHEN** готово совместимое исправление существующей стабильной линии
- **THEN** готовится новая patch-версия вместо замены файлов прежнего выпуска

### Requirement: Release metadata identifies the checked candidate

Подготовка релиза SHALL брать версию из корневого package, генерировать согласованные метаданные скиллов и checksums и привязывать CI, платформенные проверки и доставку к байтам кандидата. Предрелизы SHALL иметь соответствующую маркировку. Обычный коммит или успешный CI SHALL NOT автоматически создавать тег, публиковать релиз или разрешать новые запуски.

#### Scenario: A feature is still under development

- **WHEN** работа ещё не достигла проверенного кандидата
- **THEN** выполненные изменения описываются в `Unreleased` без заявления об опубликованной функции
- **AND** стабильная версия package меняется только при подготовке кандидата

#### Scenario: Final validation changes distributed bytes

- **WHEN** исправление меняет подготовленный дистрибутив после приёмки
- **THEN** затронутые проверки и checksums обновляются для этих байтов
- **AND** релиз не выдаёт старые наблюдения за проверку изменённого содержимого
