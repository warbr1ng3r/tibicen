# Proposal

## Why

A fresh working session read an accepted memory exception but could not reliably connect its business name to a newly requested API. That closed observation remains a functional HOLD, not proof of a core defect. Future memory policies should preserve the operation identity supplied by the owner and distinguish a scoped exception from an unresolved same-scope conflict.

## What Changes

- Clarify how the configured policy records the known subject, affected behavior and boundary of an accepted exception.
- Apply clearly matching accepted exceptions while retaining unrelated defaults; ask when identity or the active decision is genuinely unclear.
- Keep ordinary Markdown, existing write limits and current user authority; add no store, schema or runtime.
- Check correction, fresh reuse and a genuine conflict in a separate finite subscription-only observation. Preserve previous outcomes unchanged.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `project-memory`: preserve decision scope and distinguish applicable exceptions from actual contradictions.

## Impact

The shared project-memory reference, paired user documentation and Unreleased notes change. Development-only cases and observations check behavior separately from structural validity. No package version, published artifact, application runtime API or dependency changes.
