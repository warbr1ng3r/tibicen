# Дизайн (_ru)

Краткий перевод ключевых решений; канонический текст — `design.md`.

## Контекст

`applyPlan` проверяет только тождество содержимого
(`approvedDigest === digest(proposal)`) и ничего более; полный анализ акторов —
в отчёте о границе пакета. Хост не экспортирует идентичность согласующего,
поэтому любое заявление об «аутентификации согласующего» было бы ложным.
Минимальная коррекция, подтверждённая свидетельствами, — сохранить то, что
фактически произошло на гейте согласования.

## Решения

1. **Форма записи** (один объект, опциональные массивы `approvals`):
   `{ outcome: 'consumed' | 'refused', operation: 'apply' | 'resume',
   channel: 'cli --approve' | 'programmatic', approvedDigest: string | null,
   proposalDigest: string, root: string, sessionId: string | null, at: string }`.
   `approvedDigest` — предъявленное на канале значение (`null` при отсутствии);
   `proposalDigest` — digest точного компилированного плана на гейте. Для
   потреблённой записи они равны по определению гейта; для отказной их различие
   и есть детектор класса A3.
2. **Момент записи потребления**: после прохождения гейта и первого сохранения
  сессии. Сбой после этого сохранения оставляет запись с незавершённой
  сессией. Предварительный отказ до сохранения, включая устаревший план,
  не создаёт запись потребления.
3. **Момент записи отказа**: присоединяется к ошибке `consent-required` (CLI
   показывает как `error.approval`), включая идентификатор сохранённой сессии,
   если state существует, либо ID последней сессии паспорта при stateless
   resume. Новый apply без state не заимствует ID прежней сессии.
   Отказ никогда не записывает проект:
   `runtimeHooks`/`bindRunner` CLI может отказать до запуска `applyPlan`, а
   существующий инвариант требует, чтобы отказный resume оставлял сохранённый
   state байт в байт — запись журнала отказов была бы сама несогласованной
   записью `.tibicen`.
4. **Метка канала**: CLI передаёт `'cli --approve'`, библиотека по умолчанию —
   `'programmatic'`. Разрешены только эти метки. Вызывающий код контролирует
   переданную метку; она не доказывает личность или доверенное происхождение,
   а из текста исполнителя ничего не выводится.
5. **Показ**: результат `apply`/`resume`, `status`, `report` отдают `approvals`
   из живого state с откатом только к сводке с тем же ID сессии паспорта.
   Без state status выбирает последнюю сессию паспорта;
   `finalize`/`writeManifest` копируют записи в сохраняемую сводку сессии.
6. **Границы и совместимость**: не более последних 8 записей в state сессии;
   `approvals` опционально везде и проверяется (`tamper-suspect` при
   неверном свидетельстве) на границах чтения state и паспорта. State и паспорта,
   записанные до изменения, загружаются без изменений.

## Риски

- Попытка потребления добавляет время. Отказ по-прежнему сохраняет state
  побайтно; эту границу проверяют регрессии.
- Запись отказа в конверте ошибки — аддитивный JSON; потребители, проверяющие
  только `error.code`, не затронуты.
- Злонамеренный исполнитель может удалить записи вместе с любым файлом state;
   записи — сохранение свидетельств, не защищённая от подделки безопасность, а
   копия в паспорте переживает очистку state.

## Миграция

Не требуется: только опциональные поля, без подъёма версии схемы. Старые сессии
просто без записей; их resume дописывает новые.


## Integration follow-up — 20 November 2026

`core/approvals.ts` содержит общую проверку ограниченного журнала и канала.
Канал проверяется до записи. Чтение state/паспорта отклоняет неверный список,
сохранённый отказ, разные/нестроковые digest, чужой ID сессии и неподдержанный
канал. У каждой записи потребления digest равны и не null, ID совпадает с
владельцем. Последняя активная запись также совпадает с текущим корнем/digest;
прежние могут ссылаться на прошлые планы и абсолютные POSIX/Windows-корни.

Исторический паспорт не привязан к сегодняшнему пути checkout: после копирования
или переноса история читается, а stateless resume дописывает новое согласие с
текущим корнем без смены ID сессии. Прежний гейт корня/плана не меняется.
Отсутствующий журнал остаётся неизвестным legacy-свидетельством. Fallback и
status/report выбирают только совпадающий ID, не последнюю чужую сессию.
Итоговый список проверяется перед первой записью state.
