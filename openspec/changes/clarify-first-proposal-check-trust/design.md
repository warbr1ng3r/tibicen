# Design

The existing trust and readiness execution gates remain intact. Clarify the input order rather than weakening those gates: show the exact requested code/commands, include the proposed trust scope, select the real supported check profile, and set readiness only from observed environment facts. Then obtain separate external approval for that unchanged plan.

Keep the distinctions in the shared proposal reference: `trusted: true` is proposed scope, `environmentReady: true` is a caller's checked declaration, tool access is technical capability, and digest-bound external consent permits application. None authenticates the others. A self-created questionnaire or generated answer supplies no external approval.

The agent/host route can still violate instructions. Preserve the five returned consent failures, later limited functional observations and missing approval/dispatch exports. A small guidance clarification does not establish technical human authentication, universal model compliance or a fresh behavioral acceptance result. No new approval service or credential layer is introduced.
