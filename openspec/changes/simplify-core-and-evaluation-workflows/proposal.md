# Proposal

## Why

Владелец 25.10.2026 выбрал сначала упрощение архитектуры и закрытие технических долгов. Текущая проверка может пропустить исчезнувший ранее применённый файл; крупные обработчики и повторение процедур запуска затрудняют исправления, а общий путь проверок каждый раз собирает сайт.

## What Changes

- Сверять проверяемый состав с последним зарегистрированным состоянием и текущими согласованными изменениями; сообщать исчезновение и локальное расхождение без автоматического восстановления.
- Выделить одну процедуру построения состава для CLI/runtime, затем фазы применения без изменения согласия, журналов, схем и восстановления.
- Убрать повторение ограниченного запуска процессов в eval-коде; отделить выбор оснований и конкретные сценарные проверки от orchestration.
- Добавить короткие команды проверок по областям, сохранив полный общий gate, и воспроизводимый локальный вход в диагностику без платного fallback.
- Упорядочить данные матрицы и текущие статусы документации по мере работы с соответствующей областью.

## Capabilities

### New Capabilities

Нет. Рефакторинг и команды разработки не создают новую продуктовую возможность.

### Modified Capabilities

- `verification-and-delivery`: структурная проверка учитывает зарегистрированные файлы, даже если новый скан их не обнаружил; локальная диагностика и отбор оснований явно сохраняют пределы исполнения, наблюдений и самостоятельной поставки.

## Impact

`scripts/{core,verify,tibicen.ts}`, `scripts/evals/`, соответствующие тесты, команды package.json и документы разработки. Runtime остаётся без сторонних зависимостей. Версия продукта исправляется отдельно задачей 1.1 существующего `prepare-first-public-release`. Публичный выпуск, новые агенты, платные прогоны и расширение процесса на второго агента не входят в этот change.
