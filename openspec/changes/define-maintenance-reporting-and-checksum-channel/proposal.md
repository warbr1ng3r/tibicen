# Proposal

## Why

Current guides promise a general private conduct contact that has not been appointed, and leave the advisory/checksum destination undefined. The original [release requirements](../prepare-first-public-release/specs/release-process/spec.md), [tasks 3.1–3.2](../prepare-first-public-release/tasks.md) and [Vision §10.13](../../../docs/PRODUCT_VISION.md) require usable participation/security routes and an independent channel; this proposal makes their operational scope explicit without reducing the technical MVP.

## What Changes

- **Prospective policy change:** replace the later unfulfilled general private conduct-inbox promise with public issues/PRs for nonsensitive project matters, private GitHub Support reporting for GitHub platform-rule violations, and the unchanged private vulnerability route to the confirmed security maintainer. Preserve conduct protections, privacy and recusal; appoint no alternate or new recipient.
- Define an independent channel as a separately committed Pages advisory/checksum artifact, publication and HTTP origin, distinct from release attachments. State its shared GitHub administration and corresponding limits.
- Add a small static index using actual published version/source/distribution/manifest/archive bindings and append-only superseding warnings. Begin with the already published limited alpha after checking its exact records; add a future candidate only when its publication facts exist.
- Coordinate the English/Russian policy and guide wording, then verify local data and, under separate publication authorization, actual public routes/bytes. Planning, policy adoption, working-channel verification and full release acceptance remain separate facts.

## Capabilities

### New Capabilities

- maintenance-channels: concrete reporting recipients/privacy boundaries and separately published immutable advisory/checksum records. This operational capability implements the existing release-process obligations; it does not duplicate the release checklist.

### Modified Capabilities

None. The release-process capability is introduced by the active release change and is absent from main specs. Its original usable-contact, private-vulnerability and immutable-byte requirements remain intact; the new delta adds the scoped operational definition rather than modifying a nonexistent main requirement.

## Impact

Later implementation reaches CODE_OF_CONDUCT, SECURITY, CONTRIBUTING, README, RELEASING, MAINTENANCE and current status references in both languages; the existing Astro public directory, site links and focused site/data checks; and concise cross-references in the active release change. No new service, dependency, provider/account, runtime payload, version or automatic publication is proposed. Detailed release work remains in [prepare-first-public-release](../prepare-first-public-release/tasks.md); monthly/source-change reviews, full technical evidence, immutable delivery and explicit publication permission remain required.

This is an unapplied planning proposal. The current private-conduct promise and channel gap remain open until the relevant policy is adopted and actual working routes/publication are verified. The earlier limited alpha and all failed observations retain their original scope.
