# Design

## Context

The 1.4 release already has public delivery and offline/platform evidence. Latest recommendation observations are read-only and assisted. This packet tests the next workflow stages without relabeling those old records. Frozen standalone files match all 100 published payload hashes. The full local roadmap is retained privately; publishable history comes from the existing curated public tree.

## Goals / Non-Goals

**Goals:** five ordinary-request cases; exact recommendation/proposal evidence; separately attributed mechanical application and fresh working tasks where applicable; retained preservation/effort counts; minimum confirmed fixes; current roadmap.

**Non-Goals:** native-host/model comparison, human usefulness, personal settings, paid APIs, new runtime/backend/dependency, blanket compatibility or a release.

## Decisions

1. Use fresh internal subagents and explicit complete skill reading. Host names are supplied context, not native observations. No external model/CLI is launched. Initial lane actors may author fixtures; this unblinded assistance is disclosed, not a benchmark.
2. Fix five scenarios before operator execution: I1 initial instructions; A1 obsolete command with retained useful rules; M1 explicit memory correction; C1 enabled/disabled local MCP diagnosis; N1 sufficient/no-change setup. Actual inputs/bytes are retained privately; synthesized requests are not external-user transcripts.
3. Recommendation agents stop before apply and never approve their own digest. Root separately reviews each exact proposal and owned fixture. A development contract-test driver may supply a **simulated approval token** to the frozen API with explicit owned HOME; this proves mechanical effects only, not user consent or a normal unassisted user run. No product refusal is bypassed. Original proposals, revisions and all started attempts remain retained.
4. Application checks follow the fixture's actual profile/trust. Unsupported pure Node-module profiles stay unverified in product reports. Root may separately run inspected builtin-only tests as development oracles; this assistance never becomes a product/native success. No MCP server or arbitrary application dependency is launched.
5. A fresh task actor receives only its prepared fixture, ordinary request and explicit project-instruction path. The task may change only named fixture app/test files. It does not read oracle/earlier responses. Root keeps independent expected outputs outside the actor inputs, checks app behavior and infrastructure preservation afterward, and records read/use separately. Memory has a later correction/read check, preserving unrelated notes.
6. At most one original execution and one separately identified corrective attempt per phase/case; preserve failures and describe why a later rerun was allowed. CLI reads/errors/retries/questions and manual/operator actions are distinct counters; no comparative time-savings claim. C1/N1 may correctly finish without apply or an app task.
7. Concrete defects get exact reproduction, expected existing contract and a small regression before a minimal correction. If no defect is established, keep runtime unchanged. New behavior outside current contracts requires revised requirements/scenarios before implementation.
8. EN is canonical, RU adjacent. Publish summaries only; fixtures, full reads, absolute paths and raw transcripts stay private. Roadmap preserves current facts and milestone order; historical states remain clearly dated, with only link rebasing when relocated.

## Reproduced preview correction

The frozen A1/M1 proposals replace one line but mark the entire instruction/memory file as deleted/added. Use linear common-prefix/suffix trimming with three context lines and one combined hunk; retain line-ending state and complete proposal content. No dependency, native Git invocation or general diff engine. Existing apply consumes exact content and hashes, not the display diff.

## Risks / Trade-offs

Assisted small fixtures cannot establish real-user value or universal loading. Mechanical apply and working-task success are separately attributed. Existing supported-profile limits may remain even after a useful task passes. No pre-start skip is counted as completed execution, no removed failure and no human/native grade is invented.
