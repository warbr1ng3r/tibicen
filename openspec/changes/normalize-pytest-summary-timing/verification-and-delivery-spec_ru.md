# Изменение требований: проверка и поставка

Основная версия — [specs/verification-and-delivery/spec.md](specs/verification-and-delivery/spec.md). Перевод находится в корне change и не является вторым входом для OpenSpec.

## MODIFIED Requirements

Дополнительный сценарий интеграционного ревью: при переходе длительности через
границу разрядов, минуты или суток меняющаяся рамка pytest нормализуется вместе
с длительностью. Игнорируются только часы timedelta; произвольные сообщения
в скобках остаются значимыми различиями. Канонический сценарий — в
[English spec](specs/verification-and-delivery/spec.md).

### Requirement: Project verification covers every approved command
Проверка проекта SHALL сообщать сопоставимый результат только после полного выполнения одного и того же одобренного набора команд в соответствующих исходном и итоговом деревьях. Частичное выполнение, отсутствие доверия, изменение источника команды или неизвестный исход SHALL сохраняться как `unverified` с причиной. Сравнение провальных прогонов SHALL допускать изменчивую длительность в распознаваемых временных записях раннера, сохраняя значимые различия ошибок.

#### Scenario: Both runs stop after the same successful prefix
- **WHEN** первая команда проходит в обоих деревьях, но вторую нельзя исполнить, потому что её проверенный скрипт изменился
- **THEN** результат остаётся `unverified`, даже если записи первой команды совпадают
- **AND** отчёт не заявляет отсутствие регрессий всего одобренного набора команд

#### Scenario: Trust or command outcome prevents completion
- **WHEN** команде не хватает доверия или её предыдущий исход неизвестен
- **THEN** неполное выполнение не становится `green`, `red-fixed` или `pre-existing-red`
- **AND** причина и ранее известные регрессии сохраняются независимо от статуса передачи

#### Scenario: A complete comparison is available
- **WHEN** все одобренные команды завершены и сопоставимы
- **THEN** сохраняется различие между зелёными результатами, существующими ошибками, исправлениями и новыми регрессиями
- **AND** новому проекту не нужен выдуманный baseline, но требуется полный итоговый набор команд

#### Scenario: Identical failures differ only in recognized runner timing records
- **WHEN** сопоставимые провальные прогоны имеют одинаковый ненулевой код выхода и различаются только временной записью Node spec/TAP, полной сводкой времени Python unittest или полной обрамлённой строкой сводки pytest (`=+ <счётчики или «no tests ran»> in Ts =+`)
- **THEN** сравнение сообщает `pre-existing-red`, а не новую регрессию
- **AND** имена тестов, значения утверждений и счётчики тестов остаются частью сравниваемого вывода

#### Scenario: Duration-shaped data changes the failure
- **WHEN** ошибка меняет утверждаемое значение, имя теста, счётчики сводки или обычную фразу журнала с `(1s)` на `(5s)`, либо меняет постороннее поле `duration_ms` или неоформленную фразу `in Ts`
- **THEN** значимое различие остаётся `changed-failure`
- **AND** неподдержанные форматы вывода сохраняют строгое сравнение

#### Scenario: The failure exit code changes
- **WHEN** сопоставимые прогоны имеют идентичный нормализованный вывод, но разные ненулевые коды выхода
- **THEN** сравнение сообщает `changed-failure`, а не `pre-existing-red`
