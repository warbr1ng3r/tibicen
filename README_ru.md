Tibicen помогает настроить агентскую инфраструктуру нового проекта или привести существующую в порядок. Он работает внутри привычного агента: исследует проект, предлагает одну подходящую настройку, показывает изменения, применяет согласованное и отдельно сообщает результаты проверок.

Два входа:

- `tibicen-init` — «Настрой агентскую инфраструктуру». Для пустой папки и существующего приложения без настройки.
- `tibicen-adopt` — «Проверь и обнови агентскую инфраструктуру». Для исправления, дополнения и обновления уже имеющихся инструкций и подключений.

Исходники приложения, существующие пакетные манифесты, CI и данные при внедрении сохраняются. До согласия нет записи, установки или запуска проектного кода. Tibicen не создаёт коммиты, включая временные репозитории и проверки. После работы остаются инструкции и паспорт `.tibicen/manifest.yml`; постоянного процесса Tibicen в проекте нет.

[**1.5.1 опубликован**](https://github.com/warbr1ng3r/tibicen/releases/tag/v1.5.1): понятное согласование служебных записей и сохранение прав файлов в стенде разработки. Точное согласие на CLI-план остаётся обязательным; схемы и выбранная память не меняются. [Проверки и ограничения выпуска](docs/evals/results/2026-11-07-release-1.5.1/README.md) отделяют явное чтение скилла и помощь оператора от автоматической загрузки и измеренной пользы человеку. Метаданные Pages проверяются отдельно.

Предыдущий выпуск (историческая запись): [**1.5.0 опубликован**](https://github.com/warbr1ng3r/tibicen/releases/tag/v1.5.0):
проверка явно выбранных инструкций, пересмотр изменившихся источников запомненных
фактов и объяснение влияния переданных upstream-рекомендаций на локальное решение.
Необязательные дополнения отчёта сохраняют согласия и выбранную память;
фонового обновления нет. Точная публичная установка, обновление/восстановление/
удаление и три свежих наблюдения с помощью прошли в
[границах отчёта выпуска](docs/evals/results/2026-11-07-release-1.5/README.md).
Автоматическая нативная загрузка, активация MCP и общая совместимость моделей
не подтверждены; модель и провайдер остаются вашим выбором.
Память проекта появилась в 1.1.0; её [сопровождаемые свежие задачи](docs/evals/results/2026-11-04-project-memory/README.md)
сохраняют исходный охват. Прежние выпуски сохранены в [CHANGELOG](CHANGELOG.md).

Встроенной инициализации агента или прямой просьбы проверить существующие инструкции тоже может быть достаточно. Сравнительная экономия усилий и человеческая полезность Tibicen не измерены.

## Установка Tibicen

Команда ниже закрепляет поставку 1.5.1 полным коммитом.
[Отчёт выпуска](docs/evals/results/2026-11-07-release-1.5.1/README.md) фиксирует точные
проверки, сохранённые прежние неудачи и границы свидетельств точного кандидата.
Публикация и публичная поставка — в [сведениях о выпуске](docs/RELEASING.md).
Ветка исходников не является целью установки.

Установка использует отдельную собранную поставку. Проверены точные файлы,
доступ к версии/ресурсам, явная замена, восстановление резервной копии и удаление.
Нативная загрузка проверяется отдельно и не гарантируется установщиком.
Явная цель `universal` помещает оба полных скилла в `~/.agents/skills/`;
хост, модель и провайдер не обязаны присутствовать в каталоге Tibicen.

```sh
npx skills@1.7.4 add https://github.com/warbr1ng3r/tibicen/tree/287ef7b22630482aca7996e5a0faad601cede778 -g --agent universal --skill tibicen-init tibicen-adopt --copy
```

Для точной фиксации коммита используйте полный SHA поставки из release notes. Не устанавливайте скиллы из основной ветки исходников: в ней есть инструменты разработки. Для Git-маршрута установщика нужны Node и Git, зависимости репозитория и сборка сайта не требуются.

Откройте сессию проекта в привычном агенте с доступом к файлам и попросите:

> Прочитай `~/.agents/skills/tibicen-init/SKILL.md` и следуй его инструкциям. Настрой агентскую инфраструктуру этого проекта с минимумом процесса. До применения покажи точный план.

Для существующей инфраструктуры используйте `~/.agents/skills/tibicen-adopt/SKILL.md`
и попросите проверить и улучшить настройку. Замените `~` фактическим домашним путём,
если хосту нужен абсолютный путь. Явное чтение доступно без нативного обнаружения
скиллов; оно не доказывает автоматическую загрузку или поведение в другой сессии.
См. [установку и полное ручное восстановление папок](docs/INSTALLATION.md)
и [работу с разными хостами и моделями](docs/HARNESS_PORTABILITY.md).

## Сборка и установка из исходников

Для сборки и работы скиллов нужен Node ≥22.20 и хост, способный читать файлы проекта и выполнять необходимые локальные операции. Модель и провайдер настраиваются в этом хосте; Tibicen не добавляет клиента провайдера, требования учётных данных или списка разрешённых моделей. Зависимости и сборка сайта для установки скиллов не нужны. Для доставки установщиком нужен Git; установленный Tibicen может работать без Git через временную копию проекта.

Исполнение команд контролирует группу процессов на POSIX и останавливает потомков при тайм-ауте или отмене, с запасом до одной секунды на принудительное завершение. На Windows исполнение пока возвращает `process-tree-unavailable` до запуска команды; операции чтения доступны. Standalone-проверки прошли на [macOS, Ubuntu и Windows для записанного снимка рабочих исходников](docs/evals/results/2026-10-30-platform-checks/README.md). Эти проверки не подтверждают охват финального кандидата или native-агентов.

Из папки с исходниками Tibicen сначала соберите скиллы:

```sh
node scripts/build.ts
```

Затем запустите **одну** команду подходящим менеджером пакетов:

```sh
# npm
npx skills@1.7.4 add ./dist -g --agent universal --skill tibicen-init tibicen-adopt --copy

# pnpm
pnpm dlx skills@1.7.4 add ./dist -g --agent universal --skill tibicen-init tibicen-adopt --copy

# Yarn 2+
yarn dlx skills@1.7.4 add ./dist -g --agent universal --skill tibicen-init tibicen-adopt --copy
```

Yarn Classic 1.x не имеет `dlx`; используйте `npx`. Это выбор способа запуска установщика: менеджер пакетов и зависимости целевого проекта не меняются.

Сохраняйте явный `--agent universal`: без него установщик может выбрать несколько целей. `--copy` создаёт независимую копию; `-g` устанавливает в user-scope разработчика. Прежние наблюдения доставки через npm/pnpm/Yarn использовали именованные нативные цели и сохраняют этот охват в отчётах; универсальное нативное обнаружение они не доказывают. Полные папки и их ресурсы должны оставаться вместе.

Используйте явный запрос чтения `SKILL.md` выше с установленным расположением. Можно попросить «всё по умолчанию»: это убирает вопросы интервью, но итоговый план всё равно требует согласия.

`dist/` — дерево дистрибутива с двумя самостоятельными скиллами и `SHA256SUMS`. Каждый содержит собственные копии общих ресурсов, автоматически собранные из единственного исходника. Опубликованная distribution-ветка и версионные tags содержат это собранное дерево. Установка из корня несобранных исходников не поддерживается.

### Обновление или удаление установки

Замена установленного Tibicen и обновление инфраструктуры проекта — отдельные действия. Замена скиллов не запускает adopt в проектах автоматически.

Перед переустановкой сохраните локально изменённые каталоги скиллов в безопасном месте вне установки. Повторный `add --copy` в skills 1.7.4 заменяет весь выбранный каталог, включая дополнительные файлы; локальные правки не объединяются. Перед переносом полезных изменений сравните резервную копию с новой версией. Храните правила проекта и пресеты вне каталогов установленных скиллов Tibicen.

Для установки из локального пути `skills update` не проверяет источник автоматически. Проверив новую сборку и сохранив правки, явно повторите выбранный закреплённый `add`. Установка из Git по SHA или tag тоже остаётся на этой ссылке: `skills update` не выбирает следующий релиз Tibicen. Для обновления сохраните правки и повторите `add` с явным URL нового выпуска. Resume проекта — отдельная согласуемая операция Tibicen. Приёмка конкретного кандидата описана в release notes.

Удаление обоих скиллов из общего user-scope:

```sh
pnpm dlx skills@1.7.4 remove tibicen-init tibicen-adopt -g --agent universal -y
```

Удаляются каталоги скиллов и находящиеся внутри файлы. Прежние локальные macOS-наблюдения для именованных нативных целей сохранили файлы проектов, `.tibicen` manifest/state, пресеты и конфигурацию агента вне этих каталогов; эти наблюдения сохраняют исходный охват целей. Пустые родительские каталоги и lock-файл установщика могут остаться. Удаление не отменяет согласованную настройку проекта; изменения проекта рассматривайте отдельно. Точный охват описан в [свидетельствах доставки](docs/evals/results/2026-10-27-candidate-delivery/README.md).

## Работа с проектом

1. Агент исследует фактические файлы, команды, ограничения и доступные источники.
2. Предлагает достаточную конфигурацию. Дополнительный скилл или MCP появляется при понятной пользе; отсутствие лишних компонентов — нормальный результат.
3. Показывает точные пути, изменения, источники/SHA, команды, env-имена, доверие к коду, стоимость и ручные шаги. Данные предложения находятся в памяти/stdin до согласия.
4. После согласия применяет только показанный план. Изменение затрагиваемого файла другим процессом останавливает запись.
5. Передаёт результат, ограничения и первый полезный запрос. Паспорт сохраняет происхождение, изменения и историю исходной сессии.

Начиная с 1.2.0 adopt объясняет исходную настройку, конкретную находку, что
оставить или изменить, выполненные проверки и один следующий шаг. Существующий
отчёт включает свежую диагностику только для чтения рядом с сохранёнными
результатами сессии. См. [четыре простых примера](docs/ADOPT_DIAGNOSIS.md).
Переданные версии агентов остаются контекстом; датированное содержимое источника
само по себе не доказывает применимость или загрузку.

`complete` означает завершение подключения без известного обязательного дефекта; проверки проекта и поведения имеют независимые результаты. `manual-action-required` означает оставшиеся обязательные внешние действия. При внутреннем сбое или неисправленном обязательном дефекте — `incomplete`; состояние и исходные версии затрагиваемых файлов сохраняются для продолжения с новым согласием.

Одного согласованного `AGENTS.md`, явно читаемого каждым выбранным хостом, может
хватить для нескольких инструментов и выбранных пользователем моделей.
Обязательное чтение или активация, которые ещё не состоялись, сохраняют
`manual-action-required`. Нативные общие копии требуют отдельно поддержанного
запроса; недоступные автоматические пробы задач/квизов/загрузки остаются
`unverified`, не блокируя доступную настройку. Хосты только для чтения или без Node
получают конкретную недоступную операцию и локальный/ручной следующий шаг,
а не выдуманный скан или завершённое применение.

Контекст задачи и диагностика MCP доступны в 1.4.0; прежние поставки сохраняют опубликованные байты.

## Возможности и пределы проверки

- Сканирование, изменение согласованных агентских файлов, добавление/замена/удаление, повторная проверка и продолжение сессии.
- Живой подбор из GitHub API: каноническое происхождение, полный SHA, лицензия, возраст, архивность, install-хуки, блоклист и эвристическая проверка инъекций. Число контрибьюторов не используется.
- Свежие официальные рекомендации выбранных агентов: источники, даты, структурные выдержки и gaps. Применимость оценивает агент; дата загрузки сама по себе не доказывает качество рекомендации.
- MCP stdio: точечные изменения JSON Claude/Cursor с сохранением остальных записей; для Codex — ручной TOML-блок. Значения секретов не запрашиваются; известны только env-имена. Наличие env у Tibicen не подтверждает окружение другого уже запущенного агента.
- Проверка структуры инфраструктуры для разных стеков. Build/test/lint — web-профиль, только согласованные команды на контролируемых копиях с воспроизводимым окружением. Если окружение не подтверждено, результат — `unverified`, а не ложный зелёный прогон.
- Контролируемая типичная задача, квиз и native compat имеют условный путь исполнения для проверенной версии Claude Code. Для других агентов либо отсутствия авторизации, доверия, контролируемого startup и наблюдаемого результата — `unverified` с причиной. Exit code и список обнаруженных скиллов не доказывают загрузку инструкций.
- Восстановление baseline из другого процесса не подменяется новым исходным состоянием: `baseline-unavailable`. Известные регрессии и история попыток сохраняются.
- Сохранение личного пресета и файла отчёта выполняется по отдельному явному запросу. Конструктор в `landing/` скачивает пресет в браузере без сервера и отправки ответов.

Собственные YAML-файлы записываются как JSON, совместимый с YAML. Поддерживается только это строго проверяемое подмножество: произвольный YAML, теги и исполняемые выражения не разбираются. Чужие неоднозначные конфиги требуют ручного шага.

Проверенные версии и условия запуска: [матрица агентов](references/agent-matrix.md). Техническая приёмка релиза сохраняет полную функциональность MVP, строгие инварианты, функциональное качество, положительные наблюдения загрузки и использования скиллов/процесса, доставку/обновление/восстановление точного кандидата, заявленный охват и готовность сопровождения. Нужны наблюдения с привязкой к кандидату и независимое инженерное ревью; см. [инженерную оценку](docs/evals/ENGINEERING_ACCEPTANCE.md) и [реестр готовности](docs/evals/V1_READINESS.md). Добровольные человеческие наблюдения полезности и калибровка рубрики вынесены в отдельную работу после публикации; локальные проверки и инженерное ревью не доказывают измеренную пользовательскую пользу.

## Команды для разработки

Для разработки всего репозитория используйте Node 24 LTS и pnpm 11.21.0 (версия закреплена в `packageManager`). Workspace задан в `pnpm-workspace.yaml`, зависимости — в едином `pnpm-lock.yaml`. Включите pnpm через Corepack (`corepack enable pnpm`) либо установите указанную версию pnpm самостоятельно. Примеры npm/Yarn выше относятся только к установщику скиллов.

```sh
pnpm install --frozen-lockfile
pnpm lint
pnpm format:check
pnpm typecheck
pnpm test
pnpm build
pnpm eval:diagnostic --help
pnpm eval:external --help
node scripts/tibicen.ts self-test
node scripts/tibicen.ts help
```

Во время правок используйте проверки нужной области; перед интеграцией запускайте `pnpm test`.

| Команда               | Область                                                                         |
| --------------------- | ------------------------------------------------------------------------------- |
| `pnpm typecheck:core` | Корневой TypeScript и тесты, включая evals, без проверок Astro                  |
| `pnpm test:core`      | Продуктовый цикл, адаптеры, проверки и самостоятельные скиллы; без сборки сайта |
| `pnpm test:evals`     | Офлайн-стенд и подставные драйверы; без сборки сайта и вызовов моделей          |
| `pnpm test:site:unit` | Сборка сайта и Node-тесты структуры страницы и клиентской логики                |
| `pnpm test:site`      | Сборка сайта и браузерные тесты Chromium, Firefox и WebKit                      |

Полный `pnpm test` сохраняет lint, форматирование, все проверки типов, сборку сайта, строгую валидацию OpenSpec и все Node-тесты. Браузерные проверки по-прежнему запускаются отдельно через `pnpm test:site`.

[Офлайн-CI](docs/CI.md) выполняет полный gate, сборку, проверку сумм и self-test распакованных поставок без авторизации моделей. Зафиксированный исходник 1.2 прошёл [GitHub Actions на Ubuntu](https://github.com/warbr1ng3r/tibicen/actions/runs/41957289753); полный офлайн-прогон прошёл 804 теста без пропусков. Точный кандидат и повторно используемые платформенные привязки — в [отчёте выпуска](docs/evals/results/2026-11-05-release-1.2/README.md).

Команда `pnpm eval:diagnostic` даёт документированный [вход в диагностику](docs/evals/EXTERNAL_RUNS.md): по умолчанию dry-run, либо офлайн-калибровка с fake driver. Native-запуск требует явно заданного поддержанного контракта; неподдержанный маршрут сохраняется как blocked.

ESLint проверяет TypeScript, JavaScript и Astro рекомендованными правилами. Prettier форматирует код и конфигурацию с отступом в два пробела и одинарными кавычками. `pnpm lint:fix` применяет автоматические исправления линтера, `pnpm format` — форматирование; обе проверки стиля входят в `pnpm test`. Замороженные фикстуры, копии внешних исходников, сохранённые свидетельства и документация исключены из форматирования.

Сборка использует обычный каталог `dist/`. Произвольное назначение допустимо внутри `dist/` или вне репозитория, без пересечения с исходным деревом. Каталог назначения, оба дерева скиллов и `SHA256SUMS` проверяются на опасные пути и симлинки до любой очистки.

Исходники и тесты написаны на TypeScript со строгой проверкой типов. CLI выполняется непосредственно Node ≥22.20. Для разработки и сборки лендинга нужен Node ≥22.23.4; TypeScript, Astro и инструменты проверки типов остаются зависимостями разработки и сайта. Runtime-зависимостей нет. `scripts/tibicen.ts` выдаёт структурированный JSON. Исследование и предложение ничего не сохраняют; готовое предложение и его digest передаются через stdin. `--approve` — средство связать фактическое согласие человека с конкретным планом, а не разрешение скрипту или агенту самостоятельно подтвердить ввод.

Основные команды: `scan`, `discover`, `practices`, `proposal`, `apply`, `resume`, `status`, `verify`, `report`, `preset-load`, `preset-save`. `verify` отдельно выполняет только структурную проверку. Исполняемые проверки задаются в согласованном предложении. Формат ввода и пример: [proposal-format.md](references/proposal-format.md). Команды только для чтения `harnesses` и `mcp-diagnose` доступны в 1.4.0; см. [руководство профилей](docs/HARNESS_CAPABILITIES.md).

Лендинг — отдельный Astro workspace в `landing/`, с адаптированными секциями AstroWind, Tailwind CSS, клиентскими скриптами TypeScript и локальными ресурсами. Происхождение секций и MIT-уведомление описаны в [landing/README.md](landing/README.md). Зависимости всех частей устанавливаются одним `pnpm install --frozen-lockfile` из корня. Запуск с обновлением при правках — `pnpm dev:site` (http://127.0.0.1:8371/). Сборка — `pnpm build:site`, просмотр сборки — `pnpm preview:site`. Статический результат в игнорируемой папке `landing/dist/` можно разместить на обычном статическом хостинге; сервер приложения и внешние ресурсы для работы страницы не нужны. Лендинг и его зависимости не попадают в устанавливаемые скиллы.

## OpenSpec для разработки

OpenSpec 1.14.3 закреплён в devDependencies. `pnpm openspec list` показывает изменения, `pnpm spec:check` проверяет требования и завершённость архивных задач; проверка входит в `pnpm test`. Скиллы разработки Codex находятся в `.agents/skills/`. Для отключения служебной телеметрии CLI задайте `OPENSPEC_TELEMETRY=0` в окружении процесса.

Продуктовое видение задаёт назначение и MVP, план — порядок этапов, OpenSpec — подробные требования и задачи конкретного изменения. Существенное новое поведение проходит через change; мелкие текстовые и CSS-правки выполняются напрямую. OpenSpec и его dev-зависимости не включаются в устанавливаемые скиллы Tibicen.

Внешние эксперименты имеют отдельный явный вход: [контракт исполнения и текущие ограничения](docs/evals/EXTERNAL_RUNS.md). Команда загружает только доверенный локальный host driver, выбранный явным `run`; обычные тесты остаются офлайн. Native-профилям агентов нужны проверенные границы дерева процессов и собственный наблюдаемый preflight; текущие production-маршруты отказывают до появления такой границы. См. [ограничения native runner](docs/evals/NATIVE_RUNS.md).

Стенд разработки включает [замороженную матрицу из 67 случаев](docs/evals/MATRIX.md), закреплённые материалы Ponytail/Spec Kit и наблюдённые эффекты пакета OpenSpec. [Контролируемая диагностика Codex](docs/evals/CODEX_DIAGNOSTIC.md) использует отдельно проверенный подписочный профиль; первые диагностические прогоны не подтверждают полную приёмку скиллов/процесса или пользу релиза.

Два исходных этапа документированы ретроспективно 2026-10-22: архивы содержат исходные SHA до переписывания истории и свидетельства проверок, выполненных в ту дату. Это не утверждение, что OpenSpec применялся тогда или что были выполнены живые агентские испытания.
