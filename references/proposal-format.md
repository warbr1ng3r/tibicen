# Ввод предложения · schema 1

Чтение и сериализация собственных JSON-документов ограничены 8 МиБ в UTF-8. Совокупный state включает план, исходники и историю; если его начальная сериализация не помещается, применение отказывает до изменений. При последующем превышении прежний читаемый state/паспорт не заменяется. История не удаляется автоматически; слишком большой документ прежней версии требует отдельного ручного разбора.

Опциональный вход process и его точные границы описаны в [адаптере OpenSpec](process-openspec.md). Входные поля framework/version/agent/agentVersion выбирают поддержанную конфигурацию; cliPackageRoot явно указывает отдельно установленный пакет, instructions: preserve/replace — решение для локальной инструкции. Скрипт возвращает process/schema 1 с хэшами и режимом сохранения, включает его в digest, паспорт и историю. Этот объект не является согласием или свидетельством загрузки CLI/агентом.

Команда `proposal` принимает JSON, дополняет его фактическими исходными хэшами и полным диффом, затем возвращает `{ proposal, digest, summary }`. Пример первоначальной настройки без сторонних компонентов:

```json
{
  "mode": "init",
  "changes": [
    {
      "path": "AGENTS.md",
      "action": "add",
      "content": "# Работа с проектом\n\nСначала изучи фактическую структуру и задачу пользователя.\n",
      "reason": "Единая точка входа с короткими инструкциями проекта"
    }
  ],
  "commands": [],
  "sources": [],
  "forbiddenPaths": [],
  "manualActions": [],
  "assumptions": [],
  "gaps": [],
  "checks": {},
  "compat": { "enabled": true },
  "practices": []
}
```

Для улучшения `mode: improve`. Каждое изменение задаёт `path`, `action` (`add`, `modify`, `delete`) и причину; `content` нужен для добавления и изменения, для удаления отсутствует. Пути относительны проекту. Содержимое должно соответствовать фактам конкретного проекта: пример не является обязательным шаблоном инструкций. Не добавляй собственные `.tibicen/`-файлы в `changes` — паспорт и state ведёт скрипт.

`forbiddenPaths` ограничивает чтение и запись ресурсов проекта в операциях, которым передано это поле. Обязательные внутренние операции с паспортом и state выполняются отдельно и показаны в `serviceWrites`; это поле не является общим запретом доступа ко всей файловой системе. Если пользователь запрещает эти внутренние пути, остановись до вызова Tibicen и укажи gap. Чтобы сохранить доступный для чтения файл без изменений, оставь его вне `changes` и проверь итоговый дифф; это не основание добавлять его в `forbiddenPaths`. Если явный запрет пользователя закрывает ресурс, необходимый адаптеру, сохрани запрет и укажи gap.

Сторонний источник: `repo`, полный `sha`, `license`, `skillPath` и проверенные основания. Для скилла `files` содержит `{path, sourcePath, contentHash, fileMode?}`: целевой относительный путь, путь в исходном репозитории, SHA-256 содержимого и обычные права исходника. Поиск возвращает `fileMode` из Git `100644`/`100755`; исполняемый файл требует явного `493` (`0755`), обычный — `420` (`0644`). Старое отсутствие режима поддержано для обычного upstream-файла, но не подтверждает исполняемость. Скрипт после согласия заново проверит источник, права и получит эти файлы на SHA. Неизменённый уже установленный файл тоже можно включить для повторной проверки происхождения. Для MCP-источника укажи `kind: mcp`; запись источника не означает установки кода сервера. Если компонент ещё не получен, не помечай его установленным. Исключение неизвестной лицензии требует `license: unknown` и `licenseException: {reason}` с явным согласованием; остальные гейты сохраняются.

`changes[].fileMode` — необязательное целое число обычных битов `0..511` (в JSON десятичное); специальные биты запрещены. Для собственного текста отсутствие поля сохраняет права существующего файла, для нового даёт `384` (`0600`). Скомпилированный план показывает `beforeMode` и итоговый `fileMode`, включая правку одних прав при совпавшем содержимом; они входят в digest и повторную проверку перед записью. Для замены источника итог соответствует проверенным upstream-правам; явные preserve/merge сохраняют отдельно показанные локальные решения. Паспорт различает исходный `fileMode` и фактический `installedMode`, журнал — известные `beforeMode/afterMode`. Прежние схемы остаются читаемыми без выдумывания отсутствующих данных; state/паспорт/счётчик записываются с `0600`.

Свежие официальные сведения получает `practices --agents codex,cursor,claude-code`; выбери только нужных агентов. В `practices` переноси фактически проверенные источники, дату и область применимости. При недоступности источника укажи gap, а не свежую проверку.

Команда: `id`, `kind` (`build`, `test`, `lint`, `install`, `git-init`, `task`, `quiz`, `compat`), `executable`, массив буквальных `argv`, относительный `cwd`, массив `envNames`. `trusted: true` допустим только после явного доверия показанному коду. Не включай значения env, shell, динамический `npx`, inline-код, коммиты или публикацию. Для установки требуется `--ignore-scripts`; `git-init` разрешает только `git init`.

Ручной шаг: `id`, понятное `description`, `status: pending` или подтверждённое `done`. Будущий шаг не отмечай выполненным. Неподтверждённые проверки оставляй `unverified` с причиной; `checks.profile: web` и `checks.environmentReady: true` допустимы только при фактически подготовленном подходящем окружении.

Поля служебных записей, существенный состав запусков и точные диффы возвращённого proposal тоже входят в согласуемый объём. На применение передавай неизменённый возвращённый proposal либо весь envelope и его digest; поля `approved`, `approval` и `approvedDigest` внутри данных не являются согласием.

## Предпочтения и основания

Поле `assumptions` уже входит в digest плана, показывается в `summary.assumptions`, а после согласованного применения — в паспорте и `report.assumptions`. При незавершённой сессии report показывает допущения её текущего плана; без сохранённого плана/паспорта — пустой список. Просмотр не сохраняет новый профиль пользователя и не пишет проект.

Для выведенного предпочтения рекомендуемый формат — id, preference, status `inferred` и basis с источником, ссылкой и коротким наблюдением. Это соглашение о содержимом, не новая обязательная схема: прежние строки и JSON-объекты остаются допустимыми. Условный пример ниже используй только при фактически прочитанном основании; не выдумывай номер строки или историю:

```json
{
  "assumptions": [{
    "id": "response-detail",
    "preference": "concise-answers",
    "status": "inferred",
    "basis": [{
      "source": "project-instructions",
      "reference": "AGENTS.md:4",
      "observation": "Инструкции проекта требуют коротких ответов с необходимыми условиями"
    }]
  }]
}
```

Основания могут быть из доступного диалога, материалов/инструкций проекта или выбранного пресета. Явное решение человека — подтверждённый факт, а не догадка; при отражении в этом поле допустим status `user-confirmed` с действительным основанием. Для каждого компонента объясняй пользу относительно существующей настройки; если её достаточно, обоснуй сохранение. Отсутствие признаков не является основанием выдумать предпочтение. Исправление допущения меняет digest; поля вроде `approved` внутри данных ничего не подтверждают. Строгая схема пресетов и обычные гейты установки/исполнения сохраняются.

## Обновление компонента и паспорт

Для новой установки используй `sources` и точные `changes`. При выборе новой редакции уже установленного компонента используй `componentUpdates: [{source, decisions}]`. `source` имеет тот же формат, что элемент `sources`, и перечисляет весь выбранный новый состав; повторять его в `sources` не нужно. Компонент сопоставляется по `repo` и `skillPath`, включая оставшиеся ресурсы его прежних редакций. Скрипт сравнит прежний паспорт, текущие файлы и новый состав.

`decisions` — массив `{path, resolution, reason}`. Для каждого локально изменённого файла явно выбери `preserve`, `merge` или `replace`. Для каждого прежнего файла, отсутствующего в новом составе, выбери `preserve` или `remove`: исчезновение upstream не является разрешением удалить ресурс. Для чистого файла замена допустима без отдельного override. Выбранные итоговые байты для `replace`/`merge` и удаления для `remove` всё равно должны быть показаны в обычных `changes`; скрипт проверит соответствие решения операции и исходным хэшам. `merge` означает уже подготовленное объединённое содержимое и дифф, не скрытый автоматический merge. `preserve` не допускает изменения байтов или ложного сохранения отсутствующего выбранного ресурса: такой файл нужно восстановить либо явно исключить из нового состава.

Пример решения: `{"path":".agents/skills/example/SKILL.md","resolution":"preserve","reason":"Сохранить согласованное локальное ограничение"}`. Новый ресурс, занимающий существующий чужой путь, даёт `component-path-conflict`, даже при совпадении содержимого. Соседние пользовательские файлы не включаются в состав по расположению; разрешение конфликта требует отдельного точного плана.

Возвращённые `proposal.components` и `summary.components` показывают исходный паспорт, версии схем и для каждого пути — прежнее происхождение, фактический исходный хэш, новый источник/хэш, итоговый локальный хэш, решение и причину. Этот результат, включая миграцию, входит в digest; не составляй готовый inventory вручную. При применении скрипт заново сверяет план с паспортом и файлами, проверяет выбранные источники на SHA. До согласия паспорт, state и счётчик не записываются.

Паспорт schema 2 хранит `contentHash` исходного файла поставки отдельно от `installedHash` фактического файла. Сохранённая или объединённая локальная версия остаётся связанной с источником, но не обозначается точной копией SHA. Полезный ресурс, исчезнувший upstream и сохранённый в проекте, остаётся связан со своей прежней поставкой. Удалённое исключается из установленного состава; прежние записи и решения сохраняются в истории сессий. Метка `provenance-verified` подтверждает проверенный источник, а не равенство локальных байтов upstream; миграция не присваивает эту метку старым неподтверждённым данным.

Для schema 1 требуется явный ввод `migrateManifest: true`: предложение показывает переход 1 → 2 и фактические хэши, применение требует согласия на его digest. Неизвестная или неполная схема даёт отказ до записи. Паспорт остаётся schema 2; новые сессии используют state schema 3 с исходным паспортом, исходными байтами и журналами записи/исполнения. State schema 1/2, неизвестный формат и старый готовый proposal автоматически не преобразуются и требуют отдельного разбора/миграции без удаления истории.

## Восстановление после прерывания

`status` и `report` читают сохранённую сессию без записи и возвращают `recovery`: для каждого пути сравниваются исходный хэш, согласованный итог и фактический файл, включая отсутствие. `pending` означает исходное состояние; `matches-approved-result` — итог уже присутствует и при продолжении того же плана не записывается повторно; `ambiguous` требует разбора. Совпадение результата не доказывает автора записи: в записи применения оно имеет `evidence: matches-approved-result`, если подтверждённой записи Tibicen в журнале нет. Неожиданные байты не затираются; для исправления нужен новый точный план с фактическим исходным хэшем и новое согласие.

`report.applied` перечисляет известные применённые пути и операции, `report.reason` — сохранённую причину остановки либо `null`. Используй их вместе с проверками и ручными шагами для итогового отчёта; результат чтения `report` сам по себе не выполняет новых проверок.

State сохраняет первые исходные байты сессии отдельно от исходных байтов текущего согласованного плана. Перед заменой плана наблюдаемые операции и прежние решения сохраняются в истории state, включая ещё не попавшие в паспорт. Новый proposal сверяет состав с прежним согласованным планом и фактическими файлами: `components.recoveredOwnership: true` показывает восстановленный состав, его digest входит в согласие, а `manifestHash` и `fromSchema` по-прежнему описывают фактический паспорт. Соседние чужие файлы не включаются. Перед записью паспорта сохраняются его точное содержимое и исходный/итоговый хэши. Паспорт вне обоих состояний останавливает продолжение. Пока state существует, `status` остаётся `incomplete`, включая сбой перед очисткой. `resume --approve DIGEST` требует нового согласия, сохраняет идентификатор, попытки, известные регрессии, историю операций/происхождения и перехода схемы. Утраченный исполняемый baseline не восстанавливается из уже изменённого проекта: сравнение остаётся `baseline-unavailable`.

Перед запуском команды записывается `commandAttempts` со статусом `running`; сохранённый результат — `completed` или `failed`. После обрыва незавершённая запись имеет неизвестный исход, даже если ожидаемый файл или `.git` присутствует. Для повтора подготовь новый proposal с точной командой в `commands` и `retryCommands: [{id, commandDigest, reason}]`: идентификатор и digest берутся из `recovery.unknownCommands`, `reason` отдельно объясняет необходимость повтора. Этот состав входит в новый digest и требует нового согласия. Неизвестный исход `install`/`git-init` блокирует продолжение, в том числе план, который молча исключает команду; записанная успешная setup-команда повторно не запускается. Проверка с неизвестным исходом без отдельного повтора остаётся `unverified / command-outcome-unknown` и не запускается скрыто. Наличие или совпадение файлов не используется как свидетельство исполнения.

## Управляемый блок

Для точечной работы с собственным блоком в Markdown (`.md` / `.mdc`) передавай `managedBlock` вместо `action` и полного `content` файла:

```json
{
  "path": "AGENTS.md",
  "managedBlock": { "content": "Используй фактические команды проекта.\nСохраняй пользовательские ограничения." },
  "reason": "Обновить только блок Tibicen, сохранив остальные инструкции"
}
```

Скрипт использует отдельные строки `<!-- tibicen:begin v1 -->` и `<!-- tibicen:end v1 -->`. Без маркеров добавляет блок и видимый в диффе разделитель; одну корректную пару обновляет на её фактическом месте. `managedBlock.content: null` удаляет только блок вместе с маркерами, не файл. Совпадающий результат не создаёт файловую операцию. Нетронутые байты сохраняются, включая CRLF; новые строки блока используют окончания его строк либо файла. Маркеры внутри fenced/indented code считаются примерами, а не управляемыми блоками.

Старые строки `<!-- tibicen:begin -->` / `<!-- tibicen:end -->` распознаются явно. Для обновления с переводом на v1 требуется `managedBlock.migrate: true`; преобразование входит в отдельно просматриваемый точный дифф и новый digest. Удаление корректного старого блока не требует преобразования. Неизвестная версия, дубликаты, вложенность, обратный порядок и повреждённая пара останавливают точечную операцию с номером строки. Исправление готовь отдельным полным `content` и точным диффом, сохраняя пользовательские решения; не обходи отказ записью вне плана. Конечные маркеры проверяются до записи и при `verify`, независимо от хэша файла.

Для форматов без поддержанного Markdown-блока остаются обычные согласованные файловые операции и паспорт с хэшами. Возвращённый proposal уже содержит итоговый `content`, исходный хэш и дифф; `managedBlock` — только вход команды `proposal`, не поле готового плана.

## Общая редакция для двух coding tools

`sharedRules` связывает один общий текст правил и стадий процесса с нативными точками входа двух инструментов. Текст составляется по решениям проекта; обязательного шаблона процесса нет. Поддержанные для этой операции версии и пути — из проверенной матрицы: Codex `0.157.0` / `AGENTS.md`, Claude Code `2.1.283` / `CLAUDE.md`. Неподтверждённый агент, версия или путь дают явный отказ до записи, а не обещание совместимости.

```json
{
  "mode": "improve",
  "sharedRules": [{
    "id": "project-process",
    "content": "Сначала изучи задачу и ограничения проекта.\nСтадии: предложение, реализация, проверка, передача результата.\n",
    "reason": "Одна согласованная редакция для выбранных инструментов",
    "targets": [
      { "agent": "codex", "agentVersion": "0.157.0", "path": "AGENTS.md" },
      { "agent": "claude-code", "agentVersion": "2.1.283", "path": "CLAUDE.md" }
    ]
  }]
}
```

Скрипт создаёт обычные точные диффы управляемых блоков обоих файлов, сохраняя нетронутые пользовательские области и окончания строк. Не добавляй конкурирующий `changes` для той же точки входа. Один блок имеет одного владельца: несколько материалов для одного пути объединяй в один согласованный текст. Старые маркеры сначала требуют отдельного явного преобразования по правилам управляемых блоков.

Возвращённый `proposal.sharedRules` хранит `id`, общий текст, `revision` (SHA-256 текста с LF и завершающим переводом строки), причину, агентов, проверенные версии и пути. Эти сведения и все файловые диффы входят в digest согласия. Паспорт и история сессий сохраняют редакции; это проверяемая связь копий, не свидетельство их загрузки агентами. После настройки постоянного процесса синхронизации нет.

Для обновления передай тот же `id`, новый `content` и `reason`: `targets` можно опустить, тогда сохраняются обе зарегистрированные копии. Пропуск всего поля или материала сохраняет прежнюю связь и не исправляет файлы скрыто. Тихое исключение зарегистрированной копии из готового плана отклоняется; перенос/отключение адаптера требует отдельного разбора. `summary.sharedRules` показывает состояние файлов после предложенных изменений. `verify` сверяет фактическое содержимое блоков с зарегистрированной редакцией, включая пути, не вошедшие в текущий файловый дифф: старая копия получает `shared-rule-copy-outdated`, отсутствующая — `shared-rule-copy-missing`. Совпадение хэша всего файла не заменяет эту сверку; пользовательские разделы вокруг блока не меняют редакцию общего текста.

После прерывания связь сохраняется в state и наследуется новым оставшимся планом; частично записанные копии не объявляются согласованными. Исправление всё равно требует нового точного плана и согласия. Schema 2 паспорта допускает это дополнительное поле; отсутствие старых записей не превращается в подтверждённую связь по совпадению текстов. Это структурная проверка редакций, не запуск команды агентов или проверка поведения новой сессии.

## MCP

Поле `mcp` — массив `{agent, trusted, operations}`. Операция: `{name, action: upsert|remove, server: {command, args, envNames}}`; `server` нужен для `upsert`. `trusted: true` означает явное доверие показанному коду сервера, включая возможный автозапуск агентом. Ввод env содержит только имена. Для Claude/Cursor скрипт подготовит точечный дифф; Codex получит ручной TOML-блок. `mcp-verify` проверяет последующее применение без запуска MCP и без вывода значений env.

Применение заново сравнивает фактические исходные и итоговые MCP-записи. Добавленный или изменённый сервер требует явного доверия к соответствующему агенту и целевому пути, включая полный raw `changes` и вручную изменённый resolved plan. `requiresExecutionTrust` не предоставляет разрешения. Форматирование, неизменённые серверы и удаление не требуют нового доверия; неоднозначный или неподдержанный конфиг требует ручного разбора до записи.

## Исполняемые проверки

Build/test/lint задаются в `commands`. `checks.profile: web` и `checks.environmentReady: true` включаются после подтверждения воспроизводимого окружения; без этого команды не запускаются. Проверки существующего проекта сравнивают исходный снимок с ним же плюс все изменения Tibicen. Возобновление без сохранённого в текущем процессе исходного снимка даёт `baseline-unavailable`.

Для уже установленных локальных Node-зависимостей передай в input:

```json
{
  "checks": {
    "profile": "web",
    "environmentReady": true,
    "environment": {
      "kind": "local-node-modules",
      "roots": ["node_modules", "landing/node_modules"]
    }
  }
}
```

`proposal` вычислит hash содержимого, число файлов/байтов, platform, arch и точную Node version. Проверь их вместе с командами до согласия на digest. Это явное доверие исполняемому package payload: содержимое зависимостей не добавляется в контекст агента, произвольные встроенные секреты эвристически не распознаются. Credential paths, `.bin`, machine metadata и caches исключаются; допустимы native bindings и относительные ссылки внутри копии проекта. Лимиты: 50 000 entries, 512 MiB всего, 64 MiB на файл. Roots должны быть непересекающимися обычными каталогами `node_modules` без ссылок в предках.

Зависимости захватываются до baseline; каждое исполнение получает отдельные байты из сохранённого снимка. Команды используют явные Node entrypoints, например `node node_modules/package/bin/cli.js`. При компиляции `node` закрепляется абсолютным путём текущего Node; иные runtime отклоняются, PATH не выбирает другую версию; `.bin` и запуск package-manager shims не поддержаны. Пакеты не устанавливаются. Несовпадение hash/runtime, недоступный root или workspace target оставляют `verify: unverified` с причиной `node-environment-*`. Временная копия сохраняет оригинал, но сама по себе не ограничивает права доверенной команды на ОС. Поле optional; прежние планы остаются читаемыми.

`checks.task` и `checks.quiz` имеют `{specification, execution}`. `specification` содержит `kind`, `prompt` и `expectedArtifacts: [{path, hash|contains}]` для задачи либо пять `questions: [{id, question, answer}]` для квиза. Ответы квиза берутся из паспорта и решений пользователя. `execution` содержит `agent`, `agentVersion`, `trusted`, `startupControlled`, `envNames` и `maxBudgetUsd`. Поддержанный контролируемый путь Claude использует только отдельно разрешённый уже доступный `ANTHROPIC_API_KEY`; значение не входит во ввод. Без авторизации, бюджета, доверия или контролируемого startup — `unverified`, новую авторизацию ради проверки не создавай.

`compat` содержит `enabled`, `pairs` и общие параметры `execution` того же вида. Пара: `{skill, ref, agent, agentVersion, path, contentHash}`. SHA и хэш берутся из проверенного источника; каталог не равнозначен загрузке. Для непрослеживаемого происхождения оставляй gap. Скрипт добавляет возможные команды проб в предложение до согласия. Маркер `__TIBICEN_PROJECT_COPY__` означает только создаваемую после согласия изолированную временную копию; остальные argv и параметры запуска не подменяются.

Если среда изменилась так, что ранее недоступная проба стала исполнимой, подготовь новое предложение. Нельзя незаметно добавить запуск к ранее согласованному плану.
