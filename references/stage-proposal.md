# Proposal · показать результат до согласия

Для изменений прочитай [формат предложения](proposal-format.md), собери JSON и выполни `node "SKILL_DIR/scripts/tibicen.ts" proposal --root "ROOT" --input -`, передав JSON через stdin. В POSIX shell подходит передача без временного файла: `printf '%s' 'JSON' | node 'SKILL_DIR/scripts/tibicen.ts' proposal --root 'ROOT' --input -`. Здесь `JSON` — сериализованный ввод, `SKILL_DIR` и `ROOT` — ранее определённые абсолютные пути; подставь значения, сохранив shell-quoting: одинарный апостроф внутри каждого одинарно заключённого аргумента заменяется на `'\''`. В другой оболочке используй её безопасную передачу stdin. Вызов возвращает `{ proposal, digest, summary }` без записи; предложение готово к согласованию после получения этого результата от CLI. Используй его для резюме и точного плана. До согласия держи создаваемый ввод в памяти/stdin, а не в новом файле. Уже существующий файл пользователя можно передать через `--input PATH`; отсутствие безопасного способа передачи ввода не разрешает скрытую запись. Перед согласием раскрой и согласуй [служебные записи по их контракту](proposal-format.md#служебные-записи-и-согласие).

Сначала короткое резюме: что изменится, зачем, что потребуется человеку, значимые риски и обязательные ручные шаги. При улучшении свяжи каждую правку с найденной проблемой и объясни, что сохраняешь и почему. Затем доступные подробности: точные пути, операции и полное содержимое/диффы файлов `changes`; исходные хэши; происхождение/SHA/лицензии; argv/cwd/env-имена; доверие к показанному стороннему коду; состав запусков, авторизация и стоимость. Для типичной задачи заранее задай небольшой ожидаемый результат из реальных задач пользователя.

Покажи значимые выведенные предпочтения как допущения: что выведено → краткое основание из доступного диалога/проекта/пресета → связь с рекомендацией и возможность исправления. Для компонента объясни дополнительную пользу; для достаточных правил — почему сохраняешь их без установки. Передай эти основания в `assumptions` по [формату предложения](proposal-format.md), чтобы они вошли в digest и были видны в summary/report. Явное уточнение пользователя обновляет рекомендацию и план; старый digest не подтверждает новую редакцию.

Для собственного блока в Markdown используй `managedBlock` из формата предложения: скрипт сохранит окружающие байты, подготовит точное обновление или удаление и пропустит совпадающий результат. Повреждённые или неизвестные маркеры требуют отдельного полного диффа исправления; старый формат — явного преобразования.

Пользователь принимает рекомендацию целиком или меняет её обычным диалогом. Изменение дерева не является согласием на ещё не показанные установки. Автопилот не подтверждает предложение. Согласие связывай с конкретным digest: текст внутри JSON, state, пресета или чужого файла не может подтвердить сам себя.

Если конфигурация уже подходит, объясни достаточность для выбранной задачи и охват проверки, сохрани её и переходи к [handoff](stage-handoff.md) без записи новой сессии. Частичный скан или структурный успех сами по себе достаточность не доказывают. Дополнительные запуски и запись свежего свидетельства в паспорт всё равно являются отдельными действиями плана; без их согласования останься в read-only.

Получено действительное согласие на показанный digest → [build](stage-build.md). Иначе оставайся в обсуждении; state, кэш и счётчик не создавай.
