Tibicen помогает настроить агентскую инфраструктуру нового проекта или привести существующую в порядок. Он работает внутри привычного агента: исследует проект, предлагает одну подходящую настройку, показывает изменения, применяет согласованное и отдельно сообщает результаты проверок.

Два входа:

- `tibicen-init` — «Настрой агентскую инфраструктуру». Для пустой папки и существующего приложения без настройки.
- `tibicen-adopt` — «Проверь и обнови агентскую инфраструктуру». Для исправления, дополнения и обновления уже имеющихся инструкций и подключений.

Исходники приложения, существующие пакетные манифесты, CI и данные при внедрении сохраняются. До согласия нет записи, установки или запуска проектного кода. Tibicen не создаёт коммиты, включая временные репозитории и проверки. После работы остаются инструкции и паспорт `.tibicen/manifest.yml`; постоянного процесса Tibicen в проекте нет.

## Локальная установка

Для сборки и работы скиллов нужен Node ≥22.20 и настроенный агент. Зависимости и сборка сайта для установки скиллов не нужны. Для доставки установщиком нужен Git; установленный Tibicen может работать без Git через временную копию проекта.

Исполнение команд контролирует группу процессов на POSIX и останавливает потомков при тайм-ауте или отмене, с запасом до одной секунды на принудительное завершение. На Windows исполнение пока возвращает `process-tree-unavailable` до запуска команды; операции чтения доступны. macOS проверена локально; Linux ещё требует платформенной приёмки.

Из папки с исходниками Tibicen сначала соберите скиллы:

```sh
node scripts/build.ts
```

Затем запустите **одну** команду подходящим менеджером пакетов:

```sh
# npm
npx skills@1.7.4 add ./dist -g --agent codex --copy

# pnpm
pnpm dlx skills@1.7.4 add ./dist -g --agent codex --copy

# Yarn 2+
yarn dlx skills@1.7.4 add ./dist -g --agent codex --copy
```

Yarn Classic 1.x не имеет `dlx`; используйте `npx`. Это выбор способа запуска установщика: менеджер пакетов и зависимости целевого проекта не меняются.

Вместо `codex` можно выбрать `claude-code` или `cursor`. Команды проверены реальной установкой обоих скиллов через npm, pnpm 11.21.0 и Yarn 4.18.1 в отдельные временные user-scope (Node 24.15.0, macOS). После установки их ресурсы доступны вне исходного репозитория. `--copy` создаёт независимую копию; `-g` устанавливает скиллы в user-scope разработчика.

В агенте явно вызовите скилл по имени и опишите проект, например: «Используй tibicen-init. Настрой агентскую инфраструктуру этого проекта, минимум процесса». Можно попросить «всё по умолчанию»: это убирает вопросы интервью, но итоговый план всё равно требует согласия.

Публичного адреса релиза пока нет. `dist/` — готовое дерево дистрибутива с двумя самостоятельными скиллами и `SHA256SUMS`; каждый содержит собственные копии общих ресурсов, автоматически собранные из единственного исходника. Для обещанной установки `npx skills add <владелец>/tibicen -g` публикуется именно это дерево. Установка из корня несобранных исходников не поддерживается.

## Работа с проектом

1. Агент исследует фактические файлы, команды, ограничения и доступные источники.
2. Предлагает достаточную конфигурацию. Дополнительный скилл или MCP появляется при понятной пользе; отсутствие лишних компонентов — нормальный результат.
3. Показывает точные пути, изменения, источники/SHA, команды, env-имена, доверие к коду, стоимость и ручные шаги. Данные предложения находятся в памяти/stdin до согласия.
4. После согласия применяет только показанный план. Изменение затрагиваемого файла другим процессом останавливает запись.
5. Передаёт результат, ограничения и первый полезный запрос. Паспорт сохраняет происхождение, изменения и историю исходной сессии.

`complete` означает завершение подключения без известного обязательного дефекта; проверки проекта и поведения имеют независимые результаты. `manual-action-required` означает оставшиеся обязательные внешние действия. При внутреннем сбое или неисправленном обязательном дефекте — `incomplete`; состояние и исходные версии затрагиваемых файлов сохраняются для продолжения с новым согласием.

## Возможности и пределы проверки

- Сканирование, изменение согласованных агентских файлов, добавление/замена/удаление, повторная проверка и продолжение сессии.
- Живой подбор из GitHub API: каноническое происхождение, полный SHA, лицензия, возраст, архивность, install-хуки, блоклист и эвристическая проверка инъекций. Число контрибьюторов не используется.
- Свежие официальные рекомендации выбранных агентов: источники, даты, структурные выдержки и gaps. Применимость оценивает агент; дата загрузки сама по себе не доказывает качество рекомендации.
- MCP stdio: точечные изменения JSON Claude/Cursor с сохранением остальных записей; для Codex — ручной TOML-блок. Значения секретов не запрашиваются; известны только env-имена. Наличие env у Tibicen не подтверждает окружение другого уже запущенного агента.
- Проверка структуры инфраструктуры для разных стеков. Build/test/lint — web-профиль, только согласованные команды на контролируемых копиях с воспроизводимым окружением. Если окружение не подтверждено, результат — `unverified`, а не ложный зелёный прогон.
- Контролируемая типичная задача, квиз и native compat имеют условный путь исполнения для проверенной версии Claude Code. Для других агентов либо отсутствия авторизации, доверия, контролируемого startup и наблюдаемого результата — `unverified` с причиной. Exit code и список обнаруженных скиллов не доказывают загрузку инструкций.
- Восстановление baseline из другого процесса не подменяется новым исходным состоянием: `baseline-unavailable`. Известные регрессии и история попыток сохраняются.
- Сохранение личного пресета и файла отчёта выполняется по отдельному явному запросу. Конструктор в `landing/` скачивает пресет в браузере без сервера и отправки ответов.

Собственные YAML-файлы записываются как JSON, совместимый с YAML. Поддерживается только это строго проверяемое подмножество: произвольный YAML, теги и исполняемые выражения не разбираются. Чужие неоднозначные конфиги требуют ручного шага.

Проверенные версии и условия запуска: [матрица агентов](references/agent-matrix.md). Полная проверка реальными агентами и пилот полезности ещё необходимы до публичного выпуска; локальные проверки не доказывают экономию времени на реальных проектах.

## Команды для разработки

Для разработки всего репозитория используйте Node 24 LTS и pnpm 11.21.0 (версия закреплена в `packageManager`). Workspace задан в `pnpm-workspace.yaml`, зависимости — в едином `pnpm-lock.yaml`. Включите pnpm через Corepack (`corepack enable pnpm`) либо установите указанную версию pnpm самостоятельно. Примеры npm/Yarn выше относятся только к установщику скиллов.

```sh
pnpm install --frozen-lockfile
pnpm lint
pnpm format:check
pnpm typecheck
pnpm test
pnpm build
pnpm eval:diagnostic --help
pnpm eval:external --help
node scripts/tibicen.ts self-test
node scripts/tibicen.ts help
```

Во время правок используйте проверки нужной области; перед интеграцией запускайте `pnpm test`.

| Команда | Область |
|---|---|
| `pnpm typecheck:core` | Корневой TypeScript и тесты, включая evals, без проверок Astro |
| `pnpm test:core` | Продуктовый цикл, адаптеры, проверки и самостоятельные скиллы; без сборки сайта |
| `pnpm test:evals` | Офлайн-стенд и подставные драйверы; без сборки сайта и вызовов моделей |
| `pnpm test:site:unit` | Сборка сайта и Node-тесты структуры страницы и клиентской логики |
| `pnpm test:site` | Сборка сайта и браузерные тесты Chromium, Firefox и WebKit |

Полный `pnpm test` сохраняет lint, форматирование, все проверки типов, сборку сайта, строгую валидацию OpenSpec и все Node-тесты. Браузерные проверки по-прежнему запускаются отдельно через `pnpm test:site`.

[Офлайн-CI](docs/CI.md) выполняет полный gate, сборку, проверку сумм и self-test распакованных поставок без авторизации моделей. Локальная проверка и фактический удалённый запуск учитываются отдельно.

Команда `pnpm eval:diagnostic` даёт документированный [вход в диагностику](docs/evals/EXTERNAL_RUNS.md): по умолчанию dry-run, либо офлайн-калибровка с fake driver. Native-запуск требует явно заданного поддержанного контракта; неподдержанный маршрут сохраняется как blocked.

ESLint проверяет TypeScript, JavaScript и Astro рекомендованными правилами. Prettier форматирует код и конфигурацию с отступом в два пробела и одинарными кавычками. `pnpm lint:fix` применяет автоматические исправления линтера, `pnpm format` — форматирование; обе проверки стиля входят в `pnpm test`. Замороженные фикстуры, копии внешних исходников, сохранённые свидетельства и документация исключены из форматирования.

Сборка использует обычный каталог `dist/`. Произвольное назначение допустимо внутри `dist/` или вне репозитория, без пересечения с исходным деревом. Каталог назначения, оба дерева скиллов и `SHA256SUMS` проверяются на опасные пути и симлинки до любой очистки.

Исходники и тесты написаны на TypeScript со строгой проверкой типов. CLI выполняется непосредственно Node ≥22.20. Для разработки и сборки лендинга нужен Node ≥22.23.4; TypeScript, Astro и инструменты проверки типов остаются зависимостями разработки и сайта. Runtime-зависимостей нет. `scripts/tibicen.ts` выдаёт структурированный JSON. Исследование и предложение ничего не сохраняют; готовое предложение и его digest передаются через stdin. `--approve` — средство связать фактическое согласие человека с конкретным планом, а не разрешение скрипту или агенту самостоятельно подтвердить ввод.

Основные команды: `scan`, `discover`, `practices`, `proposal`, `apply`, `resume`, `status`, `verify`, `report`, `preset-load`, `preset-save`. `verify` отдельно выполняет только структурную проверку. Исполняемые проверки задаются в согласованном предложении. Формат ввода и пример: [proposal-format.md](references/proposal-format.md).

Лендинг — отдельный Astro workspace в `landing/`, с адаптированными секциями AstroWind, Tailwind CSS, клиентскими скриптами TypeScript и локальными ресурсами. Происхождение секций и MIT-уведомление описаны в [landing/README.md](landing/README.md). Зависимости всех частей устанавливаются одним `pnpm install --frozen-lockfile` из корня. Запуск с обновлением при правках — `pnpm dev:site` (http://127.0.0.1:8371/). Сборка — `pnpm build:site`, просмотр сборки — `pnpm preview:site`. Статический результат в игнорируемой папке `landing/dist/` можно разместить на обычном статическом хостинге; сервер приложения и внешние ресурсы для работы страницы не нужны. Лендинг и его зависимости не попадают в устанавливаемые скиллы.

## OpenSpec для разработки

OpenSpec 1.14.3 закреплён в devDependencies. `pnpm openspec list` показывает изменения, `pnpm spec:check` проверяет требования и завершённость архивных задач; проверка входит в `pnpm test`. Скиллы разработки Codex находятся в `.agents/skills/`. Для отключения служебной телеметрии CLI задайте `OPENSPEC_TELEMETRY=0` в окружении процесса.

Продуктовое видение задаёт назначение и MVP, план — порядок этапов, OpenSpec — подробные требования и задачи конкретного изменения. Существенное новое поведение проходит через change; мелкие текстовые и CSS-правки выполняются напрямую. OpenSpec и его dev-зависимости не включаются в устанавливаемые скиллы Tibicen.

Два исходных этапа документированы ретроспективно 2026-10-22: архивы содержат исходные SHA до переписывания истории и сегодняшние свидетельства проверок. Это не утверждение, что OpenSpec применялся в прошлом или что были выполнены живые агентские испытания.
