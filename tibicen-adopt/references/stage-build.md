# Build · применить только показанное

Выбранный [процесс OpenSpec](process-openspec.md) применяется тем же proposal/apply и журналом. Служебные файлы и исходные хэши перечислены точно; установка CLI — отдельный известный шаг, без изменения зависимостей приложения. Не запускай init/update как обход показанного диффа.

Передай согласованный план скрипту `node SKILL_DIR/scripts/tibicen.ts apply --root ROOT --plan - --approve DIGEST`, передав JSON в stdin; принимаются сам proposal и полный envelope из команды proposal. Существующий файл можно передать через `--plan PATH`. Не изменяй скиллы и проект обходом применения, если скрипт отказал. Новая команда, источник или область записи требуют нового предложения и согласия.

Для существующего приложения сначала зафиксируй baseline согласованного фактического дерева, когда профиль и доверие позволяют прогон. Итоговая проверка сравнивает этот же снимок со всеми изменениями Tibicen. Невозможный baseline даёт причину `unverified`; его нельзя заменить снимком после собственных изменений.

Перед записью сверяются исходные хэши и безопасные пути. Получай выбранные файлы по показанному SHA; в установленное записывай только действительно полученные файлы. Сохраняй не затронутые планом блоки и пользовательские ограничения. Удаление допустимо только показанное. Запись секретов и коммиты запрещены, включая временные репозитории и запускаемых агентов.

При обрыве/`incomplete` state остаётся. Сначала прочитай `status`/`report`: `recovery` отличает исходный файл (`pending`), уже присутствующий итог (`matches-approved-result`) и неожиданные байты (`ambiguous`). Итог не записывается повторно; неожиданное изменение требует разбора и нового точного плана. Совпадение файла не доказывает автора записи или исход команды. Неизвестный исход setup-команды требует отдельно обоснованного `retryCommands` в новом плане; исполняемые проверки без согласованного повтора остаются `unverified`.

Для продолжения `resume --root ROOT --approve DIGEST` читает план из state, но требует заново показанной оставшейся работы и нового согласия. При явной передаче плана поддерживается `--plan -`/`--plan PATH`; исходный идентификатор сессии и история не обнуляются. После `manual-action-required` state может отсутствовать: получи новый proposal с учтённым ручным шагом, покажи точный план и новый digest, затем после согласия выполни `resume --root ROOT --plan - --approve NEW_DIGEST`. Так завершается исходная сессия; обычный `apply` начинает новую интеграцию. Текущий state schema 3 сохраняет исходные байты сессии и плана, паспорт и журналы. State schema 1/2 и неизвестные форматы автоматически не преобразуются — при отказе остановись и объясни необходимость отдельного разбора/миграции, не удаляй историю ради новой сессии. Формат повтора и границы восстановления описаны в [proposal-format](proposal-format.md).

При дефекте допустимы максимум две попытки ремонта внутри согласованной области; расширение снова согласуется. Неисправленный обязательный дефект подключения → `incomplete` с причиной и применённым. Если автоматическая часть готова и остаётся только внешний шаг человека — `manual-action-required`.

Собственные JSON-документы ограничены 8 МиБ в UTF-8 как при чтении, так и перед записью. Начальный state включает полный план, исходники и историю: превышение совокупного лимита останавливает применение до изменений. Поздний рост журнала или паспорта оставляет последнее читаемое состояние; историю не подрезай. Уже слишком большой файл прежней версии требует отдельного ручного разбора, не удаления state ради перезапуска.
