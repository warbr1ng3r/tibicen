# Optional OpenSpec process · bounded adapter revision 1

Предлагай этот процесс при подтверждённой потребности в спецификациях, стадиях и ревью. Достаточный процесс команды сохраняется. Первый адаптер поддерживает локальный spec-driven OpenSpec 1.14.3 и проверенные форматы Codex 0.157.0 / Claude Code 2.1.283. Непроверенные версии, store-конфигурация и Spec Kit дают явный gap; это не повод выполнять произвольный init.

В обычном входе proposal можно указать:

    {
      "mode": "improve",
      "process": {
        "framework": "openspec",
        "version": "1.14.3",
        "agent": "codex",
        "agentVersion": "0.157.0"
      }
    }

План показывает точные диффы и исходные хэши:

- openspec/config.yaml в JSON-совместимом YAML создаётся только при отсутствии config.yaml/config.yml;
- openspec/specs/.gitkeep и openspec/changes/archive/.gitkeep создают обычную структуру;
- собственная инструкция Tibicen — .agents/skills/tibicen-openspec/SKILL.md для Codex либо .claude/skills/tibicen-openspec/SKILL.md для Claude.

Это собственный текст адаптера, не копия генерируемых OpenSpec скиллов. Нативная CLI выдаёт шаблоны/инструкции spec-driven; её библиотека, runtime и сгенерированные development skills не входят в Tibicen. Существующие config, пользовательские changes/specs, шаблоны, AGENTS.md/CLAUDE.md и приложение автоматически не переписываются. Каталог openspec/ целиком не становится разрешённой областью записи.

Если внешнего CLI нет, автоматическая файловая часть после точного согласия выполняется, а итог остаётся manual-action-required. Отдельно согласуются версия @fission-ai/openspec@1.14.3 и место установки вне зависимостей приложения. Затем передай абсолютный путь каталога этого пакета в process.cliPackageRoot и получи новый proposal/digest. Путь к глобальному shim вместо каталога пакета не принимается.

Скрипт только читает package.json, CLI entrypoint, schema и четыре шаблона, проверяет имя/версию/лицензию и фиксирует их хэши. Это structure-and-package-resources, не проверка происхождения всей npm-среды, исполнения CLI, загрузки агентом или выполнения задачи. Host должен отдельно проверить доверие/источник и согласовать запуск CLI перед рабочим циклом. Tibicen не исполняет init/update, установщик, hooks или package scripts во время настройки.

Повторное предложение с теми же входами не создаёт файловых изменений. Локальная правка собственной инструкции сохраняется и регистрируется как preserved, включая последующие повторы. Для явной замены укажи process.instructions: replace, проверь дифф и согласуй новый digest; preserve явно оставляет текущие байты. Отсутствующие ранее сохранённые локальные инструкции не реконструируются по одному хэшу. Замена зарегистрированного агента/версии требует отдельной миграции, отсутствующей в первом адаптере.

При первой регистрации или переносе CLI меняется строка CLI invocation. Сохранённая инструкция должна содержать одну такую строку с новой точной командой; отсутствие или дублирование отклоняет proposal с process-instructions-cli-conflict. Сырой план проверяется повторно перед записью. Явно обнови эту строку, сохранив полезные локальные правила, либо запроси instructions: replace и согласуй показанный дифф. Само изменение metadata не исправляет команду в файле. Если CLI ещё не зарегистрирован, обязательный pending-шаг openspec-cli нельзя удалить, пометить done или сделать необязательным даже в сыром плане с новым digest.

Отдельный process в паспорте/schema 2 и истории хранит версию адаптера, целевой формат, режим сохранения инструкций, фактические хэши и выбранный каталог/ресурсы CLI. Старые паспорта без process читаются без изменения схемы. Незавершённый state/schema 3 сохраняет process вместе с proposal; resume использует общий журнал, новый план и согласие. Скрыто исключить зарегистрированный process из сырого плана нельзя.

Структурная verify независимо проверяет зарегистрированные материалы и ресурсы CLI, даже если произвольный внешний verifier сообщил passed. Loading, task и CLI execution остаются unverified. Наличие файлов и успешный native CLI smoke-test не заменяют живую приёмку новой агентской сессией; её ведёт отдельный стенд разработки.

После передачи новая сессия читает собственную инструкцию, использует list/status/instructions и нативные шаблоны. Создание конкретного change и реализация приложения имеют отдельные согласованные области; archive/sync требуют явного запроса. Tibicen не создаёт коммиты.
